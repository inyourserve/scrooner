## The score

A new table, `analytics.coverage_snapshot`, holds one row per day per data point (`pipeline/db/migrations/0034_coverage_snapshot.sql`), written by `scrooner-map snapshot-coverage` (`pipeline/src/scrooner_pipeline/mapper/coverage_snapshot.py`). Two aggregate rows per day are the numbers to watch:

- **`avg_metric_coverage_score`** — unweighted mean of `coverage_pct` across every *active* `analytics.metric_definition` row (64 metrics today). This is the product-facing number: what a user's screener/company-page results actually cover, on average, across everything Scrooner can currently compute. **This is the number to optimize.**
- **`avg_concept_coverage_score`** — same mean, over the 44 canonical concepts (raw tag-level coverage). A leading/diagnostic indicator, not the target itself — a metric needs *every* one of its input concepts covered for the *same period*, so concept coverage moving doesn't 1:1 translate to metric coverage moving.

Both are deliberately unweighted, hard-denominator means — no metric/concept is worth more than another in the formula, even though some clearly matter more to a real investor. Matches this project's own `doc/status/SCORECARD.md` precedent (a separate, differently-scoped score) of "one documented formula, not eyeballed."

**Current, 2026-09-03 (end of day):** `avg_metric_coverage_score` = **57.19%**, `avg_concept_coverage_score` = **73.19%**, against 5,216 active companies — individually verified row-by-row against live data (46 concepts + 64 metrics, zero mismatches) after three real bugs cost real time to find: `resolve()`'s delete scope silently wiping `total_debt_resolved`, an unresolved write anomaly in this tracker's own insert path (both `doc/learnings/2026-09-03-*`), and `expanded_metrics.py`'s delete scope silently wiping `market_cap`/`trailing_pe`/`dividend_yield`/`ebitda`/3 "days" metrics on every run (`doc/learnings/2026-09-03-expanded-metrics-delete-scope-bug.md`). Trend: 79.41% (buggy) → 54.39% (corrected baseline, 09-02) → 54.74% (item 1 closed, 09-02) → 54.76%/73.15% (item 2's 4 tags, 09-03) → 56.85%/73.19% (Priority 1 restoration + revenue fix, 09-03) → **57.19%/73.19%** (`shares_outstanding_fallback` parser generalized + run at full population, 333/504 extracted, 09-03 end of day) — **+2.80pp in one day** once the false-positive corrections are accounted for.

**A real bug in this score's own first computation, caught and fixed the same day it was built.** `analytics.metric_value` stores an explicit row with `is_null_reason` set even when a metric couldn't be computed for a company (the same traceability discipline as `excluded_missing_data` elsewhere in this project) — the first version of `_load_metric_coverage()` counted `distinct company_id` without filtering `value is not null`, so any metric with null-reason rows showed inflated coverage, several at a false 100%. First (wrong) reading: 79.41%. Fixed same-day (`coverage_snapshot.py`'s `filter (where mv.value is not null)`); every number in this doc from this point on is the corrected one. See `doc/learnings/2026-09-02-coverage-score-system.md` for the full writeup and the generalized lesson (now also in root `CLAUDE.md`'s "Notes for skill/agent authors").

To see the trend once more than one day of history exists:
```sql
select snapshot_date, item_name, coverage_pct
from analytics.coverage_snapshot
where item_type = 'score'
order by snapshot_date, item_name;
```

## Why the score is still relatively low, and the priority roadmap to move it (2026-09-03)

`avg_metric_coverage_score` (54.76%) is an unweighted mean across all 64 active metrics — including several that are *correctly, structurally* low (Piotroski's 9-simultaneous-input bar, price-dependent metrics capped by real market-data gaps) alongside real, closeable gaps. Ranked by real, estimated leverage:

### Priority 1 — [DONE] Restore 7 metrics silently wiped by a real bug found today

Re-checking the full coverage list turned up a second major infrastructure bug (beyond yesterday's `resolve()` one): `expanded_metrics.py`'s per-company delete was scoped to a dict that mixed its own 9 outputs with 8 metrics it only *reads* as dependencies — deleting all 17 on every run, reinserting only its own 9. `market_cap`/`trailing_pe`/`dividend_yield` had been silently wiped back to a genuine 0%; `ebitda`/`debtor_days`/`inventory_days`/`payables_days` were also affected. Fixed at the root (`OUTPUT_METRIC_NAMES` explicit scoping, 1 new regression test) — see `doc/learnings/2026-09-03-expanded-metrics-delete-scope-bug.md`. **3-stage full-population restoration completed, 0 errors, 348/348 batches × 3 stages, verified against live data with zero mismatches: `market_cap` 0%→60.03%, `trailing_pe` 0%→48.72%, `dividend_yield` 0%→16.09%.**

### Priority 1b — [NEW] "Should-be-near-100%" concept audit, prompted directly

Some concepts are GAAP-mandatory for any real operating company (every 10-K reports revenue, shares outstanding, total assets) and should approach 100% — a shortfall there is a stronger signal of a real, closeable gap than a shortfall in a genuinely optional/structural metric. Checked the two most likely candidates by sampling which real companies were missing each:

- **`revenue` (86.3%)**: sampled the missing companies by SIC code — most are legitimately pre-revenue (280 SPACs/"Blank Checks", 145 pre-revenue biotech/pharma, various royalty trusts/REITs/banks that use a different revenue-equivalent concept entirely). But several — **J.M. Smucker, Georgia Power, Consumers Energy** — are large, obviously revenue-generating companies with a real gap: they exclusively tag `RevenueFromContractWithCustomerIncludingAssessedTax`, a real ASC 606 variant the mapping didn't have (only the "Excluding" form was mapped). Verified via a full statistical coexistence check (3,435 real period-pairs, not a sample): 62.8% exact match — a real, if imperfect, majority relationship, safe to add at lowest priority since `first_match` can never let it override an existing better value. **Shipped** (migration `0038`, 51 new companies). A second candidate, `SalesRevenueGoodsNet`, was checked and rejected (11.9% exact match across 5,725 pairs, 67.3% diverging 10%+ — a real goods-only component for many filers, not a synonym, and only 8 new companies at stake).
- **`shares_outstanding` (91.0%)**: sampled the missing companies — **Hormel Foods, Dillard's, Constellation Brands, Cato Corp** and many others (504 active companies total) only tag weighted-average diluted/basic share counts, never a real point-in-time figure. This is the *exact* same gap `pipeline/CLAUDE.md` already documented for Block/Reddit specifically — but it turns out to affect ~500 companies, not 2, and the purpose-built fix (`company_master/shares_outstanding_fallback.py`, 10-K cover-page text extraction) had **only ever been run for 2 companies**, never at full population — the same "built once, verified small, never scaled" shape as `calculate-price-metrics` before this week. **Piloted on 30 real companies before committing to a full run** (this session's own lesson: verify generalization before trusting a small-sample success) — result: only **7/30 extracted (23%)**, 20/30 "no pattern match." The regex was built and validated against exactly 2 companies' cover-page phrasing and does not generalize to the population's real formatting diversity. Zero fetch failures — the SEC-fetch infrastructure itself is fine; the gap is purely in the extraction pattern. **Not run at full population** — this needs real parser-improvement work (sampling several more real "no pattern match" cover pages, generalizing the regex, re-verifying) before a full run would be worth the SEC-fetch budget, not a `/loop`-able quick win like the other items here.

### Priority 2 — Decide, don't just chase: Piotroski F-Score (17.98%)

Genuinely structural, not a bug — needs all 9 raw inputs simultaneously for 2 consecutive FY years. Its own inputs (`gross_profit` 48%, `total_debt` 68%) are real, separately-trackable gaps, but even fixing those to 100% wouldn't push Piotroski much past the product of its 9 inputs' coverage. Worth an explicit product decision (accept as a low-but-honest premium metric, or deprioritize display prominence) rather than treating 18% as a bug to close.

### Priority 3 — [CLOSED, non-issue, verified 2026-09-03] Re-investigated the "period-alignment gap"

Checked live before assuming anything: **4,269 companies have both `current_assets` and `current_liabilities` covered at all, and 4,265 of them have a real `current_ratio` metric value** — a 4-company gap, not the large period-misalignment the earlier framing described. `current_ratio` (81.8%) essentially matches its own inputs' joint coverage; the earlier "period-alignment" concern was stale, not a real, current bottleneck. `quick_ratio`'s real shortfall (48.0%) is fully explained by its extra `inventory` input (48.8% coverage, itself already investigated — see Priority 5's rejection above, its 3 candidate tags don't safely sum to a usable fallback). No further action needed here; `quick_ratio`'s ceiling is genuinely bounded by `inventory`'s own real, currently-unimprovable coverage.

### Priority 4 — [DEPRIORITIZED, checked 2026-09-03] `dividends_per_share`/`dividends_paid` — likely already near its real ceiling

Before investing in a new text-extraction parser (as this doc originally proposed), checked *who* is actually missing `dividends_paid` by SIC code — the same reality check that found real structural ceilings for banks/`current_assets` earlier. Result: the missing ~3,057 companies are overwhelmingly growth-stage, non-dividend-paying industries — Pharmaceutical Preparations (423), Blank Checks/SPACs (294), Software (172), Biological Products (142), Medical Instruments (112), Semiconductors (59), mining exploration (60+). These are very likely **genuine, correct nulls** (companies that simply don't pay a dividend), not filers using an unrecognized tag or disclosing it only in prose. Building a dividends-specific head parser would plausibly yield real coverage for only a small minority of the "missing" population — **deprioritized below Parser 3 (Part 2) and the remaining safe-candidate concepts**, not abandoned, but not worth the build effort ahead of higher-confidence work. Every XBRL candidate tag checked so far remains rejected (preferred-stock-specific or a subset) — that finding stands.

### Priority 5 — [REJECTED, verified 2026-09-03] `inventory`'s sum-mode fallback resolver

Checked live, at full statistical scale (30,530 real coexisting periods, not a small sample) before building anything: unlike `total_debt`'s current/noncurrent split (genuinely mutually-exclusive halves of the same balance, safe to sum), `InventoryFinishedGoods + WorkInProcess + RawMaterials` does **not** reliably equal `InventoryNet` — only 33.8% exact match, and **46.1% diverge by 10%+**. Root cause, confirmed on real companies: inventory valuation reserves/obsolescence allowances (LIFO reserves, net-of-reserve adjustments) sit between the gross component sum and the reported net figure for a large fraction of real filers — sometimes overstating (3D Systems: gross components ~10% higher than net, consistently, across 3 real years checked), sometimes understating (374Water: a consistent $50K gap in several quarters, likely an unlisted 4th component). This is a **worse** statistical profile than `SalesRevenueGoodsNet` (doc 40, also rejected). **Not built** — the verification step this project insists on before shipping any fallback caught a real, would-have-been-wrong candidate before it shipped.

### Priority 6 — Re-verify the remaining `gap_safe_candidate_found` concepts from doc 40 not yet checked

`accounts_payable` (already improved via `cf_ap_change`'s sibling), `accounts_receivable`, `depreciation_and_amortization`, `sga_expense` — same one-concept-at-a-time coexistence-check discipline as items 2/3 in the original list, lower individual leverage than 1-5 above but real, incremental, low-risk gains.

### Priority 7 — [DONE] Generalize the `shares_outstanding_fallback.py` cover-page parser

See Priority 1b above for the original finding. Read ~55 real cover pages across two samples, found 9 distinct real phrasings beyond the original 2, wrote a dedicated regex + test for each (16 tests), then extracted the whole thing into a reusable `company_master/text_extraction.py` head-parser/sub-parser framework (doc 42) — proven behavior-preserving (refactor produced byte-identical results against real data). Real success: 23% → 63.6% combined across two independent samples. Full 504-company run: **333 extracted, 0 errors.**

**Correction to this item's own original framing**: `core.shares_outstanding_fallback` does NOT feed the `shares_outstanding` canonical_fact concept at all — it's read directly by `price_metrics.py` as its own internal fallback, so the `shares_outstanding` concept score (91.0%) is unaffected by this work. The real, measured gain landed where it actually flows: `market_cap` +130 (60.0%→62.5%), `price_to_sales` +266, `price_to_book` +122, `fcf_yield` +89, and downstream into `ev_ebitda`/`ev_sales`/`peg_ratio`/`buyback_yield` (+36 to +166 each) once `calculate-expanded-metrics` was rerun against the newly-real `market_cap`.

## Cadence

`scrooner-map snapshot-coverage` now runs daily as the last step of `.github/workflows/pipeline-refresh.yml` (added 2026-09-03), after `scrooner-incremental`/`scrooner-operations`.

**A real, bigger gap found while wiring this in, deliberately not silently solved**: checked all 3 existing GitHub Actions workflows (`pipeline-refresh.yml`, `ci.yml`, `live-sec-verification.yml`) — **none of them run the Normalizer or Mapper `calculate`-family stages on any schedule.** `scrooner-incremental` (the only daily job) is Collector-only: it discovers new filing *metadata* into `raw.sec_filing_documents`, but nothing downstream ever reprocesses that into `core`/`analytics` automatically. Every full-population `resolve-facts`/`calculate`/`calculate-price-metrics`/etc. run this whole session was triggered manually. Practical consequence: today's added daily snapshot will faithfully record the score every day, but the score itself will only move on the days someone manually reruns the Mapper chain — it will NOT self-heal as new filings arrive.

**Not fixed this pass, on purpose** — automating the full reprocessing chain on a schedule is a real cost/scheduling decision, not a small addition: a full-population run took 3-4+ hours today (calculate → calculate-price-metrics → calculate-expanded-metrics alone), which is at or beyond typical CI job timeout/cost norms, and running it against the FULL population every day (rather than just the companies with genuinely new filings) would be wasteful given doc 05's "low operational burden" principle. This needs an explicit decision — likely an incremental-scope version (only companies `scrooner-incremental` found new filings for that day) rather than a full-population rerun — before building it, not a default assumed here.

### 4. Re-run the full `calculate`-family chain after any concept-mapping change

Every time a new `concept_mapping` row is added (item 2 above) or a formula-shape changes, the full `resolve-facts` → `calculate` → `calculate-expanded-metrics` → `calculate-piotroski` → `calculate-quality-flags` chain needs a full-population rerun for the new coverage to actually land in `metric_value` — this is exactly the gap that caused today's `institutional_ownership_pct`/price-metrics staleness in the first place (calculate-family jobs not rerun after their source data or mapping changed). **Standing rule going forward: any concept_mapping or formula change is not "done" until the full-population rerun has actually happened and `snapshot-coverage` has captured the new number** — don't let doc/CLAUDE.md claim a fix without that last step.
