# Doc 44 — Scrooner Systems Index

**Reference (added 2026-09-08).** Purely a lookup aid — no new decisions, no status-line convention. Since roughly doc 40 onward, several standing *systems* (not one-off scripts — each has its own table(s), CLI command(s), and keeps running/getting reused) got built in quick succession, on top of the frozen Collector→Normalizer→Mapper pipeline. This doc exists because the number of them got hard to hold in your head at once — one row per system, what it's for, where it lives, and how to run it. When a new standing system gets built, add a row here in the same pass, the same discipline as `doc/status/DATA_COVERAGE.md`.

Read `pipeline/CLAUDE.md` for the full narrative (findings, bugs, evidence) behind each — this doc is intentionally just the index.

## How they chain together

```
Collector → Normalizer → Mapper resolve()/calculate()   [frozen, doc 04/09/11]
                                │
                                ├─→ Tag Coverage Library ─── informs ──→ concept_mapping (human-reviewed additions)
                                │
                                ├─→ Concept Fallback / *_resolved concepts  (per-concept, safe, additive layer)
                                │
                                ├─→ Parser Registry (Parser 3)  ── fills genuine tag-gaps resolve() can't reach at all
                                │
                                ├─→ Statement Classification ── which concept renders on which company-page row
                                │
                                ├─→ Coverage Matrix + Coverage Snapshot ── measures how complete all of the above is
                                │
                                └─→ Data Sanity Layer (yfinance cross-check) ── independent-source correctness check,
                                          with its own Tag Investigator that traces a flagged finding back through
                                          concept_mapping's own raw core.fact rows and, when safe, writes a
                                          per-company override into the SAME *_resolved-concept mechanism above
```

Nothing downstream of `resolve()` ever writes into `core.fact`, `analytics.canonical_fact` for a `resolve()`-owned concept, or `analytics.concept_mapping` automatically — every system below is additive, sitting next to or on top of the frozen Mapper, never inside it. See `pipeline/CLAUDE.md`'s own "Notes for skill/agent authors" for why (a single company's evidence is not global evidence — the same lesson keeps recurring across several of these systems).

| **Tag Investigator / Per-Company Tag Preference** (2026-09-08, updated same day) | The "fix" half of the sanity layer: for a flagged company, traces every raw `core.fact` row under any tag already mapped to the relevant concept (including non-authoritative rows), scores each against an independent value (yfinance), and — ONLY when a candidate reconciles AND a safe `*_resolved` concept exists to receive it — stores which SEC tag to prefer for that company GOING FORWARD (every period it has data for, not just the flagged one). Never writes to `concept_mapping` (a single company's match isn't evidence a global tag-priority change is safe), and the stored value always comes from `core.fact` (a real SEC filing) — yfinance only ever detects/matches, per explicit user direction. | `sanity/tag_investigator.py` | `analytics.data_sanity_investigation` (every outcome: `auto_fixed`/`needs_review`/`no_match_found`), `analytics.company_tag_preference` (which SEC tag to prefer, per company+concept — supersedes migration 0049's per-period `canonical_fact_sanity_override`) | `scrooner-sanity investigate` (wired into the daily cron, right after `run`) | 1 real critical case investigated live so far (Commerce Bancshares) — correctly resolved to `no_match_found` (a real bank revenue-completeness gap, not a fixable tag mixup) |

## What's deliberately NOT a "system" in this list

One-off scripts that produce a static artifact and don't have a standing table/cron/CLI of their own (`build_tag_coverage_library.py`'s JSON output, `find_concept_gap_clusters.py`'s findings) are tools, not systems — they're referenced from the systems above that consume their output, not listed as their own row a second time. Doc 06's 14 project Parts (Collector, Normalizer, Mapper, etc.) are the product's actual architecture, not "systems" in this doc's sense — this doc only covers what got built ON TOP of that frozen architecture.
