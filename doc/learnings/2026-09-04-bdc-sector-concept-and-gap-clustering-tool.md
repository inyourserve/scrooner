# 2026-09-04 — A real sector-specific concept (BDCs), and a reusable "gap clustering" discovery tool

## What happened

Sizing Parser 3 (doc 42's rendered-table extraction technique) before building it — following this project's own "measure before building" discipline — turned up something more valuable than the original target. Breaking down the 693 active companies still missing `revenue` by SIC code found 44 with **no `sic_description` at all**, every one of them a Business Development Company (Ares Capital, Main Street Capital, Prospect Capital, Goldman Sachs BDC, etc.). A BDC's income statement genuinely has no "revenue" line — it starts from "Total investment income" (interest/dividend/fee income from its portfolio of loans to other companies), a structurally different concept, the same class of gap this project already recognized for banks/insurers/REITs (doc 42 Part 1).

Checked ARCC's own rendered "CONSOLIDATED STATEMENTS OF OPERATIONS" directly: "Total investment income" is tagged `us-gaap:GrossInvestmentIncomeOperating`, a standard tag (not a custom extension). Verified across the real population: 118 active companies use it (broader than the original 44-BDC sample — other closed-end funds too), values sanity-checked plausible and correctly scaled (ARCC $763M-$3.05B across real quarters/years).

## What was shipped

A new, deliberately SEPARATE canonical concept, `bdc_total_investment_income` (`mapper/expanded_concepts.py`), never merged into the generic `revenue` concept — mirroring doc 42 Part 4's own reasoning for banks/insurers: blending a lending business's investment income into `revenue` would silently corrupt `gross_margin`/`revenue_growth`/every ratio assuming a product company's cost structure. Single tag, `first_match`, `approved` confidence. Seeded and resolved for all 118 real companies, zero errors. 9 of the original 44 hand-sampled BDCs use no gross tag at all (only `NetInvestmentIncome`, already net of expenses) — deliberately left unmapped rather than substitute a net figure for what's meant to be a gross concept, an honest gap not a fix.

No downstream `metric_definition` wired to this concept yet — this pass closes the raw-data gap only (traceable, screenable via a future dedicated metric), the same "data layer first" sequencing this project used for `segment_revenue.py`.

## The reusable discovery tool

User suggestion, mid-session: instead of investigating gap companies one at a time, **group them by which tag they already share with each other** — a large shared-tag cluster among companies missing a concept is real evidence of a sector pattern (like BDCs), not something a keyword search for "revenue" would ever find (`GrossInvestmentIncomeOperating` shares no vocabulary with "revenue" at all).

Built `scripts/find_concept_gap_clusters.py` — generic over any `canonical_concept` name, not hardcoded to `revenue`. Two real refinements were needed before it produced a useful signal, both found live, not assumed:

1. **A first, naive, unfiltered version was dominated by noise.** The top "shared tags" among companies missing `revenue` were `RetainedEarningsAccumulatedDeficit`, `AdditionalPaidInCapital`, `PreferredStockSharesAuthorized` — real correlation (SPACs/shells share a simple capital-raising balance sheet shape), zero revenue signal. Fixed by restricting candidates to `unit='usd'` + `period_type='duration'` facts only — revenue-shaped concepts are always a monetary flow, which mechanically excludes instant/balance-sheet items and non-monetary tags (share counts, ratios) without needing to guess keywords.
2. **Even after that, SPACs (280) and pre-revenue biotech/pharma (~250) still dominated** every result with tags related to their shared pre-revenue business stage (IPO proceeds, related-party debt, stock issuance costs) — real correlation, still not revenue. Fixed with an optional SIC-based exclusion filter (the same categories doc 42 Part 1 already confirmed are legitimate absence, not a gap) — this is what actually let the BDC-adjacent signal surface: with SPACs/pharma/biotech/mining excluded, the missing-revenue population dropped from 693 to 181, and `ManagementFeeExpense`/`AdministrativeFeesExpense` (real fund-management fee tags, full-population count of only ~270-274 — a narrow, sector-specific signature) rose to the top.

**A third cluster surfaced as a direct result, not yet built**: the `ManagementFeeExpense` cluster (65 companies) is mostly the already-fixed BDCs (expected — they still show as "missing revenue" by design, since `bdc_total_investment_income` is deliberately a separate concept) plus a genuinely distinct sub-population of **mortgage REITs** (AGNC Investment Corp, Ellington Financial, TPG RE Finance Trust, Cherry Hill Mortgage Investment Corp, Rithm Property Trust, NexPoint Real Estate Finance) — confirmed live to have neither `GrossInvestmentIncomeOperating` nor the new `bdc_total_investment_income` concept. Mortgage REITs earn primarily interest income on mortgage-backed securities, likely reporting under an `InterestIncome`/`InterestAndDividendIncomeOperating`-family tag rather than a BDC's investment-income tag — a real, different sector cluster, flagged here but not yet investigated or built.

## Performance lesson, found live building the tool

The first version's SQL used a correlated subquery to compute each candidate tag's full-population company count inline — timed out against `core.fact`'s real ~67M-row scale (`QueryCanceled: canceling statement due to statement timeout`, the same class of timeout `unmapped-tags`'s own full-population run hit earlier the same day). Fixed by splitting into two passes: a cheap group-by scoped only to the missing-population's own facts (a small slice), then a narrow per-tag count query (using the existing `idx_fact_concept_id` index) only for the small number of top candidates that survive pass one — never a correlated subquery against the full table.

## Lesson

**Grouping a gap population by what they already share is a real, generalizable discovery method — distinct from (and complementary to) both keyword-based tag search (`build_tag_coverage_library.py`) and rendered-report label matching (Parser 3).** It found a real sector concept (BDCs, 118 companies) that a "revenue" keyword search structurally could never surface (`GrossInvestmentIncomeOperating` doesn't share the word "revenue"), and it did so cheaper than reading each company's rendered financial statement one at a time. Its own real failure mode — dominant, correlated-but-irrelevant noise from a large homogeneous population (SPACs sharing a pre-revenue capital-raising shape) — needed the same "root-cause before trusting" discipline as every other tool this project has built this week: the first unfiltered run looked broken, not because the SQL was wrong, but because the underlying population itself doesn't cluster meaningfully on revenue-relevant tags at all. The fix (a monetary-duration filter, then an already-known-structural-population exclusion) is directly reusable for the next concept this tool gets pointed at.
