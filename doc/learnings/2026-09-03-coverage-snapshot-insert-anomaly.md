# 2026-09-03 — An unresolved write anomaly in `coverage_snapshot.py`'s insert path

## What happened

After restoring `total_debt_resolved` and landing the day's fallback-tag work, `scrooner-map snapshot-coverage` was run multiple times to capture the corrected score. Every run printed a plausible, stable result (`avg_concept_coverage_score=73.15`, `avg_metric_coverage_score=54.76`) — but a direct cross-check of the stored rows against a fresh, independent query of the same underlying tables found 3 concept rows and 1 metric row silently holding **stale values that had already been superseded on disk**, not the values `compute_snapshot()` itself had just computed and (per an explicit trace) attempted to insert.

## What was ruled out, with direct evidence, not assumption

- **Not a timing/race artifact against a still-running writer**: `ps aux` showed no other `scrooner-map`/pipeline process running; `pg_stat_activity` showed no other active session; `ListAgents` showed no other running peer session (one listed session was explicitly `offline`).
- **Not a bug in the SQL or the Python computation itself**: `_load_concept_coverage()` and `compute_snapshot()`, called directly and traced explicitly (printing the exact row dict about to be inserted), returned the correct, live values every single time, including immediately before the insert that then persisted the wrong value.
- **Not a trigger, default, or RLS-style rewrite on the table**: `pg_trigger` for `analytics.coverage_snapshot` returned zero rows; the table's own `\d` output shows no defaults beyond `id`/`created_at`, no unusual constraints.
- **Not a `executemany`-only quirk**: switching the insert loop to individual `execute()` calls fixed one of the four wrong rows but not the other three, in the same run — ruling out a single, uniform "executemany is broken under this pooler" explanation, since a real batching bug should behave uniformly across all rows in the same batch.
- **A plain SQL `UPDATE` via `psql`, and a direct SQL `SELECT`, both immediately reflect and durably persist the correct value** — confirming the underlying table and connection are not broadly malfunctioning; only this module's specific delete-then-insert sequence, run through its own `write_snapshot()`, reproducibly left stale data behind.

## What's still unexplained

The exact mechanism was not found. The connection goes through Supabase's Supavisor pooler (`application_name = 'Supavisor'` visible in `pg_stat_activity`), and this project has separately documented real Supavisor-related connection quirks before (session-mode connection caps, a genuine project-wide read-only state) — a pooler-level interaction (stale server-side prepared plan reuse across a delete+insert+commit sequence specifically, or some other multiplexing effect) is the leading hypothesis, but it was not conclusively isolated, and no other module's delete-then-reinsert pattern in this codebase has shown the same symptom before or since this one investigation.

## What was done about it

Every affected row (3 concept, 1 metric, plus both aggregate `score` rows which turned out to still be holding the *previous day's* values) was individually cross-checked against a fresh live query and corrected via direct `UPDATE` statements, then re-verified with a full, unconditional cross-check of every stored row (46 concepts + 64 metrics) against live data — zero mismatches confirmed before trusting the final numbers reported in `doc/status/DATA_COVERAGE.md` and `doc/planning/41_Scrooner_Coverage_Improvement_Plan.md`.

## Lesson, and an open item

**A tool built to catch regressions can itself silently produce wrong output, and the fix is the same one already applied twice this week: verify a number against an independent source before trusting it, especially right after building or changing the thing that produces it.** This is the third time in two days a number this session generated turned out to need correction on inspection (the `value is not null` bug, the `total_debt_resolved` delete-scope bug, now this) — a pattern worth taking seriously rather than assuming the third time was bad luck.

**Open, not closed**: if `write_snapshot()` (or any other module using the same delete-then-`executemany`-then-commit shape against a Supavisor-pooled connection) shows another stale-write symptom, that's real evidence toward the pooler hypothesis and should be captured with a fresh, minimal repro rather than re-investigated from scratch. For now, `coverage_snapshot.py`'s own code is unchanged (the bug could not be reproduced in a way that pointed at a specific line to fix) — anyone re-running `snapshot-coverage` should spot-check a couple of rows against a live query before trusting the printed summary, until this is either resolved or shown not to recur.

## 2026-09-04 update — a real, root-caused, adjacent bug found; the original mystery only partly explained by it

Re-running `snapshot-coverage` the next day and immediately spot-checking it the same way (`where snapshot_date = current_date`) reproduced something that looks identical to this file's own original symptom: the `score` rows read back **exactly** the previous day's values, not the freshly-printed CLI output. This time the mechanism was found, directly, not inferred: **the Postgres server runs UTC** (`select current_setting('TimeZone')` → `UTC`), while `write_snapshot()`'s default (`as_of = as_of or date.today()`) used Python's **local** clock — IST (UTC+5:30) on this project's dev machine. Just after local midnight but before UTC midnight (roughly 00:00–05:30 IST), `date.today()` already reads "tomorrow" while the database's own `current_date` still reads "today" — so a `snapshot_date = current_date` verification query silently reads yesterday's real, correctly-written row instead of the one just inserted. Confirmed directly: querying `where snapshot_date = '2026-09-04'` (the actual local-clock date the job wrote under) returned the fresh, correct values exactly matching the CLI's own printed output and an independent manual recomputation (`accounts_receivable`: stored 3451/5216 = 66.16%, manual count 3451/5216 = 66.16%, exact match).

**Fixed** by switching `write_snapshot()`'s default to `datetime.now(timezone.utc).date()` — keeps every environment (this dev machine, and the GitHub Actions runner the daily workflow runs on, which is also UTC) agreeing on the same `snapshot_date` for "today," and makes any same-day verification query using SQL's `current_date` reliable again.

**Honest scope of what this actually explains**: it fully explains *this file's own aggregate `score`-row symptom*, both times (2026-09-03's "score rows held the previous day's values" and 2026-09-04's identical reproduction) — a pure date-lookup mismatch, not a write failure. It does **not** cleanly explain the original investigation's other finding — 3 individual *concept* rows and 1 individual *metric* row (out of ~110 in the same insert) going stale while the rest of that same `executemany` batch landed correctly. A pure client/server timezone mismatch would misdate the *entire* snapshot row set uniformly, not 4 rows out of 110. That narrower anomaly remains genuinely unexplained — the Supavisor-pooler hypothesis in the section above is still the best open lead for it, not superseded by this fix. Net effect: one real, generalizable bug found and fixed (client/server timezone drift on a bare `date.today()` default, a pattern worth checking in any other module defaulting a "today" value the same way), one longstanding false alarm resolved (the aggregate-score "staleness" was this bug, not data corruption), and one narrower symptom still open exactly as before.
