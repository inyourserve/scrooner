# yfinance Full Financial Statements system + SEC-tag-preference upgrade (2026-09-08)

Built by explicit user request, in three parts across the same session: (1) a separate system to verify quarterly statement line items (not just the Data Sanity Layer's aggregate ratios) against yfinance, (2) an upgrade to the fix mechanism ("for every data fill or fix, use only SEC EDGAR, yfinance for sanity and matching only -- we have to store the sec tag wrt metric, company and fetch from sec only"), and (3) real findings + recommendations from running both.

## Part 1: the yfinance Full Financial Statements system

Separate from `sanity/yfinance_check.py` (which only checks `.info()`'s aggregate ratios for the LATEST period). This fetches yfinance's actual per-line-item **quarterly** income statement, balance sheet, and cash flow (`Ticker.quarterly_income_stmt`/`.quarterly_balance_sheet`/`.quarterly_cashflow`) and compares every available quarter's individual line items against our own statement-table values.

New package `yfinance_financials/` (`fetch.py`, `line_item_map.py`, `compare.py`, `report.py`), new CLI `scrooner-yfinance-financials` (`seed-line-item-mapping`, `fetch-statements`, `compare`, `investigate`, `report`), three new tables (migration `0050`): `analytics.yfinance_statement_line` (raw fetched data), `analytics.yfinance_line_item_mapping` (the "tag db" for yfinance's own row labels — mirrors `concept_mapping`'s approved/provisional/rejected discipline), `analytics.statement_comparison_finding`.

**Real mechanics verified live before writing any mapping (never assumed):**
- yfinance's quarterly statement columns are **calendar quarter-ends** (2026-06-30), not a company's real fiscal quarter-end (AAPL's real Q3 2026 ends 2026-06-27) — the period join needs a tolerance window (15 days), never an exact date match.
- yfinance's `Capital Expenditure`/`Cash Dividends Paid`/`Repurchase Of Capital Stock` are reported **negative** (cash outflows); our own `capex`/`dividends_paid`/`share_buybacks` are stored positive — confirmed against a real AAPL value ($-2,455,000,000) before adding a `sign_flip` flag to the mapping.
- **Banks report no `Gross Profit`/`Cost Of Revenue`/`Operating Income`/`Operating Expense` rows at all** — confirmed live against JPM. Their `Total Revenue` is a yfinance-**computed** aggregate (net interest income + non-interest/fee income: JPM's real $52.852B = $25.511B net interest income + ~$27.3B fee income), which structurally disagrees with our own bank-specific revenue tag (`InterestAndDividendIncomeOperating`, gross interest income alone, ~$50.6B for JPM). **This generalizes the Commerce Bancshares critical finding from 2026-09-08's earlier session to the entire banking sector**, not just one company — the mapping carries a `notes` field flagging this for every bank-incompatible concept, keyed off `core.company.sic_code` (`602`/`603`/`606` prefixes).

## Part 2: SEC-tag-preference upgrade to the fix mechanism

Explicit user direction mid-session: yfinance may only ever detect/match a discrepancy, never supply the value that gets stored — every actual fix must trace to a real SEC tag, and that tag preference should be **stored per (company, concept)**, applying to every future period automatically, not just the one period a check happened to flag.

This superseded migration 0049's `analytics.canonical_fact_sanity_override` (a per-period value snapshot) with `analytics.company_tag_preference` (migration 0051) — company_id + canonical_concept_id + the specific SEC taxonomy:tag, not a value. `sanity/tag_investigator.py` rewritten accordingly:
- `_write_tag_preference()` replaces `_write_override()` — stores the winning tag, not a value.
- `resolve_company_tag_preferences()` replaces `resolve_sanity_overrides()` — for the small number of companies with a preference, pulls **every** `core.fact` row under their preferred tag (any period, any `is_authoritative` value) and reconciles per period via `_reconcile_by_mode()` (a real, majority-vote reconciliation: picks the most-common value among possibly-disagreeing filings for the same period, tie-broken deterministically by the highest fact id — directly modeled on the Flowserve case, where 2 of 3 filings agree and 1 differs by a trivial rounding amount). Companies WITHOUT a preference are untouched, passed through in bulk set-based SQL exactly as before.
- `investigate()` gained an optional explicit `period_id` parameter so a caller checking every quarter (not just "most recent") — the new statement-comparison system — can reuse the exact same fix pipeline for whichever period it flagged, instead of duplicating the tag-tracing logic.

9 new/updated tests (`test_tag_investigator.py`'s `TestReconcileByMode`), full suite 459 → 464 → verified again after every change.

## Part 3: real findings and recommendations

Ran the new system against the golden-10 (all 3 statement types, all available quarters — 7,574 raw line items fetched, cleanly).

### A real, generalizable comparison bug, found and fixed before trusting any results

First run: 151 "major" findings, dominated by companies like Nike showing **~15x** disagreements (net income $211M ours vs. yfinance's... wait, reversed: ours $3,219M vs. yfinance's $211M). Investigated before trusting it: Nike's `core.period` has **both an FY row and a Q4 row sharing the exact same `end_date`** (2025-05-31 — confirmed live, 2 FY rows plus 1 Q4 row, all three that date). The comparison's period-matching logic was including FY periods in its candidate pool for a QUARTERLY comparison, and its tie-break (both periods equidistant at zero) could pick either — sometimes landing on the FY figure while checking against yfinance's genuinely-quarterly number. This is the exact "FY and Q4 share an end_date" ambiguity `pipeline/CLAUDE.md` already documented once (2026-08-17, the company-page statement-table sort order) — now confirmed to also break a period-matching JOIN, not just a display sort. **Fixed** by restricting the comparison's own period candidates to quarterly periods only (`fiscal_period in ('Q1','Q2','Q3','Q4')`), matching yfinance's own `quarterly_*` granularity. Re-ran: major findings dropped from **151 to 10** — confirming this was the dominant false-positive source, not a batch of real bugs.

A second, unrelated efficiency bug was also found and fixed before this first real run completed: the original `compare_company()` re-queried `analytics.canonical_concept` for a concept's id, and `analytics.canonical_fact` for a value, once **per finding** (dozens per company) rather than once per company — the same per-row-in-a-loop shape this project's `restatements.py` lesson already warns against. Fixed by bulk-loading both (concept ids inside `_load_mapping()`, values inside a new `_load_our_values()`) once per company. The golden-10 `compare` command went from hanging past 60s on company #1 to completing all 10 companies in under 10 seconds.

### Finding 1 (real bug, fixed): `operating_expenses`'s `CostsAndExpenses` fallback tag is a different, broader concept

After the period-matching fix, Alphabet still showed a real, **consistent** ~140-150% overstatement of `operating_expenses` across every single quarter (not noise — same direction, similar magnitude every period). Traced directly to the SEC tags: Alphabet's priority-1 `OperatingExpenses` tag has **zero** facts at all, so `resolve()` correctly fell through to the priority-2 (`provisional`) fallback, `CostsAndExpenses` = $65,157,000,000 for Q2 2025. Checking the actual composition: `CostOfRevenue` for the same period is $39,039,000,000, and $65,157M − $39,039M = $26,118M — **exactly** yfinance's own "Operating Expense" figure for that quarter. `CostsAndExpenses` is a **total costs-and-expenses subtotal (Cost of Revenue + real operating expenses combined)**, not operating expenses alone — a different concept that happens to share vocabulary, the exact trap doc 40's tag-coverage-library work already named as a recurring risk ("every candidate is a lead to investigate, never an approval").

Sized before fixing, not assumed: **682 companies** currently depend on this exact fallback (have `CostsAndExpenses` but no `OperatingExpenses` tag at all). A coexistence test against a second real company (company_id 2378, which reports both `CostsAndExpenses` and `CostOfRevenue` for the same periods) confirmed the same pattern holds generally: `CostsAndExpenses − CostOfRevenue` always yields a plausible, positive "implied real opex" figure across 10 sampled periods, never a value that would suggest `CostsAndExpenses` is sometimes the correct concept by coincidence.

**Fixed**, per the SEC-tag-only rule: `analytics.concept_mapping`'s `CostsAndExpenses` row for `operating_expenses` (id 272) marked `confidence = 'rejected'` (with the full evidence trail in its own `notes` column) — `resolve()` already excludes `rejected` rows from resolution, the same mechanism doc 02's own confidence discipline was built for. `resolve-facts` re-run for the 682 affected companies (in progress as of this doc's own writing) to clear the wrong `operating_expenses` canonical_fact rows.

**Recommendation for the row/column naming ask**: no rename needed here — `operating_expenses`'s display label ("Operating Expenses") is already correct; the bug was in which SEC tag fed it, now fixed at the mapping layer. A genuine follow-up worth scoping separately (not done this session): `CostsAndExpenses − cost_of_revenue` is itself a safe, derivable recovery for those same 682 companies (the exact `concept_fallback.py` arithmetic-derivation shape already used for `gross_profit_resolved`/`cost_of_revenue_resolved`) — rejecting the tag stops the active overstatement but also drops those 682 companies' `operating_expenses` coverage back to null until/unless that derivation is built. Flagged as a real, sized, not-yet-built opportunity rather than silently left implicit.

### Finding 2 (verified NOT a bug — a real, defensible reporting difference): Block's `operating_income`

Block showed a large, consistent divergence too (our value roughly half of yfinance's every quarter, and opposite-signed in the most recent quarter: ours −$172.0M vs. yfinance's +$328.1M). Traced directly to the SEC tag: our value comes from Block's own **`OperatingIncomeLoss`** tag, **`is_authoritative = true`** — a real, as-filed figure straight from Block's own 10-Q, not a Scrooner resolution error. Checking whether a simple derivation (Revenue − CostsAndExpenses = $6,056.8M − $3,081.2M = $2,975.6M) reproduces either figure: it matches **neither** ours nor yfinance's, meaning yfinance's own "Operating Income" is itself a computed/adjusted figure (consistent with `quarterly_income_stmt`'s own row set carrying a separate `EBIT`/`Total Operating Income As Reported` distinction, seen live for AAPL earlier this session) — likely excluding certain items (stock-based comp, restructuring, etc.) that GAAP requires inside reported operating income but that an analyst-style adjusted view might not.

Per the explicit rule this session established (SEC EDGAR is the only value source; yfinance is for detection/matching only): **when our value is a real, authoritative, as-filed SEC figure and no simple derivation reconciles yfinance's own number either, the SEC figure is correct as-is — no fix applied.** Recorded as a documented, explained divergence (the same treatment already given to `peg_ratio`'s methodology gap in the Data Sanity Layer), not chased further.

## Verification

- `pytest tests/unit/` — 464/464 passing (up from 455 at the start of this session's yfinance-financials work).
- Live-verified end to end against the real golden-10: `seed-line-item-mapping` (29/29 mapped, 0 unresolved), `fetch-statements` (10/10 companies, 7,574 rows, 0 failures), `compare` (before/after the period-matching fix: 151 → 10 major findings), `report` (both markdown outputs read directly, not just counted).
- Both real findings (Alphabet, Block) traced to the exact underlying `core.fact` rows via direct SQL before any conclusion was drawn or any fix applied — never inferred from the comparison numbers alone.
- The `operating_expenses` `CostsAndExpenses` rejection's blast radius (682 companies) was measured before acting, and a coexistence test against a second, independent company confirmed the pattern generalizes rather than being an Alphabet-specific artifact.

## What's NOT done (named, not silently dropped)

- The 682-company `operating_expenses` coverage recovery (deriving from `CostsAndExpenses − cost_of_revenue`) is scoped above but not built.
- Only quarterly statements are fetched/compared — annual (`income_stmt`/`balance_sheet`/`cashflow`, no `quarterly_` prefix) would need its own period-matching logic (FY periods this time, not excluded) and wasn't built this pass.
- This system was only run against the golden-10 — a full-population run would cost 3 yfinance requests per company (3x the Data Sanity Layer's own cost) and hasn't been sized/scheduled yet; deliberately not run blindly at scale before these two real findings justified building it at all.
