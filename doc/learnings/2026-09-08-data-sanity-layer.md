# Data Sanity Layer (2026-09-08)

Built by explicit user request: "create a data sanity layer with yfinance, which will check the data correctness and report it, it will be continuous run."

## What it is

An independent, continuous cross-check of a handful of our own computed values against yfinance (Yahoo Finance) -- a genuinely separate data source from SEC EDGAR, so a real pipeline error has a real chance of surfacing here rather than staying invisible because every other check we have is downstream of the same pipeline. yfinance is an **observer, not an authority** -- this project's data moat is still SEC EDGAR, parsed once, traceable to a filing (doc 01/02); a mismatch here means "go look," never "overwrite our value with Yahoo's."

## Design decisions

- **"Continuous run" = a daily GitHub Actions cron** (`.github/workflows/pipeline-sanity.yml`), not a long-lived process -- matches doc 02's locked "no Redis/Celery" stack and the existing `pipeline-refresh.yml` precedent, the only "continuous" shape this project's infra actually supports without adding new operational burden.
- **Rotating batch, not the whole population daily.** yfinance has a real, tightening rate limit (see `company_master/yfinance_industry.py`'s own docstring); checking all ~5,216 active companies every day isn't necessary for a sanity layer and risks the exact throttling that module already documented. `pick_rotation_batch()` always picks the coldest-checked companies first (`checked_at asc nulls first`), so the whole population cycles through over roughly a week at the default `--limit 750`.
- **Shares the SAME `CrossProcessRateLimiter` lock file as `yfinance_industry.py`** (`DEFAULT_RATE_LIMITER_LOCK_PATH`, imported directly, not a second lock path) -- both modules hit the same Yahoo endpoint, so they share one aggregate budget rather than each independently pacing against the full limit and doubling real throughput if both happen to run in the same window.
- **Four checks, chosen for a clean unit match**, not maximum coverage: `market_cap`, `trailing_pe`, `shares_outstanding` (all straightforward numeric comparisons against `analytics.metric_value`/`analytics.canonical_fact`), and `revenue_zero_check` (a special-cased boolean check, not a pct-diff comparison -- see below). `dividend_yield` was deliberately excluded: yfinance has changed its own representation of that field across versions between a fraction and a whole percentage, a real unit-ambiguity trap not worth guessing through for a correctness check.
- **Per-metric severity thresholds, not one universal threshold.** `market_cap`/`trailing_pe` tolerate more drift (10%/30% minor/major) than `shares_outstanding` (3%/15%) -- Alpaca's delayed-SIP price feed vs. whatever Yahoo's own quote source is, plus "trailing" window definitions rarely aligning to the day, mean real, expected drift exists for price-derived metrics. A single tight threshold would flood every run with noise and bury the findings actually worth a human looking at.

## `revenue_zero_check` -- built specifically off yesterday's finding

The 4th check exists directly because of [`2026-09-07-statement-table-coverage-and-revenue-zero-bug.md`](2026-09-07-statement-table-coverage-and-revenue-zero-bug.md): `resolve()` can return an authoritative-but-spurious $0 for Revenue. `revenue_zero_check` flags exactly this shape: our latest-period revenue is 0/missing while yfinance's `totalRevenue` is a real, material (>$1M) number.

**A real calibration bug was found and fixed on the very first test run** (golden-10, before this went anywhere near production): TSM, Enbridge, and Ares Capital (a BDC) all fired as false-positive "critical" findings. The actual cause: all three have **zero** `revenue` canonical_fact rows ever -- a real, already-documented structural absence (Foreign Private Issuer reporting quirks for TSM/Enbridge; Ares Capital is a BDC, whose real concept is `bdc_total_investment_income`, deliberately kept separate from `revenue` per doc 42's sector-isolation reasoning) -- not the Flowserve-shaped bug this check targets. Fixed by requiring `has_revenue_history` (at least one `revenue` canonical_fact row, ever) before the check can fire at all; a company with no revenue concept captured is `DATA_COVERAGE.md`'s concern, not this layer's. Verified: golden-10 re-run went from 3 false "critical" findings to 0.

## A second real bug found the same session: stale rows never cleared

The first implementation used a plain per-row `ON CONFLICT (company_id, metric_name) DO UPDATE`. After fixing the calibration bug above and re-running, the `report` command **still showed the old, now-incorrect "critical" findings** for TSM/Enbridge/Ares Capital -- because `_check_revenue_zero` now correctly returns `None` for all three (nothing to upsert), a plain upsert never touches or deletes the stale row from the previous run. The old wrong finding just sat there forever, undetectable from the report alone.

Fixed by switching `_write_batch` to delete-then-reinsert, scoped to the companies actually evaluated that run (not a blind `DELETE FROM ... WHERE 1=1`) -- the same discipline this project already applies everywhere else a batch job's output set can shrink between runs (`resolve.py`, `concept_fallback.py`). A company skipped this run for a transient fetch failure/rate limit/no ticker is explicitly excluded from the delete scope, so it keeps its last-known-good rows rather than losing them just because this particular run couldn't reach it.

**Generalizable lesson, worth restating even though this project has hit adjacent versions of it before:** any batch job whose per-item output can be "nothing to write" (not just "a different value") needs delete-then-reinsert, or an equivalent explicit-absence signal -- a plain upsert can only ever add or change rows, never remove a finding that's no longer true. Verify this specifically by checking that a finding which SHOULD disappear between two runs actually does, not just that a new finding appears correctly.

## Two known false-positive patterns, documented rather than chased

Confirmed real but NOT bugs, found while calibrating the first live run — a future reader triaging a `major` `shares_outstanding`/`market_cap` finding should check for this shape before assuming a Scrooner data error:

- **Alphabet (GOOGL/GOOG): our `shares_outstanding` (12.23B) is 121% above yfinance's (5.53B) for the `GOOGL` ticker specifically.** Alphabet has three share classes (A/B/C); our XBRL-sourced figure very plausibly captures the combined total across all classes, while yfinance's `sharesOutstanding` for one specific ticker reports only that class's float. `company_master/security_type.py`'s own docstring already names Alphabet's dual/triple share classes as having "more than one legitimately valid primary candidate" for an unrelated reason (ticker resolution) -- same underlying multi-class structure, a different symptom.
- **Nike (NKE): our `shares_outstanding` (855M) is 29% below yfinance's (1.20B), and `market_cap` is 41% below.** Nike also has two share classes (A closely-held, B publicly traded as NKE); the same multi-class ambiguity likely applies in the opposite direction.

Not fixed this session -- a correct fix needs a genuinely multi-class-aware shares-outstanding model, out of scope for a first version of the sanity layer whose job is to surface disagreements, not resolve every one immediately.

## Part 2, same day: wiring an actual fix, not just a report

Direct follow-up request: "wire up solution as well, if something problem with data, so fix the fetcher tree for particular data and check which tag will be correct for that metric for that company and store that in db."

**Deliberately does NOT write to `analytics.concept_mapping`.** `resolve()` was checked directly (`resolve.py:45`, `where confidence != 'rejected'`) and confirmed to use every non-`rejected` tier in actual resolution -- so even a `'provisional'` concept_mapping row would immediately change `resolve()`'s output for **every** company reporting that tag, not just the one company a sanity finding was raised for. This is the exact single-company-generalized-to-everyone risk doc 40's tag-coverage-library work already learned the hard way ("every candidate is a lead to investigate, never an approval"). A real match for one company is real evidence for that company; it is not evidence a global tag-priority change is safe.

**What got built instead**, new `sanity/tag_investigator.py` + migration `0049`:

1. `find_candidate_tags()` -- for the flagged (company, period), pulls **every** raw `core.fact` row under any tag currently mapped to the relevant canonical concept, including rows `resolve()` marked `is_authoritative=false`. This is the actual "fetcher tree" trace the request asked for -- not a fuzzy keyword search across all XBRL tags, but everything this company's own filings already reported under a tag this concept already recognizes.
2. `_score_and_decide()` (a pure function, unit-tested independently of the database) -- scores every candidate against the external (yfinance) value, picks the closest, and classifies the outcome three ways:
   - **`auto_fixed`** -- within tolerance (20%, wider than the sanity check's own thresholds since revenue's real reporting period doesn't line up exactly with yfinance's trailing-twelve-month window) AND the concept has a `*_sanity_resolved` concept wired up to receive the fix.
   - **`needs_review`** -- within tolerance, but no `*_sanity_resolved` concept exists yet for this concept (e.g. `shares_outstanding` -- a real lead, correctly not auto-applied without somewhere safe to write it).
   - **`no_match_found`** -- nothing reconciles. An honest, recorded outcome, not silence -- most `shares_outstanding` investigations land here, since the standard Company Facts API strips dimensional/per-share-class XBRL data entirely (doc 22), so the tag that would actually explain Alphabet's/Nike's multi-class mismatch usually isn't in `core.fact` at all to find.
3. The actual fix: `analytics.canonical_fact_sanity_override` (company_id, canonical_concept_id, period_id, value, evidence) -- scoped to exactly the one (company, period) verified, never a blast-radius-widening rule. Merged into a THIRD concept (`revenue_sanity_resolved`, migration `0049`) via `resolve_sanity_overrides()` -- the identical "new resolved concept, zero concept_mapping rows, resolve() never touches it" idiom already established by `total_debt_resolved` (0033) and `gross_profit_resolved` (0047), just sourced from a targeted per-company override instead of a global tag or an arithmetic derivation. Set-based SQL (one DELETE + one INSERT...SELECT), not a per-company loop, same discipline as every other batch job in this codebase.
4. Every outcome -- fixed, needs review, or no match -- is recorded in `analytics.data_sanity_investigation` (upserted per company/concept/period), so "we looked and found nothing reconcilable" is a distinct, visible outcome from "never investigated."
5. Wired into the daily cron (`.github/workflows/pipeline-sanity.yml`): `sanity run` → `sanity investigate` → `sanity report` -- detect, attempt-fix, report, every day, on the rotating batch.
6. `statements/classify.py`'s Revenue row now reads `revenue_sanity_resolved` instead of raw `revenue` (mirroring the exact same repoint done for Gross Profit/Cost of Revenue/Operating Expenses in the earlier statement-table pass). **Deployment-order gotcha, caught before it caused a real outage:** `revenue_sanity_resolved` starts with ZERO rows the moment it's created -- repointing the statement line to it before ever running `resolve_sanity_overrides()` at least once would have shown a blank Revenue row for every company on the site, even with zero actual overrides needed. Fixed by running `scrooner-sanity investigate` once immediately after the repoint (it unconditionally re-merges every `FIXABLE_CONCEPTS` entry at the end, regardless of whether any findings existed to investigate) -- confirmed live: 317,366 rows, an exact 1:1 passthrough of raw `revenue`, before any override existed. Live-verified on AAPL's actual rendered page afterward: unchanged real values.

Scope note: only `statements/classify.py`'s display layer was repointed. `calculate.py`/`ttm.py`'s metric formulas (margins, growth rates, etc.) still read raw `revenue` directly -- a company whose revenue gets auto-fixed at the display layer would still compute ratios from the old, wrong value until those consumers are repointed too. Named as a real, scoped v1 limitation, not silently glossed over -- follows the same "additive extension, not a full rewire" pattern doc 47's Gross Profit fix used, which also only reached the statement table.

### First real end-to-end test, same day: the safety guardrail worked exactly as designed

A 400-company live batch (real active population, not golden-10) surfaced exactly ONE real `critical` `revenue_zero_check` finding: **Commerce Bancshares (CBSH)**, our revenue $0 vs. yfinance's $1.84B. Running `investigate` against it found the closest candidate tag (`InterestAndDividendIncomeOperating` = $407M) still **77.9% off** -- correctly classified `no_match_found` rather than forced through as a fix. The real root cause, surfaced by looking at the actual number: Commerce Bancshares is a **bank**, and `revenue`'s only tag that has any value at all for it is interest income alone -- missing non-interest income (fees, etc.), which is what pushes a real bank's total revenue several times higher. This is a genuinely different problem (a revenue-concept completeness gap for banks) from the resolve()-authoritative-$0 bug this check was built to catch, and the investigator correctly told the difference rather than assuming every `revenue_zero_check` hit has the same cause.

**Found and fixed a real overclaiming bug in the sanity check's own note text because of this:** `_check_revenue_zero`'s note unconditionally said "matches the resolve() authoritative-$0 bug found 2026-09-07" for every critical finding, presuming a specific root cause the check itself hadn't verified. CBSH proved that claim false for a real case. Fixed to say "same SHAPE as... but not necessarily the same root cause" and point at `scrooner-sanity investigate` for the real answer -- **the investigation step is the source of truth for root cause, the initial check is only a shape-based trigger.** No cases in this same 400-company batch reached `auto_fixed` (all 16 traceable findings -- the 1 critical plus a slice of the 15 `shares_outstanding` majors -- correctly resolved to `no_match_found`), which is itself a reasonable, safe outcome for a first real-world run: the system did not force a wrong fix anywhere just to produce one.

## Part 3, same day: "why not all the metric?" -- widened from 3 checks to 22, and found 2 more real bugs before shipping any of it

Direct follow-up. The original scope (market_cap, trailing_pe, shares_outstanding, plus the revenue-zero special case) was deliberately narrow -- "clean unit match only." Checking a real AAPL `.get_info()` payload directly (not assuming) showed it already carries ~20 more fields with a real counterpart in `analytics.metric_definition` -- and since the full payload is already fetched per company for the original 3 checks, examining more of it costs **zero additional yfinance requests**.

`METRIC_MAPPINGS` (a new table-driven config in `yfinance_check.py`, replacing the old hardcoded 3-tuple) went from 3 to 22 metrics: `dividend_yield`, `debt_to_equity`, `price_to_book`, `price_to_sales`, `roe`, `roa`, `operating_margin`, `gross_margin`, `ebitda_margin`, `net_margin`, `quick_ratio`, `current_ratio`, `institutional_ownership_pct`, `payout_ratio`, `ebitda`, `ev_ebitda`, `ev_sales`, `revenue_growth_yoy`, `peg_ratio`, plus the original 3 and the revenue-zero check. Deliberately excludes anything doc 02 scopes OUT of this product entirely (analyst targets/ratings, short interest, beta, governance/ESG scores) -- there's nothing to sanity-check against a metric we don't compute.

**Two real unit-scale traps found and fixed before any of this shipped**, both caught by checking a real value, not assuming a field's representation: yfinance's `dividendYield` is a whole-percentage number (0.34 meaning 0.34%) while ours is a plain fraction (0.0034); `debtToEquity` is likewise percentage-scaled (78.445 meaning a 0.78 ratio) while ours is a plain ratio. `METRIC_MAPPINGS` carries a `(normalize_ours, normalize_external)` pair per metric, defaulting to identity, only overridden where live-verified necessary.

**Two real, independent pipeline bugs surfaced immediately on the first live AAPL run** -- both found BECAUSE this expansion happened, not despite it:

### Bug 1 (fixed): `ebitda` metric_value was only ever a single quarter, never a real TTM figure

Our stored `ebitda` for AAPL: **$39.0B**. yfinance's: **$168.0B**. A ~330% gap that looked like a serious data error. Root cause, found by checking the actual stored rows: `ebitda`'s `metric_value` rows exist only per-quarter (Q1-Q4) and per-FY (`calculate.py`'s own generic-engine output) -- **never a TTM row**. `mapper/expanded_metrics.py`'s `_ebitda_ttm()` helper already correctly sums the 4 most recent quarters internally (to compute `ev_ebitda`/`net_debt_ebitda`/`ebitda_margin`/`debt_to_ebitda`), but that sum was never persisted anywhere else could read it -- so any OTHER consumer (this sanity layer's own "most recent period" query, a future feature, a human debugging) could only ever see one quarter. AAPL's own last 4 quarters ($39,015M + $39,324M + $54,066M + $35,554M = $167,959M) match yfinance's figure to within $3,136 -- six decimal places of agreement, not a coincidence.

**Fixed** by persisting `_ebitda_ttm()`'s own already-correct result as a genuine `period_label='TTM'` row for the SAME `ebitda` metric_definition_id (`expanded_metrics.py`, `OUTPUT_METRIC_NAMES` gains `"ebitda"`) -- safe specifically because the delete that scopes this module's writes already filters `period_label = 'TTM'`, a label `calculate.py`'s own Q1-Q4/FY rows never use, so the two writers can never collide. Verified live: AAPL's new TTM row is exactly $167,959,000,000. Test suite updated (`test_expanded_metrics.py`'s `OUTPUT_NAMES`/`DEPENDENCY_NAMES` -- `ebitda` moved from the latter to the former, with an explicit note on why this doesn't reopen the 2026-09-03 delete-scope bug the test file itself was written to catch). Rolled out full-population via `calculate-expanded-metrics` (a pure local recomputation, no new fetches -- same idempotent, safe-to-rerun operation this project has run many times before).

### Bug 2 (fixed): `roa` had the exact same annualization trap `roic`/`roe`/the "days" metrics already got a fix for -- just never given it

Our stored `roa` for AAPL: **7.8%** (most-recent period). yfinance's `returnOnAssets`: **27.1%**. Checking AAPL's own `roa` rows directly showed why: quarterly rows sit at 7-11% (one quarter's net income over a full-year-scale balance-sheet snapshot), while the **FY** row correctly shows **31.2%** -- much closer to yfinance's figure (the residual ~4pp gap is plausibly yfinance averaging beginning/ending assets rather than using year-end assets, a real but minor definitional difference, not investigated further). This is the identical trap `pipeline/CLAUDE.md` already documents for `roic`/`roe` and the three "days" metrics: dividing a period FLOW (net income) by a point-in-time STOCK (total assets) only makes sense when the flow is annual -- a quarterly numerator understates the true rate ~4x for the same balance.

**Fixed** by adding `"roa"` to `calculate.py`'s `FY_ONLY_METRICS` set (previously `{"roic", "roe", "debtor_days", "inventory_days", "payables_days"}`) -- the exact same one-line-of-membership fix already proven for 5 other metrics hitting this same trap, no new mechanism needed. This means `roa` will only ever be computed/stored for FY periods going forward; the misleading quarterly rows stop being written on the next `calculate` run. Full population rollout of `calculate` (not just `calculate-expanded-metrics`) is a larger, separate follow-up given the fix landed the same session as the ebitda one -- tracked as the next action, not silently left undone.

**Both fixes came directly from widening the sanity layer's own metric coverage** -- neither bug would have been found by the original 3-metric scope, and both were caught by the exact mechanism the layer exists for: an independent source disagreeing enough to be worth investigating, verified against real stored rows before touching any code.

## What's NOT covered (named, not silently dropped)

- **Dividend yield** -- excluded per the unit-ambiguity reasoning above.
- **Revenue itself, as a precise pct-diff check** -- only the zero-vs-material special case is checked; a full TTM-revenue reconstruction (summing trailing quarters, handling cumulative-YTD tagging) would be needed for a real numeric comparison against yfinance's `totalRevenue`, and that reconstruction logic already exists elsewhere (`mapper/ttm.py`) but wasn't reused here to keep this module's first version small and independently understandable.
- **Balance sheet / cash flow lines** -- entirely out of scope for v1; the four checks here are valuation/share-count only.
