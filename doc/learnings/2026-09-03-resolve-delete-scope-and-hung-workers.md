# 2026-09-03 — Two real operational bugs found chasing coverage gains: a silent data-wipe and a multi-hour worker hang

## Bug 1: `resolve()`'s delete-then-reinsert silently wiped `total_debt_resolved`

While verifying today's new coverage-score snapshot after landing 4 new fallback tags (`research_and_development` ×2, `operating_expenses`, `cf_ap_change`, doc 41), the score went **down** — `avg_metric_coverage_score` 54.74%→51.47%, driven by `debt_to_equity` collapsing 70.6%→0.5%, `net_cash`/`net_cash_per_share` collapsing to 0%, `roic` dropping 48.9%→38.1%. Purely-additive `first_match` tag changes should never *decrease* coverage — this was a real regression, not noise.

Root cause: `mapper/resolve.py`'s `resolve_for_company()` deletes a company's **entire** `analytics.canonical_fact` row set (`delete ... where company_id = %s`, no concept filter) before reinserting only the concepts it manages. This is deliberate and correct for its own stated purpose (Mapper Day 2's own comment: prevents orphaned stale rows when a tag mapping is later rejected). But `total_debt_resolved` (doc 40's fallback-merge concept) has **zero** `concept_mapping` rows by design — it's populated only by `mapper/concept_fallback.py`, never by `resolve()`. Every `resolve-facts` run therefore deletes `total_debt_resolved`'s rows and never puts them back; only an immediate, explicit `resolve-concept-fallbacks` rerun restores them. `concept_fallback.py`'s own docstring already said this ("must run after resolve-facts") — but nothing *enforced* it, and two reruns today (`resolve-facts` → `calculate`, without `resolve-concept-fallbacks` in between) silently dropped it, invisible until the next coverage snapshot caught it by comparing day-over-day numbers.

**Fixed at the root, not by remembering the right run order**: `resolve.py` now loads the set of `canonical_concept_id`s that have ever had *any* `concept_mapping` row (rejected or not) and scopes the delete to only that set (`_load_managed_concept_ids()`). A concept with zero mapping rows is now structurally immune to `resolve()` touching it at all — this closes the gap for `total_debt_resolved` today and for any future zero-mapping fallback concept, without depending on an operator remembering a specific command sequence. 2 new unit tests (`tests/unit/test_mapper_resolution.py`), including one that directly reproduces the exact shape of this bug (a concept present in `mapping_index` with an empty `mappings` list, matching how every zero-mapping concept actually looks to `resolve_for_company()`).

## Bug 2: workers can hang for hours, not just minutes — and killing them can crash the whole batch, not just the one company

Separately, a full-population rerun stalled: `pg_stat_activity` and direct process inspection found 3 of 6 `xargs -P 6` workers had been alive-but-stuck since a single moment 4+ hours earlier, with `xargs` unable to start new batches in those slots. `pipeline/CLAUDE.md` already documents "silent multi-minute hangs" as a known Supabase-pooler issue — this was the same failure mode, just at a scale (hours, not minutes) not previously seen or planned for.

Compounding it: `common/errors.py`'s `log_error()` (the shared per-company dead-letter handler used at 20 call sites across the Normalizer and Mapper) was itself unprotected — when the *original* failure was the connection dying, `log_error()`'s own `rollback()`/insert/`commit()` calls also raised, and nothing caught that second exception. The documented contract ("one company's exception must never abort the batch") was silently violated: one dead connection crashed the *entire remaining batch* of up to 15 companies instead of just skipping the one that failed.

**Fixed**: `log_error()` now wraps its own operations in try/except, logging a warning instead of raising if the connection itself is unusable — restoring the actual documented contract regardless of *why* the original company failed. Also armed an operational watchdog (a Monitor polling `ps` every 60s, killing any `scrooner-map` worker older than 12-15 minutes) for the rest of this session's reruns, since 15 minutes is far outside any observed legitimate single-batch runtime (normal full-population stages complete in 25-45 minutes across 348 batches at 5-6x parallelism).

## A confusing side effect worth naming: "STAGE DONE" printed after a run that only did ~17% of the real work

The stalled run above eventually printed a clean `=== STAGE DONE: calculate ===` from the wrapping bash script, and `xargs`'s own exit implied every batch line had been consumed — but only 889 of 5,216 companies actually got a `calculate.company_done` log line, and the log had zero further diagnostic signal explaining the other ~4,300. `xargs` moving past a line (because its child process exited, killed or otherwise) is not the same claim as "that line's work completed" — a wrapper script's own success message reflects the *shell pipeline* finishing, not the *underlying job*. Verified via the database directly (`min`/`max company_id` actually touched) rather than trusting the log's own completion banner — the same "verify against real state, not the tool's self-report" discipline this project's `run-collector-day` skill already encodes for a different layer (a remote agent's own status claims).

## Lesson

Both bugs share a shape: **a documented safeguard or contract existed, but relied on something outside the code enforcing it** — a comment saying "run this stage right after that one" instead of code that can't be run out of order; a docstring promising "never aborts the batch" instead of a try/except that actually guarantees it. Whenever a module's own docstring states an operational *must* ("must run after X", "must never do Y"), treat that as an unfinished implementation task, not a completed one, until something structural (not just documentation) makes the violation impossible or at least loudly visible. The coverage-score tracker itself is what caught bug 1 — a second, independent confirmation (after `doc/learnings/2026-09-02-coverage-score-system.md`'s own finding) that a real, comprehensive daily measurement catches classes of regression that spot-checks and per-feature verification never will.
