# 2026-09-10 — Screener performance rewrite: root cause, fix, and two real bugs found verifying it

Prompted by a performance recommendation doc (`doc/faster-loading/fast.md`) claiming a simple ROE screen took ~23s because the Screener "reconstructs screening data from normalized filing tables on every request." That framing was checked against the live code before trusting it, per this project's own discipline — and it turned out to be wrong in an important way: the Screener already read a precomputed table (`analytics.metric_value`), not raw filing tables. The real cause was different, and finding it changed what got built.

## Measuring before building

A real `ROE > 0.15` screen via `scrooner-screen run` took **13.9s** wall-clock; a no-predicate baseline took **5.0s**. `EXPLAIN (ANALYZE, BUFFERS)` on the exact query `screener/resolve.py`'s `resolve_most_recent_values` runs (a `row_number()` window function over `analytics.metric_value`, filtered to one `metric_definition_id`) showed:

- With default `work_mem`: a 205,699-row external merge sort spilled to disk (`Sort Method: external merge Disk: 12016kB`) — 6.8s of the query's 6.85s total.
- With `work_mem` bumped to 128MB: the sort became an in-memory quicksort (fast), but total time barely improved (4.98s) — the real cost shifted to a **Bitmap Heap Scan** on `metric_value` reading **16,269 heap blocks from disk** (`Buffers: ... read=16269`) to fetch those 205,699 rows for a single metric.

The table has an index on `metric_definition_id` (added 2026-08-22, `idx_metric_value_metric_definition_id`) — this was never an unindexed-query problem. The real issue: `metric_value` holds 11M+ rows across 82 metrics, and rows for one `metric_definition_id` are scattered across the table's entire physical storage (no clustering by metric), so even an index-driven fetch has to touch pages spread across the whole table, almost none of them in cache.

Separately, measured this dev machine's round-trip latency to the project's Supabase instance (`us-east-1`, confirmed via `mcp__supabase__list_projects`): **~270ms per query round trip**, and a fresh `psycopg.connect()` costs **~1.7s** for TCP+TLS+auth alone. Both matter for the fix design below.

## The fix

1. **`analytics.company_screening_snapshot`** (migration 0061) — a narrow EAV table (`company_id, metric_definition_id, value, period_label, period_end, formula_version, dataset_version`), rebuilt offline by `screener/snapshot.py`'s `build_snapshot()`, which reuses `resolve_most_recent_values()` unchanged (same TTM-preferred/latest-`period_end` rule, just run once across all 82 metrics instead of once per request). Full delete-then-reinsert per rebuild, one transaction, `dataset_version` bumped atomically with it. Kept as a narrow EAV table rather than one-column-per-metric specifically because this project adds a new `metric_definition` every few days — a wide table would need a migration each time.
2. **Boolean-tree query compiler** (`screener/query.py`, `screener/schema.py`) — `ScreenQuery` gained an optional `where: PredicateGroup` field (AND/OR/NOT), compiled to a single parameterized SQL statement (`EXISTS` subqueries per metric leaf against the snapshot table, direct column comparisons for categorical leaves). The original flat `metric_predicates`/`categorical_predicates` (implicit AND, Python-side evaluation) still work unchanged for backward compatibility — every existing caller is unaffected. See [ADR 0001](../adr/0001-screener-redis-cache-and-boolean-logic.md) for why OR/NOT was in scope at all (it supersedes doc 14's original AND-only boundary, by explicit founder direction).
3. **Dataset-versioned Redis cache** (`apps/backend/cache.py`) — `scrooner_pipeline.screener.cache_key.compute_query_hash` canonicalizes a query (sorting AND/OR children by their own canonical JSON, so `A OR B` and `B OR A` hash identically — the exact failure mode `fast.md` itself named) and bakes in the current `dataset_version`, so a snapshot rebuild mints new cache keys automatically; no TTL-based correctness dependency.

Verified live: the same `ROE > 0.15` screen via `scrooner-screen run` (pipeline CLI, no cache, no pool) went from 13.9s to **5.7s** — the remaining time is almost entirely this dev machine's network RTT to `us-east-1` (several round trips × ~270ms), not query cost. A real `OR`/`NOT` query (`roe > 0.5 OR debt_to_equity < 0.01`, then `roe > 0.15 AND NOT sector = Financials`) was run against live data and hand-checked correct.

## Two real bugs found making the Redis cache actually fast, not just present

Getting a cache HIT down from "present but still slow" to genuinely fast took two more rounds of live measurement — a caching layer that returns instantly in isolation isn't the same claim as a caching layer that makes the endpoint fast, and this project's own discipline is to verify the second claim, not stop at the first.

**Bug 1 — `psycopg3`'s default (non-autocommit) mode pays two extra round trips per pooled connection.** After adding a process-wide `psycopg_pool.ConnectionPool` (`apps/backend/db_pool.py`) to avoid re-paying `psycopg.connect()`'s ~1.7s setup cost on every request, a cache-hit request still took ~567-573ms — isolated profiling showed a trivial `select 1` cost 0.55s query time + 0.28s "release" time, roughly 2× and 1× the measured 270ms round trip respectively. Root cause: with `autocommit=False` (psycopg3's default), every statement implicitly opens a transaction (one extra round trip: `BEGIN`), and returning a connection to the pool triggers a `rollback()` to clean up that open transaction (another round trip). Fixed by configuring the pool with `kwargs={"autocommit": True}` — safe because every use of this pool is either read-only (the Screener never writes) or a single-statement write; the one genuinely multi-statement transactional write in this codebase (`screen_runs.create_run_from_query`'s insert-then-executemany-then-commit) deliberately stays on the pipeline's original one-shot, non-autocommit `get_connection()` instead of this pool.

**Bug 2 — sharing a connection pool between a request's hot path and its own `BackgroundTasks` callback blocks the response, even though the response is logically sent first.** After autocommit fixed the round-trip multiplication, a cache hit still cost ~260-290ms — confirmed via `curl`'s `time_starttransfer` (time to first byte) that the server wasn't sending anything until that duration had elapsed. A minimal isolated FastAPI app confirmed `BackgroundTasks` genuinely does not block the response for a plain `time.sleep(0.3)` background task (TTFB ~1-8ms) — so the mechanism wasn't `BackgroundTasks` in general. A second isolated test showed a background task using its own fresh, non-pooled `psycopg.connect()` also didn't block (TTFB ~1.5ms) — only using the *same shared pool* (`db_pool.get_pooled_connection()`) from both the main handler and the background task reproduced the ~260-290ms delay. Root cause not fully traced to a specific line in `psycopg_pool`'s internals (plausibly a lock/health-check the pool performs when a connection is checked out shortly after another checkout on a different thread), but the fix is unambiguous and verified: `_log_usage()` now uses its own one-off connection (`scrooner_pipeline.db.connection.get_connection()`), never the shared pool — its own setup cost is irrelevant since it runs after the response is already on the wire.

After both fixes: a cache-hit `/v1/screen` request measured **~4-8ms** server-side (`duration_ms` from `apps/backend`'s own request-timing middleware), confirmed reproducible across 5+ consecutive requests, with `app.usage_event` rows still landing correctly (28 rows confirmed inserted during testing) — logging moved off the critical path, not dropped.

## What's still open

- **Cold (cache-miss) queries remain in the 1.5-3s range from this dev machine** — dominated by ~4 sequential Postgres round trips (metric catalog, excluded-inactive lookup, candidate companies, snapshot values) × ~270ms network RTT to `us-east-1`. This is architecturally the same class of cost the cache-hit fixes above already closed once (round-trip multiplication), and the same fix family (batch queries, cache the metric catalog/candidate-company list the same way `dataset_version` is now cached) would likely help — not done this pass. The single biggest remaining lever, named but explicitly out of scope here, is `fast.md`'s own item 6: same-region deployment. In production, `apps/backend` would run near its database, not on a developer's laptop on another continent, and most of this ~1.5-3s would collapse on its own.
- **No cron rebuilds `analytics.company_screening_snapshot` yet.** It must be rebuilt (`scrooner-screen build-snapshot`) after every Mapper run or screen results silently lag reality — this is a second job for whoever eventually closes root `CLAUDE.md`'s existing "no scheduled reprocessing chain" gap, not a new gap of its own.
- **`redis`/`psycopg-pool` are new `apps/backend` dependencies; local dev needs a real Redis** (`brew install redis && brew services start redis`, or equivalent) to run the backend at all — this is now a hard requirement, not optional, by explicit founder direction (see ADR 0001).
