# Ownership full-population scale-out + zero-new-fetch metrics — 2026-08-29

A single day's work spanning three fronts: scaling Form 4 insider transactions from the golden-10 to the full ~5,257-company population, upgrading Institutional (Form 13F) and Mutual Fund (Form N-PORT) ownership from a single filing window to a real 2-period comparison per a newly-locked product spec (`doc/scoping/insider_info.md`), and landing 7 more zero-new-SEC-fetch metrics/fields. Full evidence and numbers are in root `CLAUDE.md`'s Ownership & Insider Activity paragraph and `doc/status/PROGRESS.md`/`DATA_COVERAGE.md`; this entry focuses on the three most generalizable lessons, not a restatement of every number.

## Lesson 1: a timeout firing correctly doesn't mean the process actually stops — check what's keeping the interpreter alive, not just whether your own logic ran

Scaling Form 4 to the full population meant running against companies with far heavier filing histories than the golden-10 ever exercised — one company alone had 43 amendments' worth of decades-old Form 4 filings and stalled a whole processing chunk for 22+ hours, despite every individual HTTP call already being bounded (`sec_client.py`: 5 attempts × up to 30s + backoff, a few minutes worst case at most). Rather than chase the exact stuck line, the fix was to bound the *damage*: a hard per-company wall-clock timeout (`PER_COMPANY_TIMEOUT_SECONDS`), each company on its own DB connection so an abandoned thread never touches the connection every other company shares.

The first implementation used `concurrent.futures.ThreadPoolExecutor`. The timeout logic fired exactly on schedule — `"company_timed_out"` logged right when expected — but the CLI *process* still didn't exit for another 10+ minutes afterward, for a solo chunk where that timed-out company was the only work left. Cause: `ThreadPoolExecutor`'s worker threads are non-daemon by default, and Python's interpreter refuses to exit while any non-daemon thread is still alive — so an abandoned, still-blocked worker silently kept the whole process (and the orchestrator's `subprocess.run()` waiting on it) alive well past the point the timeout logic had already "handled" the failure. Fixed by dropping to a raw `threading.Thread(daemon=True)` instead — a daemon thread lets the interpreter exit immediately once the timeout fires, abandoned thread or not.

That fix alone still wasn't enough at the orchestrator level. The real batch orchestrator invokes each worker chunk via `uv run <cmd>` as a subprocess — and `uv run` spawns the actual Python worker as a *child* of the `uv` process, in its own process group. A plain `subprocess.run(..., timeout=N)` (or even `process.kill()`) only signals the immediate child (`uv` itself), not the grandchild doing the real work — so `uv` could die while the orphaned worker kept running underneath it. The fix needed `os.killpg` against the process group, with the subprocess launched via `start_new_session=True` so it actually has its own group to kill.

**Generalizable pattern**: a timeout mechanism can be individually correct at every layer you can see — the application logic, the thread, even the immediate subprocess — and still fail to actually stop work, because something one level up or down (the interpreter's own exit behavior for non-daemon threads; a process-launcher tool spawning its own child process group) holds the real handle. When a timeout "fires but doesn't stop anything," check what's actually alive at every layer between your code and the OS process table, not just whether your own timeout logic executed.

## Lesson 2: verify the actual mechanism before trusting the plan — twice in one day, a documented field/source assumption turned out to be wrong when checked against the real live data

Two unrelated pieces of work hit the identical shape of mistake today, independently:

- **EIN/business address/phone** were planned as `dei` XBRL tags, expected to already sit in `core.fact` the same way `dei:EntityCommonStockSharesOutstanding` does. Checking live before writing `company_master/contact_details.py` found this assumption was wrong: SEC's Company Facts API only aggregates facts carrying a *quantitative unit* — EIN and address fields are unitless text, so they were never captured in `core.fact` at all, for any company, ever. The real zero-new-fetch source turned out to be a completely different already-fetched payload, `raw.sec_submissions`'s own base JSON, which carries these fields directly.
- **N-PORT's `report_period`** was originally sourced from a SUBMISSION.tsv field that looked like the obvious candidate by name, but turned out to be the fund's fiscal-year-end date, not the actual holdings-snapshot date the product needs. Caught only by reading SEC's own bundled readme for the *specific downloaded dataset* directly, not by trusting the field name's apparent meaning.

Both mistakes were caught the same way: by checking the real, live source directly before writing the code that depended on the assumption, not by trusting what a plan document (or a field name) implied. This project has hit this exact shape of bug before — the Form 13F `VALUE`-field-convention incident (`doc/learnings/form-13f-cusip-crosswalk.md`) is the same lesson from a different day. **Generalizable pattern**: when a plan names a specific field/tag/API as the source for a new data point, that's a hypothesis, not a confirmed fact, until checked against a real live payload — and the dataset's own bundled documentation (a readme shipped with the actual data) is more trustworthy than an assumption based on a field's name or a separately-maintained spec.

## Lesson 3: a proposed speedup needs to survive contact with the real data's actual structure, not just sound plausible

While scaling beneficial-ownership (Schedule 13D/13G) to the full population, a natural-sounding optimization was floated: narrow the SEC filing-date range being fetched per company, since most companies' relevant beneficial-ownership filings cluster recently. Checked against the real distribution before adopting it — the idea doesn't hold structurally, the same way N-PORT's "just take the two most recent report_period values" idea didn't survive contact with real data either. N-PORT filers, checked live, turned out to cluster into three near-fully-disjoint ~90-day-apart quarterly cohorts by calendar month (a Jan/Apr/Jul/Oct cohort, a Feb/May/Aug/Nov cohort, a Mar/Jun/Sep/Dec cohort) rather than share one monthly cycle — so naively pairing "the most recent report_period" with "the next most recent distinct value" almost always paired two disjoint fund cohorts, manufacturing a false ~100%-turnover artifact (an entire ~530-fund portfolio looking "new" and an entire ~1,021-fund portfolio looking "exited" between two adjacent calendar months, with zero real overlap in either direction) rather than any genuine ownership change. This was caught by hand-checking a computed AAPL summary that looked implausible, then confirming the cohort structure directly against the real bulk data — not by reasoning about it in the abstract.

**Generalizable pattern**: an optimization or simplifying assumption that sounds reasonable in the abstract ("recent filings are what matters," "the two latest date values are the two most recent periods") needs to be checked against the real data's actual clustering/structure before being adopted — a plausible-sounding shortcut and a structurally-sound one can look identical until you check the real distribution, and the failure mode (a manufactured, wrong-looking result rather than an obvious crash) is exactly the kind of error a manual sanity check catches and an untested assumption doesn't.

## Also worth naming: a known, deferred issue

`ownership/insider_summary.py` has a per-company query-in-a-loop pattern — the same N+1 shape `normalizer/restatements.py` already hit once (see `pipeline/CLAUDE.md`'s existing entry on that). This is flagged, not fixed, in this pass: unlike `restatements.py`'s case, nothing here depends on the module's speed (pure local computation over already-stored rows, no SEC rate limit to respect), so it was left as a named, deferred issue rather than an urgent fix. Worth remembering: not every instance of a known bad pattern is equally urgent — the same shape of inefficiency can be a correctness-and-speed emergency in one context and a low-priority cleanup in another, depending on what actually depends on it.
