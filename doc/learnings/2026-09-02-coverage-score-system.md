# 2026-09-02 — Coverage-score tracking system built

## What prompted this

After a session of one-off coverage investigations (gross_margin, total_debt, the delisted-status bug), asked directly to stop investigating gaps one at a time and instead build a real, trackable score — something to watch increase day over day, not just a point-in-time doc snapshot.

## What was built

`analytics.coverage_snapshot` (migration `0034`), one row per `(snapshot_date, item_type, item_name)`, written by a new `scrooner-map snapshot-coverage` CLI command (`mapper/coverage_snapshot.py`). Two aggregate rows per day: `avg_metric_coverage_score` (mean coverage % across all 64 active `metric_definition` rows — the product-facing number) and `avg_concept_coverage_score` (same mean over the 44 canonical concepts — a diagnostic leading indicator, not the target itself, since concept coverage doesn't move metric coverage 1:1). Both deliberately unweighted, same "hard denominator, one documented formula" discipline `doc/status/SCORECARD.md` already established for a differently-scoped score. Idempotent (delete-then-reinsert per snapshot_date), 4 unit tests covering the pure computation against a fake connection.

## A real, immediately-actionable finding surfaced by building this

Running the very first snapshot exposed something no prior per-metric investigation this session had surfaced: **`market_cap`, `trailing_pe`, and `dividend_yield` sat at exactly 0.00% company coverage** — not low, zero. `price_to_sales`/`price_to_book`/`fcf_yield` at 0.19% (a handful of golden-10 residue rows). These are 6 of doc 02's original 18 locked V1 metrics, unblocked back on 2026-08-17 when the Alpaca market-price vendor decision resolved.

Root cause, checked live before acting: `mapper/price_metrics.py`'s CLI command (`calculate-price-metrics`) defaults to the golden-set CIK list when no `--ciks` is passed — and it had, in fact, never been invoked with a full-population CIK list at any point in this project's history. Meanwhile the underlying real price data it needs, `core.market_price_alpaca`, already covers 3,346 companies (from earlier, separate work) — sitting unused by this one stage. This wasn't a data-availability gap or a code bug; it was a stage that had simply never been run at scale, invisible until a systematic snapshot forced every metric to be checked in the same pass rather than one at a time.

Launched a full-population `calculate-price-metrics` run the same session (6 workers, fresh batch file reflecting the current 5,216-company active population after today's delisted-status fix). Completed with 0 errors across 348 batches: `market_cap` 0%→60.0%, `price_to_book` 58.7%, `trailing_pe` 48.7%, `price_to_sales` 42.0%, `fcf_yield` 36.1%, `dividend_yield` 16.1%.

## A second, more consequential bug: the tracker's own first computation was wrong

The very first `snapshot-coverage` run reported `avg_metric_coverage_score` = 79.41%. That number was **wrong** — caught within the same session, before it was used for anything, by noticing that `market_cap`/`trailing_pe`/`dividend_yield` showed 100% company coverage in the raw per-metric breakdown despite the price-metrics gap just described still being unfixed at that exact moment. `analytics.metric_value` stores an explicit row with `is_null_reason` set even when a metric can't be computed for a company — the same traceability discipline as `excluded_missing_data` elsewhere in this project, deliberate and correct at the schema level. `_load_metric_coverage()`'s first version did `count(distinct company_id)` with no filter on `value`, so every metric with any null-reason rows showed inflated — often 100% — coverage, regardless of how many rows were real.

Fixed with `count(distinct company_id) filter (where value is not null)`. The corrected baseline: **54.39%**, not 79.41% — a 25-point difference caused entirely by the query, not the data. Re-running the snapshot after the fix surfaced a second real, previously-invisible gap: `ev_ebitda`/`ev_sales`/`peg_ratio`/`buyback_yield`/`total_shareholder_yield` (5 `expanded_metrics.py` outputs that all take `market_cap` as an input) were a genuine 0% — `calculate-expanded-metrics` had last run while `market_cap` was still universally null, so every one of these 5 metrics' `metric_value` rows were real, correctly-computed nulls, not missing rows. A full-population `calculate-expanded-metrics` rerun was launched immediately to pick up the newly-real `market_cap` values.

`canonical_fact` (the concept-level table, one layer upstream of `metric_value`) does not have this problem — it never stores an explicit-null row, only real values — so this specific bug is a `metric_value`-only concern, not a general "always filter nulls" rule to blindly apply everywhere.

## Lesson

**A per-metric investigation only finds what you think to look for; a systematic sweep across every metric in one pass finds what you didn't.** Every prior coverage fix this session (gross_margin, total_debt) started from a specific complaint or a specific low number already noticed. Building the aggregate score required computing coverage for literally every active metric in one query, and two of the worst gaps in the whole system — 6 real, locked, previously-unblocked metrics sitting at 0% — had never come up in conversation because nobody had looked at them specifically. The generalizable takeaway: a tracked, comprehensive score isn't just a vanity metric to watch trend upward — the act of computing it comprehensively is itself a real discovery mechanism, independent of whatever it's later used for.

**A close second lesson, from the tracker's own bug: a brand-new measurement tool is not exempt from the same verification discipline it's meant to enforce on everything else.** The 79.41%→54.39% correction happened only because the raw per-metric breakdown was actually read and cross-checked against a fact already known in the same conversation (the price-metrics gap wasn't fixed yet) — if the aggregate score alone had been trusted and reported without inspecting the components behind it, a 25-point-inflated number would have shipped as the "real" baseline, and every future day's score would have been compared against a wrong anchor indefinitely. Building a scorekeeping system is itself new code, with its own bugs, and deserves the identical spot-check treatment as anything else that produces a number this project puts in a doc.
