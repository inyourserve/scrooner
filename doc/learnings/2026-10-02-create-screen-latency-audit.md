# Create-screen latency audit (2026-10-02)

Prompted directly: "our flagship feature is create screen, please make it faster... one touch it should run." Audited the whole path, from the `/app/screens/new` landing page to a brand-new (never-before-run) natural-language screen completing, measured live against this dev machine's real backend/DB/Redis, not guessed.

## Already fine, checked and left alone

- **The "one touch" UX already exists.** `NaturalQueryPanel.tsx`'s `runQuery()` generates a client-side `requestedRunId`, registers the in-flight request (`registerPendingRun`), and calls `router.push` to the results route *immediately* — the backend call runs in parallel with the client-side navigation, not before it. `/app/screens/new` itself does zero data fetching (pure server component, no DB/API calls) and `/app/screens/new/raw` has no SSR fetch either. One click/Enter already does "navigate + run" as one action.
- NL parsing (`ai_query/rules.py::interpret()`) is a pure in-process regex parser: measured live at **0.1-1.4ms**. Not a contributor.
- `screener/query.py`'s DB read is one round trip (`_select_snapshot_rows`), not N+1. `/v1/metrics` has a 1hr Next.js fetch cache plus a 5-minute HTTP cache-control header. `apps/app`'s own auth check (`getClaims()`) verifies the JWT locally, no network call.

## Real findings

1. **Redis/Postgres round trips are the dominant cost for a true cache-miss, and each round trip from this dev machine to Supabase (`us-east-1`) costs ~250-300ms, sometimes more** — confirmed by direct, isolated timing (not estimated): a fresh `psycopg.connect()` took 1.65s, a single `load_screenable_metric_catalog()` call took 280ms, and `run_query()` for a 2-predicate AND query took 2.3s on its own (excluding connect/catalog). This matches the already-documented 2026-09-10/09-26 findings in this same file and in `apps/backend/cache.py`'s own comments — nothing new in kind, but now re-confirmed and acted on.

2. **No backend hosting config exists at all.** `find apps/backend` for a Procfile/fly.toml/render.yaml/Dockerfile/vercel.json returns nothing. The "same-region deployment" gap named 2026-09-10 (`doc/learnings/2026-09-10-screener-performance.md`) and never acted on is still completely open — not merely unoptimized, genuinely unconfigured. **This is the single biggest lever and requires a hosting decision only the founder can make** (where apps/backend actually runs, pinned to the same region as Supabase/Redis). Flagged, not something fixable from inside this session.

3. **`dataset_version_cache.py`'s TTL was 30s despite the value only ever changing on a manual, at-most-daily snapshot rebuild** — the module's own docstring already said this TTL was a pure memory-hygiene choice with no correctness tradeoff. Raised to 300s (matching the catalog's own TTL). **Fixed.**

4. **`create_run_from_query` (the literal "create a screen" endpoint, `routers/screen_runs.py`) paid up to 5 sequential Redis round trips** — 2 reads (`get_cached_run_id`, `get_cached_result`) then up to 3 writes (`set_cached_result`, `set_cached_run_id`, `set_cached_run_page`), none pipelined. Each one is free if Redis is co-located with the backend process (true in this dev environment — same machine) but a real, compounding cost if it isn't in production (unverified, since #2 means there's no confirmed topology at all). **Fixed**: `cache.py` gained `get_cached_run_lookup()` (1 pipelined round trip for both reads) and `set_cached_run_write()` (1 pipelined round trip for all three writes, skipping the result write when it was already cached) — behavior-identical, same fail-open-on-RedisError contract as every other function in that module. 4 new tests in `tests/test_cache.py`; existing tests in `test_screen_run_cache.py`/`test_screen_result_dedup.py` updated to monkeypatch the new combined functions. Full backend suite 53→57 passing.

5. **Found, flagged, and fixed in a same-day follow-up**: the flat-AND query path (`query.where is None`, i.e. the common "metric above X and metric below Y" phrasing) did **not** push `metric_predicates` into the SQL `WHERE` clause at all — fetched the entire population and filtered in Python, while the boolean-tree (OR/NOT) path already pushed down and was measurably faster despite being logically more complex. Fixed with a provably safe SQL pre-filter, verified byte-identical against 10 real live queries (2.4s→0.34s on the flagged case). Full writeup: `doc/learnings/2026-10-02-screener-flat-and-prefilter.md`.

## Round 2 (same day, direct follow-up: "relook with a fresh lens, redesign if needed")

6. **Investigated and deliberately rejected: deferring the `app.screen_result`/`app.user_screen_run` INSERT to a background task**, the same fire-and-forget pattern `_log_usage` already uses. Would have cut the create-screen critical path from [SQL select → DB insert → Redis write] to [SQL select → Redis write] — on a cache-hit (an already-popular query), that's [Redis read → Redis write] with **zero** synchronous DB work at all. Blocked by a real correctness constraint found before shipping it: `app.saved_screen.last_run_id` has a foreign-key constraint on `app.user_screen_run.id` (migration 0064), and both `refresh_screen` and the "Save screen" flow reference a run's id *synchronously, in the same or an immediately-following request* — a deferred insert creates a real race where that FK reference lands before the row exists. Not a theoretical risk: it's exactly the "create, then immediately save" sequence this whole effort is optimizing for. Correctly left synchronous rather than shipping something that intermittently breaks saving.
7. **Fixed, safe, shipped**: `apps/backend`'s FastAPI `lifespan` now warms `dataset_version_cache`'s two in-process caches (`get_cached_dataset_version`/`get_cached_metric_catalog`) once at startup, using a connection the pool already opens — measured live at 589.5ms. Previously, the *first* real create-screen request after every deploy/restart paid both of those round trips on top of its own work; now none does. Best-effort (wrapped in try/except so a cold DB at startup never blocks the app from serving). `db_pool.py`'s main pool `min_size` raised 1→2 so a second concurrent request doesn't have to pay a fresh ~1.7s connect on its own — modest, real, and nowhere near the shared ~15-connection pooler ceiling (2 + `_usage_pool`'s 2 = 4).
8. **Found, sized, proposed but NOT shipped this pass**: for a broad/under-filtered query, `excluded_missing_data` can run into the thousands of entries (1,225 seen for one real 2-predicate query), and the full, company-name-resolved list is eagerly computed into *every* response and Redis-cached page — even though `ScreenerClient.tsx` renders it behind a collapsed `<details>` panel most users never expand. Rough sizing: ~1,225 entries × ~120 bytes ≈ 147KB, which on a slow link is itself comparable to one round trip's worth of latency. The fix (compute it as today for correctness/traceability — doc 02's explainability gate explicitly requires this list exist and stay untruncated — but serve it from a new on-demand endpoint, fetched only when the panel is expanded, instead of inline in the main response) is real and touches both `apps/backend` and `ScreenerClient.tsx`. Not shipped this pass: `apps/app`'s frontend had ~100 files of unrelated, actively-changing uncommitted work at the time, and editing `ScreenerClient.tsx` again risked colliding with it. Worth doing as its own small follow-up once that settles.

## Verification

- `uv run python` micro-benchmarks against the live dev DB/Redis (isolated connect/catalog/query timings above), including a direct call to the new `_warm_screener_caches()` against the real database.
- `apps/backend`'s full test suite: 53 passing before round 1, 57 after round 1 and still 57 after round 2 (no new tests needed for the lifespan warm-up or pool size change — both are infra-shape, not logic, and already covered by the existing suite running cleanly end to end).
- No frontend changes made in either round — the one-touch UX was already correct on inspection; changing it further was judged unnecessary (round 1) or too risky given concurrent unrelated frontend WIP (round 2, item 8).
