# Supabase usage audit (2026-10-09)

Prompted by a pasted Supabase usage report (46 GB database, 69.3 GB storage, 27 GB of that DB in indexes, 18.2M dead rows). Investigated live rather than trusting the report's numbers at face value.

## Findings, verified against the live database

1. **69.3 GB of Storage is the real cost center, not the database.** `storage.objects` in the `raw` bucket breaks down as `sec/companyfacts` (55 GB, 30,823 files) + `sec/submissions` (10 GB, 60,685 files) — the Collector's cached raw SEC payloads. This data is free, public, and re-fetchable from SEC EDGAR at any time; it's kept only as insurance against re-fetching cost/rate limits (doc 04's "lossless, immutable" design). It currently lives in the *same* paid, replicated, backed-up tier as production data. **Real, unexplored lever: move this to cheap cold object storage (S3/R2) instead of Supabase Storage** — not yet sized or acted on.
2. **The 27 GB of indexes is mostly legitimate, not bloat.** Checked `pg_stat_user_indexes` directly: the top 3 indexes on `core.fact` alone (10 GB combined) have 23-35 million real scans each. Found exactly one safe, small win — `idx_institutional_ownership_company` (207 MB, 0 scans ever, superseded by `idx_institutional_ownership_dedup` which was added later for the real query shape) — not yet dropped. Every other zero-scan index found is backing a real FK or uniqueness constraint (e.g. `fact_raw_object_id_fkey`/`fact_supersedes_fact_id_fkey` on `core.fact`) and isn't free to remove even though rarely exercised.
3. **18.2M dead rows is not an autovacuum failure.** `core.fact`, `analytics.metric_value`, and `analytics.canonical_fact` all show autovacuum runs within the last 1-2 days. The dead rows are the direct, cumulative cost of this project's own standard idempotency pattern (delete-then-reinsert on every reprocess, used almost everywhere per this file's own history) — an upsert-based pattern would avoid most of this, worth the default for new write paths rather than a retrofit.
4. **No live stuck transaction** — the single "idle in transaction" the pasted report flagged was, when checked live, a cluster of several-seconds-old transactions from an actively-running peer-session batch job (short ages, not stuck). Don't assume a flagged idle-in-transaction is still live without checking `pg_stat_activity` directly first.
5. **Real strategic observation: the database grew ~30 GB → 46 GB since 2026-08-26 while active users (last 30 days) stayed at 3.** The cost is scaling with EDGAR data breadth/internal data-quality tooling (new concepts, sanity/coverage/investigation tables), not with product usage — in tension with doc 05's own "evidence before expansion" principle on the infra-cost axis specifically, even though each individual addition was itself well-verified. Not a crisis, but worth naming before it compounds further pre-revenue.

## Separately evaluated the same day, not implemented (no code changed)

- **"Should `apps/backend` move from FastAPI to Django?"** — evaluated and recommended against. The real cost isn't "Django is slow," it's that complex queries (Screener, company page) would stay raw SQL either way, Django's ORM is still fundamentally sync under the hood, and a long list of already-measured, FastAPI-specific performance fixes in this codebase (autocommit, separate background-task pool, auth-token Redis cache, removed `conn.transaction()` wrappers) would need rediscovering blind in Django's own idioms for zero functional gain. Django's actual locked role in this stack is the (not-yet-built) internal Admin tool (Part 11), a genuinely different job than the thin API.
- **"Should data move from the `raw`/`core`/`analytics`/`app` schema split into business-domain schemas (`scrooner_pricer`/`scrooner_financials`/`scrooner_holding`)?"** — evaluated and recommended against. The current split isn't just naming — it's the enforced pipeline-stage boundary (Collector→raw only, Normalizer→core only, Mapper→analytics only) that this project's own history shows is the main thing that's kept a complex multi-stage pipeline from corrupting itself. A domain-based split would either hide that boundary one level down inside each new schema or lose it, while *increasing* cross-schema joins for the metric catalog and company identity tables that are inherently cross-domain already. If the real motivation is navigability ("where does price data live"), the better fix is named views or the existing `analytics.data_point_registry`, not relocating data or rewriting write boundaries.
