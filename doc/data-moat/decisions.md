# Data Moat — Locked Decisions (curated pull-out)

**Not the authoritative register** — [doc 02](../foundational/02_Scrooner_Decision_Register.md) is, for the whole product. This is a short, scannable subset: only the decisions specific to data correctness/verification, pulled out so a data-moat-focused session doesn't have to read doc 02's full, product-wide register to find them. If this and doc 02 ever disagree, doc 02 wins — update both in the same pass if a decision here changes.

## Locked

- **SEC EDGAR is the only source of truth for stored values.** yfinance and SEC's own Frames API exist to *detect and match* disagreements — never to supply a value that gets written into `core`/`analytics`. A fix always traces back to a real `core.fact` row. Made explicit and load-bearing 2026-09-08 (`sanity/tag_investigator.py`'s module docstring); a sharper restatement of doc 02's original "AI/external sources are assistive only" principle applied to data verification.
- **A fix is a per-company tag preference, not a per-period value snapshot.** Once a specific SEC tag is confirmed to reconcile for a company, that preference applies to every period the company has data under it — not just the one flagged period — since the underlying issue (a tag priority that's untrustworthy for this company) is usually not period-specific. Supersedes the original per-period `canonical_fact_sanity_override` design (migration 0049) with `company_tag_preference` (migration 0051), same day.
- **Never write a new tag into `analytics.concept_mapping` from a single company's evidence.** `resolve()` uses every non-`rejected` confidence tier, so even a `provisional` row changes output for *every* company reporting that tag, not just the one a finding was raised for. A real, multi-company match (the `CostsAndExpenses`/`operating_expenses` fix, verified against 682 companies + an independent coexistence test) is what justifies a global mapping change — a single flagged company is a lead, not evidence.
- **A brand-new checker's own first alarming finding gets the same scrutiny as any other finding — trace it to the real underlying rows before reporting it as a bug.** The tool itself can have the bug. Real instance: the SEC Frames checker's first run found what looked like 280 companies with a serious `is_authoritative` integrity violation; traced to the actual `core.fact`/`core.period` rows, it turned out to be the checker's own period-matching logic, not the pipeline. See `learnings/2026-09-08-sec-frames-self-consistency-check.md`.
- **yfinance is a real, explicit ToS-risk exception** (`doc/planning/y-finance.md`, doc 02), not a casual dependency. Every yfinance-calling module shares one aggregate rate limit (`common/rate_limiter.py`'s shared lock file) — running more workers doesn't increase real throughput, only lowering the shared pace interval does, and that's a deliberate risk/speed tradeoff requiring explicit sign-off, not a default to reach for.

## Open, not yet decided

- **When every candidate fact for a (company, concept, period) slot is non-authoritative** (a genuine, small-magnitude cross-filing disagreement — Stage 2e's dedupe.py correctly refusing to guess), should the fallback prefer the *most recent* filing's value, matching SEC's own Frames API convention? This would resolve the majority (79 of 88, 90%) of the SEC Frames checker's remaining real mismatches and make our data consistent with SEC's own canonical resolution — but it touches `resolve()`-adjacent tie-break behavior, which this project has repeatedly treated as a deliberate human call. Surfaced 2026-09-08, not applied.
- **Should the Frames checker's `mismatch` findings get their own auto-fix path** (like the Data Sanity Layer's Tag Investigator), given a Frames mismatch is stronger evidence of a real bug than a yfinance mismatch? Not built yet — the first real run found the residual mismatches are dominated by the already-covered restatement-timing case above, so the marginal value of a dedicated fix path hasn't been sized yet.
