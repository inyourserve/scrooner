# 2026-09-08 — Unified Data Incident view + evaluating (and scoping down) the "internal auto-fixer" vision

## What was asked

The user authored and pasted a full architectural vision for a "self-healing data + support system" (`doc/data-moat/scope/internal-auto-fixer.md`) — a 6-agent Detect→Investigate→Ticket→Assess Impact→Fix→Reprocess→Validate→Close→Learn loop (Watcher/Triage/Investigator/Impact Agent/Solver/Verifier), structured JSON incidents, a dashboard, impact-graph analysis, tiered autonomy by risk (low=auto-fix-and-close, medium=propose-then-approve, critical=block-and-alert), explicitly cautioning NOT to productize or market it as "AI fixes everything" yet. The request: "for tier 4, point 8, i scoped this, please evaluate and build this."

## The evaluation

Endorsed building now, deterministically, with no new agents: a unified incident schema across the 5 checkers already built this session, a dashboard, an impact-analysis tool, and a verifier that closes the loop. Explicitly rejected building now: 6 separate LLM agent processes (the scope doc's own text already concedes "you don't necessarily need six separate LLM processes"), an autonomous code/mapping-rewriting Solver (this project's `concept_mapping` changes are deliberately human-gated — a single company's evidence is never sufficient to change global resolution behavior, see doc 40/09-08's tag_investigator entries), and customer-support convergence (no customers yet). The tiered-autonomy model the scope doc asks for already exists implicitly: a per-company `company_tag_preference` fix (medium-risk, auto-applies once found) vs. a global `concept_mapping` change (critical-risk, human-reviewed, `rejected`/`approved` discipline) is exactly the low/medium/critical split the doc describes, just not labeled that way.

## What got built

1. **`analytics.data_incident`** (migration `0055`) — a live VIEW, not a materialized table, `UNION ALL`-ing all 5 checker tables (Data Sanity, yfinance Financials, SEC Frames, Time-Series, Freshness) into one shape with a normalized severity vocabulary (`ok`/`minor`/`major`/`critical`/`missing`). A view was chosen specifically to avoid sync lag — it always reflects each checker's current state, no separate write path to keep consistent.
2. **`incidents/dashboard.py`** — `summarize()`/`render_markdown()`, the dashboard the scope doc's own example ("Open incidents 7 / Critical 0 / ...") asked for. Real first run surfaced two genuinely new findings, neither previously known:
   - Commodity ETF/trust structures (United States Oil Fund, Natural Gas Fund, 12 Month Natural Gas Fund, etc.) dominate the "top offending companies" list — not because anything is broken, but because these are pass-through trusts with no revenue/opex/balance-sheet structure a fundamentals checker expects. Same shape as the already-documented BDC/bank carve-outs, just not yet named for this entity type. Not acted on this pass — flagged for whoever next tunes the checkers' scope.
   - `data_sanity`'s worst-metrics list is dominated by `roa`/`net_margin`/`ebitda` — consistent with the degeneracy-guard-adjacent microcap issue already documented, not a new bug, just newly visible in aggregate.
3. **`incidents/impact.py`** — real graph traversal, not invented data: `concept_to_metrics()` reads `analytics.metric_definition_input` (the exact edge `calculate.py` itself reads), `metric_to_saved_screens()` runs a real `jsonb`-text query against `app.saved_screen.query`. Found and fixed a real bug immediately on first live run: `metric_definition`'s name column is `metric_name`, not `name` — caught by actually running the command against Flowserve/revenue/total_debt, not by code review alone. `total_debt`'s impact report correctly shows **0** metrics fed — accurate, since `debt_to_equity`/`roic`/`net_debt_ebitda` actually read `total_debt_resolved` (the `concept_fallback.py` merge concept), not `total_debt` directly. A report showing 0 for the "obviously important" concept and 14 for `revenue` is the tool working correctly, not a bug — checked against known dependency structure before trusting it.
4. **`incidents/verifier.py`** — `capture_state()`/`diff_state()` (pure, unit-tested — 7 tests) + `verify_company()`, which reruns the two checks safe to rerun on demand (Tag Investigator resolution, Time-Series self-consistency) and reports resolved/regressed/still-open.

## The real bug found building the verifier

The first live run of `verify(company_id=353)` (Flowserve) ran for 90+ seconds with the DB connection sitting idle-in-transaction — not stuck, just doing a lot of Python-side work. Root cause: `investigate_open_findings()` had no company filter, so verifying ONE company's fix reprocessed all ~20,000 currently-open `data_sanity_check` rows across the WHOLE population. Killed by exact PID (per this session's own standing rule) rather than left to finish uselessly. Fixed at the source, not worked around in the caller: `investigate_open_findings()` and `timeseries_check.run_concept()`/`run_all()` both gained an optional `company_id` parameter. For `run_concept()`, the **delete** had to be scoped identically to the **load** — scoping only the load while leaving `delete ... where canonical_concept_id = %s` unscoped would have silently wiped every other company's rows for that concept on a single-company rerun, the exact "shared-table write needs scoping on every dimension" trap this project has hit and documented multiple times already (Mapper Day 6's `roic`/`roe` `period_label` collision; `expanded_metrics.py`'s 2026-09-03 delete-scope bug). Re-run after the fix: 353's full verify completed in under 2 minutes, correctly reporting `resolved=0, regressed=0, still_open=7` — an honest result, since the remaining open findings (roa, ebitda_margin, debt_to_equity ratio mismatches) are yfinance-ratio-level disagreements the Tag Investigator's `FIXABLE_CONCEPTS` (currently just `revenue`) has no mechanism to address, not a false "all clear."

## Generalizable lesson

A verifier/dashboard tool built on top of several existing checkers inherits whatever scoping (or lack of it) those checkers' own entry points have. Before wiring a "verify just this one thing" tool to a function originally built for "process everything," check whether that function has a narrowing parameter at all — if it doesn't, add one at the source (with the delete-scope discipline this project already has muscle memory for), rather than accepting a slow, wasteful call as the price of reuse.
