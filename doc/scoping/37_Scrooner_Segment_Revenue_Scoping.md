Prompted directly, following the Peer Comparison fix ("why not use segment/dimensional data instead of one SIC code per company") — the user asked to scope exactly this: revenue-by-business-segment for the top 100 companies. **Owner:** Founder/Product · **Review:** before this is approved for a build.

## The one thing to settle before anything else: "top 100 by market cap" isn't computable today

Market Cap is still 0 companies population-wide (the price-vendor blocker, unchanged all session). **`dei:EntityPublicFloat` — the obvious substitute — was checked live and found to have a real, serious data-quality problem of its own**: the top values by raw magnitude include genuine mega-caps (NVIDIA $4.0T, Microsoft $3.6T, Apple $3.25T) mixed with clearly-impossible ones (eBay at $31 quintillion; Universal Display Corp, a ~$700M-revenue company, at $6.8 trillion) — a real unit-scaling bug affecting an unknown fraction of rows, not just a few outliers filterable by a simple bound. Untangling that is a separate investigation, not something to solve as a side effect of this scope.

**Recommendation: use Revenue (most recent FY) as the universe-selection proxy instead.** It's the most reliable, already-fully-computed metric in the pipeline (4,343 companies with a resolvable FY value, checked live), and the resulting top-100 list is unsurprising and correct on inspection — Amazon, Walmart, UnitedHealth, Apple, McKesson, Alphabet, CVS, Microsoft, Costco, Berkshire Hathaway, NVIDIA, Meta, etc. (full list generated live, available on request). This is a proxy, not a perfect Market Cap substitute — a few companies here are large by revenue but not by market value (e.g. low-margin distributors like McKesson/Cencora/Cardinal Health) — but for *scoping which 100 companies to prioritize a new build for*, correctness and immediate availability matter more than perfect market-cap fidelity.

## What "segment" actually means — checked live, not assumed

Pulled Apple's real, current 10-K (filed 2025-10-31, accession `0000320193-25-000079`) directly from SEC and inspected its actual filing structure. Two genuinely different disclosures exist, and conflating them would be a real design mistake:

1. **Formal ASC 280 "reportable segments"** — for Apple, these are **geographic** (Americas, Europe, Greater China, Japan, Rest of Asia Pacific), each with its own Net Sales, Cost of Sales, and Operating Income. This is what "Segment Information" legally means under GAAP for Apple specifically — not product lines.
2. **ASC 606 "disaggregated revenue"** — a separate note, titled "Revenue" in Apple's filing, that breaks Net Sales down by **product/service category**: iPhone $209,586M, Services $109,158M, Mac $33,708M, Wearables/Home/Accessories $35,686M, iPad $28,023M (FY2025, all three years shown). **This is almost certainly what a retail investor actually means by "revenue by business segment"** for a company like Apple — but it is a different XBRL disclosure than the formal "Segment Reporting" note, and the two won't always both exist, or exist in the same shape, for every company.

**Real implication for scope**: this project cannot commit to one universal "segment" concept across companies. Some companies report geographic segments only, some product/business-unit segments only, some both, some (companies with a single reportable segment) report neither in a broken-out form at all. The right design is to capture **whatever disaggregation each company actually discloses, labeled with the company's own terms** — not force every company into one shared taxonomy (the same lesson this project already learned the hard way with Form 13F filer categorization and total_debt's alternate-tag double-counting: forcing a universal shape onto genuinely different real-world structures produces silently wrong data, not a clean abstraction).

## The real technical path — checked live against Apple's actual filing, not theorized

**Confirmed: the standard Company Facts JSON API (what this entire pipeline currently runs on) strips this data entirely** — this was already established in doc 22, reconfirmed here. **Also confirmed live for the first time in this pass: `raw.sec_filing_documents` (the table that would hold individual filing document bodies) has never fetched a single 10-K's raw XBRL instance document for any company in this project** — it only covers 3,775 CIKs, all from the ownership modules' Form 4/13D fetches, not the financial-statement pipeline. **This means the entire financial-statement side of Scrooner has never once fetched an individual filing's raw XBRL — it has only ever used the pre-aggregated bulk Company Facts JSON.** Getting segment data is a genuinely new kind of fetch for this project, not an extension of an existing one.

The good news, found by actually inspecting a real filing rather than assuming raw-XBRL parsing was the only option: **every 10-K filing includes a `FilingSummary.xml` index and a set of `R*.htm` files — SEC's own auto-rendered HTML tables of each XBRL disclosure, already human/semi-machine-readable, no XBRL dimensional parsing required.**

Concretely, for Apple's most recent 10-K:
- `FilingSummary.xml` lists every disclosure with a human title, e.g. `R21.htm` → "Segment Information and Geographic Data", `R38.htm` → "Revenue - Disaggregated Net Sales and Portion of Net Sales That Was Previously Deferred (Details)".
- `R38.htm` itself is a real (if verbosely marked-up) HTML table: row labels ("iPhone", "Mac", "iPad", "Services", "Wearables, Home and Accessories") each with three fiscal years' worth of dollar values, already extracted from the underlying XBRL dimensional facts by SEC's own renderer.

This is dramatically simpler than raw XBRL/dimensional-context parsing (the approach doc 22/23 correctly flagged as "genuinely harder" and left undesigned) — it trades a hard XML dimensional-parsing problem for an HTML-table-scraping problem, which this project has no existing tooling for either, but is a well-understood, bounded kind of work.

## Scope correction: no historical backfill needed — one filing already carries the comparison

Prompted directly ("why do we need to parse all history? we just need to show recent 2 quarter data... over time it will cover") — checked live before accepting it, and it's not just a reasonable simplification, it's how the underlying data is already shaped. Apple's own most recent 10-Q (filed 2026-07-31, `R28.htm`) already contains **four comparison columns in one table**: current quarter (Q3 FY2026, iPhone $54,252M), year-ago same quarter (Q3 FY2025, $44,582M), current 9-month YTD ($196,515M), and year-ago 9-month YTD ($160,561M) — from a single fetch of a single filing. 10-Qs carry the same "Segment Information"/"Revenue - Disaggregated..." disclosures as 10-Ks (confirmed live against Apple's real most recent 10-Q), just for the interim period instead of the full fiscal year.

This directly mirrors the pattern already locked and built elsewhere in this project (`doc/scoping/insider_info.md`'s Institutional/Mutual Fund MVP history policy: "two consecutive periods... no five-year history... preserve newly collected data so history develops naturally") — apply the same rule here:

- **Fetch only each company's single most-recent 10-Q (or 10-K, whichever is more recent)** — not a multi-year backfill across every historical filing.
- **The comparison is already embedded in that one table** — no need to separately fetch and align two different filings' worth of data.
- **History accumulates naturally**: rerunning this job periodically (e.g. quarterly, alongside normal filing-freshness checks) and keeping every period's row rather than overwriting it means a real multi-quarter trend builds up over time on its own, the same way this project's other "no backfill, let it accumulate" decisions already work.

This meaningfully shrinks the fetch volume (100 companies x 1 filing x 1-2 R.htm files, not 100 x N years x multiple filings) without changing anything about the harder parts below (title-matching heuristic, per-company segment-shape variance, new parser/storage) — the size of the *parsing* problem is unchanged; the size of the *fetch* problem drops by roughly the number of historical years this would otherwise have tried to cover.

## What a real build would actually require (not yet built, this is the estimate)

1. **A new fetch, per target company — one filing only, not a backfill** (see correction above): the company's single most-recent 10-Q/10-K's `FilingSummary.xml` (to find the right R.htm(s) by title) plus the 1-2 R.htm files themselves. For 100 companies this is ~300-400 new HTTP requests total, one time — trivial against SEC's rate limit, especially now that the cross-process rate-limiter bug (fixed this session) no longer risks an aggregate overshoot. Rerun periodically (e.g. quarterly) to pick up each new filing as it's published, keeping prior rows rather than overwriting them, so real multi-quarter history accumulates on its own.
2. **A title-matching heuristic, not a guaranteed match**: searching `FilingSummary.xml` for report titles containing "Segment" and/or "Disaggregat" (both real, standardized XBRL element names — `SegmentReportingDisclosureTextBlock`, `DisaggregationOfRevenueTableTextBlock` — so the titles are reasonably consistent) will work for most companies, but not all: some filers title these notes differently, some have both a segment note and a disaggregation note that need to be captured as two distinct facts (as confirmed for Apple), and some (true single-segment companies) will correctly have neither. This needs a real, hand-verified pass over a sample before trusting it blind across 100 companies — the same "verify against the full target set before trusting a proxy" discipline this project has already had to relearn multiple times (the ticker-change-date proxy, the N-PORT cohort-pairing assumption, the Form 4 issuer-ambiguity assumption).
3. **A new HTML-table parser**, genuinely new code — nothing in the current pipeline parses this shape (label rows + multi-period value columns from an auto-rendered financial-statement HTML table). The closest existing precedent is `statements/classify.py`, but that reads already-normalized `canonical_fact` rows, not raw filing HTML — this would be a new capability, not an extension.
4. **A new storage shape**: company-specific segment/category labels stored as-is (e.g., a `core.segment_fact` or `analytics.segment_revenue` table: company_id, period, disclosure_type ['geographic_segment' | 'product_disaggregation'], segment_label (free text, the company's own term), value) — deliberately NOT trying to map "iPhone" or "Americas" onto a shared cross-company taxonomy, per the finding above.
5. **Manual verification against a small set first** (the same golden-company discipline this entire project has used from Day 1) — Apple, plus 2-3 companies with a genuinely different segment shape (a single-segment company, a company that discloses only geography, a company that discloses only product) — before trusting the title-matching heuristic across all 100.

## Reference asset built: a pre-verified report index, not a blind runtime heuristic

Point 2 above (the title-matching heuristic) is now *research*, not just a plan — done so the eventual build doesn't have to rediscover which report each company uses.

**`pipeline/reference/segment_report_index.json`** — one entry per company: its single most-recent 10-Q/10-K (form, filing date, accession number) and every candidate report whose title matched "Segment"/"Disaggregat", each flagged `likely_tabular` (title contains "(Details)" — a real numbers table, confirmed by inspection — vs. a bare title, usually narrative text only).

**Why report *title* is what's stored, not the R-number**: `R38.htm`-style filenames are **not stable** across a company's own filings — they're a per-filing sequential rendering order that shifts if any disclosure is added, removed, or reordered in a later filing. A company's own title text for a disclosure ("Segment Information", "Revenue - Disaggregated Net Sales...") is far more stable, since it comes from the company's own XBRL element/label choices, which rarely change quarter to quarter. Storing titles means a future fetch just re-reads that filing's own (fresh) `FilingSummary.xml` at fetch time to resolve the *current* R-number — correct even if the numbering has shifted since this index was built, rather than a stale hardcoded filename.

**Generated by `pipeline/scripts/build_segment_report_index.py`** — a standalone research tool, not part of the production pipeline (not imported by any job, no CLI wiring). Rerunnable at any time to refresh the index against each company's then-latest filing. Uses the shared `SECClient` (including the cross-process rate-limiter fix from earlier this session), so it's safe to run alongside any other SEC-fetching job.

## Honest sizing

This is **not** a zero-new-fetch, quick-win item like tonight's other additions (Employee Headcount, the peer-comparison fix) — it's a genuinely new capability: new fetch pattern, new parser, new storage, real per-company variance requiring verification, not just a new concept mapping over already-fetched data. The no-backfill correction above shrinks the *fetch volume* to something genuinely small (one filing per company, ~300-400 requests total for the top 100) — but the *parsing and verification* effort is unchanged: a new HTML-table parser, a per-company title-matching heuristic that needs real hand-verification against a sample before trusting it at 100-company scale, and a storage shape that deliberately doesn't force a shared taxonomy across companies. Overall still comparable in shape to the original Ownership build (doc 19) — a new document-parsing capability against individual filings, not the bulk Company Facts API — just with a smaller, one-shot-per-company fetch footprint than a naive multi-year version would have had.
