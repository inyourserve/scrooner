**A dataset's own bundled metadata/readme can contradict a separately-fetched reference spec from the same publisher — and be the one that's current.** Found live 2026-08-17 (Ownership Stage 4): SEC's Form 13F field-layout spec PDF (`form_13f.pdf`) describes `VALUE` as "Market value (x$1000)" — true historically, but SEC changed this 2023-01-03 to report actual dollars, a change reflected only in the bulk zip's own bundled `FORM13F_readme.htm`, not the separately-hosted spec PDF. Trusting the PDF (multiplying by 1,000 anyway) turned a real ~$242B position into a displayed $242 **trillion** figure — caught by eyeballing the rendered company page, not by any type/range check. Before trusting a reference document's field description for a downloaded dataset, check whatever metadata/readme ships *with that specific download* — it's more likely to reflect the data's actual current state than a spec fetched from a different URL, even from the same official source.

**Casting a column to text in a SELECT list without an explicit alias can silently shadow the numeric column of the same name in a later `ORDER BY`.** Found live 2026-08-17 (Ownership Stage 4): `apps/site`'s `getTopInstitutionalHolders` cast `shares::text` in its outer `SELECT` (needed for the Decimal-as-string wire discipline, see below) and then wrote an unqualified `order by shares desc` — Postgres resolves an unqualified `ORDER BY` name against a `SELECT`-list output alias before a same-named `FROM`-clause column, so the sort ran as a *text* comparison ("9995" sorts above "9990000" lexicographically) instead of numeric. AAPL's real top holder (Vanguard, ~954M shares) rendered below several sub-10,000-share filers on first try. Fixed by qualifying the `ORDER BY` reference to the subquery (`order by dedup.shares desc`) so there's no ambiguity. Whenever a query casts a column to text for output, either alias the cast explicitly or qualify every later reference to the numeric original — never leave both same-named and unqualified in the same query.

**A defensive check that "shouldn't be necessary" caught a real bug a small sample couldn't have — verify new assumptions against the full target set, not just a sample.** Found live 2026-08-17 (Ownership Stage 2): `insider.py`'s docstring originally claimed Form 4 needs no issuer-vs-filer check, unlike Schedule 13D/13G — verified against a small real sample (a handful of AAPL filings) where it held. The check was implemented anyway, defensively. Running the *full* golden-10 (not just AAPL) surfaced 285 real mismatches across 5 companies (JPMorgan itself crossing 10%-ownership thresholds in other companies and filing Form 4 as *their* insider; Alphabet's venture arm filing under the parent's CIK for its own portfolio companies) — the same underlying EDGAR behavior Schedule 13G already has, just also true here. The check already excluded every one correctly; only the docstring was wrong. Lesson: a small sample that doesn't exercise an edge case looks identical to a rule with no edge case — this is the same shape of mistake Company Master 4a already hit once (a ticker-change proxy verified for one case, wrong for 27/38 at full-set scale), now confirmed a second time in a different module.

**A "corrected" number is not automatically a fully-verified one — the correction itself still needs the same full-run check as the original wrong claim.** Found live 2026-08-17 (Ownership Stage 3): doc 19's own first-draft correction (91 filings claimed after fixing a Module-5-vs-Module-4 mixup) was *itself* still an undercount — it only checked the base `submissions.json` file's `filings.recent` window, not continuation pages. Running Stage 3 for real against the full golden-10 surfaced 3,637 Schedule 13D/13G-family filings, not 90 (JPM alone: 2,975, almost all itself as institutional filer, not subject). Lesson: catching one wrong assumption doesn't retire the discipline that caught it — apply the same "check the full target set" rule to the corrected number too, not just the original claim.

**New data source pattern: EDGAR's full-submission `.txt` SGML header, when the primary document has no structured XML.** Found live 2026-08-17 (Ownership Stage 3): unlike Form 4, Schedule 13D/13G has never had a structured XML primary document — checked live against both a 2024 and a 1995 filing, both plain HTML/text. But every full-submission `.txt` (any accession, any year back to at least 1995) carries a machine-readable `SUBJECT COMPANY`/`FILED BY` SGML header with `CENTRAL INDEX KEY` for each — exactly what's needed to resolve an issuer-vs-filer question without parsing free text. Worth remembering as a fallback pattern any time a future form type turns out to lack structured XML: check the full-submission header before assuming a fragile HTML-scraping build is the only option.

**A generic "current listing" query is not the same as "the primary common-stock ticker" — a company can have many simultaneous listings for reasons that have nothing to do with going public more than once.** Found live 2026-08-17 (Alpaca integration, doc 25): the first version of `market_price_alpaca.py` resolved each company's ticker via `core.listing` (all rows with `effective_to is null`), building a `{cik: ticker}` dict. JPM alone has 9 such rows — 5 preferred-share classes plus several structured notes/ETNs it issues under its own CIK (the exact same "one CIK, many securities" pattern already found for Form 15/Chase Capital, doc 23) — and Enbridge has 14 OTC pink-sheet variants of its one real listing. A plain dict comprehension silently kept whichever row Postgres returned last, so the first live run queried Alpaca for a JPM-issued ETN ("VYLD") instead of JPM's own stock, and 3 of 10 companies got no price back at all. Fixed by sourcing the primary ticker from `golden_companies.json`'s own already-curated field instead of querying `core.listing` generically — `core.listing` still has no "is primary" flag, a real, named gap for any future wider universe, not solved here. Lesson: before trusting "the current row(s) for this company" as unambiguous, check whether the entity can legitimately have more than one for reasons unrelated to the question being asked (ticker changes, series/classes, subsidiary-issued instruments) — this is now the third time this exact shape of bug has appeared in this project (Form 15/Chase Capital, Form 4/13G issuer-vs-filer, now this).

**`core.market_price` currently holds only fabricated data.** Every row is `is_mock=true`/`source='mock'` — no real vendor has been integrated. Any code that reads this table (starting with the still-not-built Mapper follow-on that computes the 6 price-dependent metrics) must filter `is_mock=false` before treating a value as real, exactly the same hard-filter discipline as `core.fact.is_authoritative`. **`screener/` is read-only and has no HTTP exposure yet.** It queries `analytics.metric_value`/`core.company` directly (no new schema); manual testing is via `scrooner-screen '<query-json>'`. The 6 price-dependent metrics become screenable automatically the moment the Mapper follow-on above computes real values for them — `screener/resolve.py`'s catalog is already sourced from `analytics.metric_definition where requires_price = false`, no `screener/` code change needed when that changes.

**`ai_query/` runs a deterministic rule-based parser only — no LLM, no real vendor call.** Manual testing via `scrooner-ask "<english text>" --run`. Its `NLInterpreter` Protocol (`ai_query/interpreter.py`) is the swap point for a real LLM (6c) later — a new class implementing the same `interpret(text) -> InterpretationResult` contract, no change to `screener/` or anything downstream. The rule-based grammar (`ai_query/rules.py`) is deliberately bounded (see its module docstring for the documented "between" + other-clause limitation) and its alias tables (`ai_query/aliases.py`) are curated, not fuzzy-matched — extend them the same deliberate way `concept_mapping` gets extended, never by guessing at a phrase's likely meaning.

**The Collector must not:** calculate ROIC/FCF/CAGR, decide which XBRL concept means revenue, clean financial statements, generate screens, contain AI, or expose frontend APIs. It fetches, retries, checkpoints, hashes and stores — nothing else. **The Normalizer must not:** apply investor-facing formulas, decide which XBRL tag "means" revenue, or repair/guess facts the filing didn't report — see doc 09's boundary table. **The Mapper must not:** write to `core`, generate screens, evaluate filter predicates, or bypass `core.fact.is_authoritative` — see doc 11's boundary table. **Company Master must not:** calculate Market Cap/P/E/P/S/P/B/Dividend Yield/FCF Yield (Mapper's job even once 4b supplies the missing price input — see doc 13's boundary table), or assert a `delisted` status this project has no data source to confirm (schema-enforced: `active`/`stale`/`unknown` only). **The Screener must not:** write to `core`/`analytics`, parse natural language (AI Query Engine's job, strictly downstream), invent a metric/operator outside doc 02's locked lists, guess a null value instead of excluding the company, or support OR/nested boolean logic beyond simple AND-of-predicates — see doc 14's boundary table. **The AI Query Engine must not:** generate a financial fact, metric value, or company list directly (every real answer still comes from the Screener), bypass the Screener's own validation, invent a metric/field the screenable catalog doesn't have, or silently reinterpret an ambiguous request instead of flagging it — see doc 15's boundary table. **`ownership/` must not:** store a Form 4/Schedule 13D/13G row without confirming the golden company as the actual issuer (a missing/unparseable issuer field is inconclusive, never a default match), or guess `percent_of_class`/`shares_owned` from free text instead of leaving it `NULL` — see doc 19. All six frozen modules (Collector through Backend API) are not moving targets — a "quick fix" that blurs any boundary, or that starts writing a later phase's logic into an earlier folder, is building against the architecture. This matters *more*, not less, now that this is a folder instead of a repo — there's no longer a repo wall stopping a stray edit from crossing into `apps/`.

**Shared-table writes need explicit scoping on every dimension another writer keys on, not just the obvious one.** Found live 2026-08-16 (Mapper Day 6): `calculate.py` and `ttm.py` both write `analytics.metric_value`, and `roic`/`roe` share one `metric_definition_id` between them, distinguished only by `period_label`. A delete scoped by `company_id` alone, then by `company_id` + `metric_definition_id` alone, both silently destroyed the other stage's rows on rerun — only a delete additionally excluding `period_label='TTM'` correctly partitioned the two writers. Before adding any new write path to a table another stage also writes into, check what dimensions the other writer keys on, not just the primary foreign key.

**A design idea verified against one real case is not evidence it generalizes — check it against the whole target set before trusting it as a default.** Found live 2026-08-16 (Company Master 4a): a ticker-change-date proxy (derive from the nearest name-change date) was verified correct for the one case it was designed around (Block/Square, independently confirmed as a real, publicly-announced coincidence). Applied as a blanket default, it produced wrong dates for 27 of 38 golden-set listing rows — AAPL and NKE, whose tickers never changed, both got a plausible-looking but false date from an unrelated real rename. Fixed by requiring explicit per-CIK confirmation before applying any such proxy (a small, reviewed allowlist), mirroring Mapper's `approved`/`provisional`/`rejected` `concept_mapping` discipline: automate detection/ranking, keep acceptance human, especially wherever a wrong answer would look plausible instead of obviously broken.

**A composite `ON CONFLICT` key with a nullable column silently fails to dedupe.** Found live 2026-08-16 (Company Master 4a): SQL's `NULL ≠ NULL` means `ON CONFLICT (company_id, company_name, effective_from)` never matches when `effective_from` is `NULL`, so a rerun quietly inserted a duplicate row for every company with no former-names history (19 rows became 24). Fixed with delete-then-reinsert per company, the same pattern Mapper's `resolve.py`/`calculate.py` already use. Before trusting any `ON CONFLICT`-based upsert as idempotent, check whether any column in its conflict target can be `NULL` — if so, delete-then-reinsert, not an unexamined assumption the constraint will fire.

**A named test case verifies correctness, not output completeness — a new field needs its own explicit "does this appear in the output" check.** Found live 2026-08-17 (Screener Stage 5d): `query.py`'s matched-company output only included metric values that were also filter predicates. Every one of doc 14's own named test screens filtered on the metric it cared about, so none exercised `sort_by` as an independent field — a query sorted by a metric it didn't also filter on returned the correct order with no visible value explaining it, an incomplete-lineage gap. Fixed by unioning `sort_by` into the shown-metrics set regardless of whether it's also a predicate. When a new field is added to any query/result schema, check that it actually surfaces in the output, not just that it affects behavior correctly — those are different properties, and a Definition of Done's named test cases are a floor, not a ceiling.

**Test the phrasing a real user would actually use first, not the phrasing that's easiest to implement.** Found live 2026-08-17 (AI Query Stage 6b): every one of doc 15's test queries except one used clean, filler-free metric phrasing ("software companies," "top 3 by roic") and passed immediately; the one phrased the way an investor would actually type it ("companies with ROE above 30%") failed outright, because filler words weren't stripped before metric lookup. Fixed with a small, curated filler-prefix list — but the deeper lesson is about verification order: when a Definition of Done lists several test cases, don't assume they're equally likely to surface a real gap. The one closest to actual real-world usage deserves checking first, not last.

**A framework handling `Decimal`/typed values correctly in one code path doesn't mean it's handled everywhere — check every serialization boundary separately.** Found live 2026-08-17 (Backend API Stage 7b): FastAPI's automatic response encoding serializes `Decimal` as a full-precision string with zero extra code — but a manual `json.dumps()` call three lines away, used to build a JSONB column for a database write, uses Python's raw stdlib `json` module instead and crashes on the exact same `Decimal` value. Fixed with Pydantic's own `model_dump_json()`. The lesson: "the framework handles this" is a claim about one specific code path, not a property of the data type — verify each place a value gets serialized, don't extend trust from one path to another that merely looks similar.

**A database driver's typed return values can silently break an equality check against an application-level value of the same conceptual identity.** Found live 2026-08-17 (Backend API Stage 7c): psycopg returns a `uuid.UUID` object for a Postgres `uuid` column; comparing it directly (`!=`) against the plain string `user_id` Supabase Auth hands back is *always* unequal in Python, even for the exact same UUID — so an ownership check failed for every caller, including the legitimate owner (failed closed, not a security hole, but a real functional bug). Before trusting an equality check across a database-driver boundary, confirm both sides are actually the same Python type, not just the same conceptual value — `str()` both sides explicitly rather than assuming a driver's return type matches what an external system (an auth provider, an API client) hands you.

**Sorting periods by date alone breaks when two different granularities can share an end date.** Found live 2026-08-17 (company page MVP): a company's FY period and its Q4 period share the same `end_date` (Q4 is the fiscal year's own last quarter), so a statement table sorted purely by `end_date` interleaved "FY 2025" between "Q3 2025" and "Q4 2025" with no stable, sensible order. Any future view spanning multiple period granularities (FY + quarterly, or later FY + TTM) needs to partition by granularity first, sort within each partition second — never a single date-only sort across mixed granularities.

## Database

Postgres schema `raw` (Collector, append-only/upserted per doc 08) and `core` (Normalizer, `company`/`listing`/`filing`/`period`/`unit`/`concept`/`fact` — added `db/migrations/0003_core_schema.sql`, explained in doc 09). The Collector never writes `core`/`analytics`/`app`; the Normalizer reads `raw` (never writes it) and writes only `core` — no new SEC network calls happen in `normalizer/`, it's purely a transform over what the Collector already stored. Raw payloads go to Supabase Storage under `raw/sec/...`; Postgres holds metadata and the storage pointer, never the blob.

SEC fair access: declared User-Agent (see `.env.example`), aggregate request rate ≤8 req/s (doc 07 confirms SEC's own ceiling is 10/s — this is a deliberate buffer, don't creep toward it).

**Connection reliability, Supabase side:** batch DB jobs over the free-tier pooler connection have hit real, intermittent `SSL SYSCALL... Operation timed out` errors and, separately, silent multi-minute hangs with no error at all (Normalizer Day 7 — see `doc/learnings/normalizer-retrospective.md`). If a job stalls with no output: don't assume it's a repeat of a previously-fixed cause. Check `select pid, state, wait_event_type, wait_event, query_start, query from pg_stat_activity where datname = current_database()` for a genuine blocking lock first; if none, it's very likely a stalled client-side connection — stop the task and retry once cleanly rather than waiting indefinitely. Two of Day 7's three incidents turned out to be unrelated causes that looked identical from the outside. Not yet a formal runbook (doc 05's "evidence before expansion" — one day's worth of incidents isn't quite the bar); promote this to one if it recurs during Mapper work.
