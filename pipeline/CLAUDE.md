## Database

Schemas: `raw` (Collector, append-only), `core` (Normalizer: company/listing/filing/period/unit/concept/fact), `analytics` (Mapper: canonical_concept/concept_mapping/canonical_fact/metric_definition/metric_value + many data-quality tables), `app` (backend: saved screens, entitlements, usage). Raw payloads go to Supabase Storage under `raw/sec/...`; Postgres holds metadata + storage pointer only.

**Supabase pooler caps total concurrent client connections at ~15, shared across every service** (pipeline jobs, `apps/backend`, `apps/app`). Check `select count(*) from pg_stat_activity` before raising any pool size. Connections get TCP keepalives from `common/config.py`.

**SEC fair access:** declared User-Agent, aggregate rate ≤8 req/s (SEC's own ceiling is 10/s — this is a deliberate buffer).

**Database is large (~30GB+)** — `core.fact` alone is tens of GB. Any long-running DDL (`CREATE INDEX CONCURRENTLY`, etc.) needs `psql -f <script-starting-with-"SET statement_timeout = 0;">`, run detached (`nohup ... & disown`), never through the Supabase MCP `execute_sql` (its own timeout kills the connection) and never via `psql -c` (multi-statement `-c` is one implicit transaction, which `CONCURRENTLY` forbids). A `CONCURRENTLY` build interrupted mid-way leaves an invalid index (`indisvalid=false`) — `DROP INDEX CONCURRENTLY IF EXISTS` before retrying. **Run `get_advisors` (performance + security) after any DDL.**

## Component boundaries (frozen, not moving targets)

Collector: fetch/retry/checkpoint/hash/store only — never normalize, repair, infer periods, map concepts, or calculate metrics. Normalizer: never applies investor-facing formulas, maps concepts, or repairs/guesses a fact the filing didn't report. Mapper: never writes to `core`, generates screens, evaluates filter predicates, or bypasses `core.fact.is_authoritative`. Company Master: never calculates Market Cap/P/E/etc. (Mapper's job) or asserts `delisted` without a real data source. Screener: never writes to `core`/`analytics`, parses natural language, invents a metric/operator outside doc 02's locked lists, or guesses a null value. AI Query Engine: never generates a fact/list directly, bypasses Screener validation, or silently reinterprets ambiguity. `ownership/`: never stores a Form 4/13D/13G row without confirming the real issuer, never guesses a numeric field from free text.

A "quick fix" that blurs any of these, or starts writing a later phase's logic into an earlier folder, is building against the architecture — this matters *more* as a folder than it did as a separate repo, since there's no repo wall stopping a stray edit.

## Standing conventions and durable gotchas

These are the lessons from the full archived journal that are still true and still load-bearing. Full story for any of these: search the archive by keyword.

**Correctness discipline**
- `core.fact.is_authoritative = false` is a hard filter everywhere — "no authoritative fact" is a valid, expected null, never fall back to an arbitrary non-authoritative row.
- Any value handling must stay `Decimal` end to end (`parse_float=Decimal`, never cast to float, serialize as a string at any API/frontend boundary).
- A `_resolved` concept (e.g. `total_debt_resolved`, `revenue_sanity_resolved`) has **zero** `concept_mapping` rows and is never touched by `resolve()` — it exists specifically so a fallback/override mechanism can write it safely without `resolve-facts` wiping it on rerun. Any new such concept needs its delete scope to explicitly exclude it (or scope deletes to only concepts that *do* have `concept_mapping` rows) — `resolve.py`'s own delete was fixed this way 2026-09-03.
- **Shared-table writes must be scoped to every dimension another writer keys on, not just the primary foreign key.** This exact bug (two writers into the same table/concept, one writer's delete silently wiping the other's rows) recurred at least 5 times across this project (`metric_value`'s `roic`/`roe` vs `period_label='TTM'`, `expanded_metrics.py`'s delete-scope bug, `concept_fallback.py` vs `parsers/main_parser.py`, institutional/mutual-fund ownership windows, revenue resolvers). Check this explicitly before adding any new write path to a shared table.
- Keyword-matched XBRL tag candidates are frequently a **different concept sharing vocabulary** (e.g. `CostsAndExpenses` looked like opex but included COGS; `goodwill`'s top candidate explicitly excludes goodwill). Every candidate tag needs a live coexistence check (does it match the primary tag when both are present for the same company/period?) before being added past `provisional` confidence — never batch-adopt from a frequency count alone.
- A composite metric summing multiple *optional* components (dividends + buybacks − dilution, etc.) must treat a genuinely-absent component as `$0`, never require every component non-null — the tell-tale bug signature is the composite's coverage being *lower* than its most restrictive single input.
- Materiality floors matter: a ratio off a near-zero-but-nonzero denominator (revenue, assets, interest expense) is mathematically correct and economically meaningless. `calculate_shapes/materiality.py`'s `CONCEPT_MATERIALITY_FLOORS` is keyed by the actual denominator *concept*, not per-metric, so any future metric dividing by a registered concept is automatically protected.
- A TTM/trailing-window helper that does `order by period_end desc limit 4` must also check the **most recent** of those 4 is actually recent (a staleness guard) — checking "found 4 rows" alone lets a company whose computation stalled keep presenting year-old data as current "TTM" forever.
- yfinance is validation/comparison only — **never** a stored or displayed value (founder direction, standing). A blank cell is fixed by finding the real SEC tag/filing behind it; yfinance is only the target to check a derived/summed value against.
- A rendered SEC `R*.htm` statement report needs its scale qualifier ("$ in Millions/Thousands" in the report title) applied before trusting a parsed number, and its row/column alignment verified against real, diverse filings before trusting a positional index — footnote-reference cells can desync a data row's index from the header row's date columns.

**Operational / batch-job discipline**
- Any per-company/per-concept batch job loads lookups into memory up front and batches writes — never a query per row in a loop (the N+1 shape has caused real multi-hour slowdowns and connection timeouts at least 3 times).
- Batch loops must use the shared resilience helpers, never bare `conn.rollback()`: `common/errors.py::safe_rollback()` (per-company loops — caller reassigns `conn = safe_rollback(...)`) and `db/connection.py::run_tolerating_exit_commit_failure()` (CLI commands whose outer connection idles across a long batch). `test_connection_hardening.py` enforces the pattern exists at every batch call site. The Collector is exempt — it's checkpointed/resumable, so crash-then-resume is its designed recovery, not a gap.
- A background `bash -c "... | xargs -P N ..." &` wrapper is **not** stopped by killing its visible child workers — the wrapper itself respawns new ones. Find and kill the wrapper `bash -c` process (`ps aux | grep "xargs -P"`), not just children.
- Before retrying any backgrounded command that looks hung or failed, confirm via `ps aux` that the prior attempt's actual process has exited — a harness "moved to background/completed" notice only means it stopped watching, not that the process stopped running. Duplicate overlapping full-population jobs have wasted hours of real work this way more than once.
- A full-population bulk `executemany` must be chunked (~5,000 rows), never one call over the whole matched set — a single unbounded call drops the pooled connection mid-write at real scale.
- A delete-then-reinsert scoped by `company_id` (or similar) needs a supporting composite index *before* it runs at full-population scale — a missing index here has caused real production timeouts/incidents at least twice.
- Multiple Claude sessions regularly work this repo concurrently against the same shared dev Supabase instance. `ListAgents` before launching any heavy batch job (a full/wide `--ciks` run, a bulk `executemany`, a full-population rerun), and coordinate with a peer showing `busy` before starting one. Light, single-connection, index-backed reads are fine even while a peer's heavy job runs; heavy writes and full scans are not.
- This dev Mac's local disk filling up (not the database) can silently hang a process indefinitely with zero active query and zero error output — `df -h /private/tmp` costs nothing and is worth checking before assuming a process is stuck on the network/DB.
- This dev Mac's `/tmp` (and any process running there) can be wiped mid-session by an environment restart, with no warning. Database state survives (Postgres is remote); always re-derive local state (CIK lists, shard files) fresh from a live DB query rather than trusting a file or process from more than a few minutes ago.
- macOS's default `/bin/bash` is 3.2 (no `readarray`/`mapfile`, no `timeout` binary) — use `IFS=',' read -ra` and Python `subprocess.run(timeout=)` instead. An inlined `xargs -P N -I{} bash -c '<multi-line script>'` can also hit a real macOS command-length limit — call a separate wrapper script file instead.
- Local Postgres on this Mac is v14 (Homebrew/EDB); CI runs `postgres:16`, prod runs 17.6. PG15+-only syntax can't be replayed locally — test everything else against a scratch local Postgres with that one line patched out in a throwaway copy, trust real CI for that specific syntax.
- `scripts/run_sharded.sh` is the generic N-way parallel runner for any `scrooner-*` command taking `--ciks` — re-derives the active CIK list fresh from the DB, launches N detached `nohup`+`disown` workers. Helps a per-company round-trip loop; does **not** help an already-set-based bulk-SQL tool (more shards there just means more queries fighting over the same disk pages).

**CI / git / deployment**
- A commit on `main` must be pushed in the same turn it's made.
- CI goes red from uncommitted dependencies more often than from real syntax errors: a committed migration with an untracked lower number, or committed code importing a module that only exists in the working tree, both fail silently until someone runs `git ls-files --others --exclude-standard` or reads the actual job-step failure (`gh run view <id> --json jobs`, then `--log-failed`) rather than assuming.
- Several Claude sessions share this working tree and its git index — a bare `git commit` also commits whatever another session has staged. Use `git commit -- <your paths>` or check `git diff --cached --stat` first.
- `uv run <service>` does not auto-load `.env` — source it explicitly (`set -a; source .env; set +a`) before running `apps/backend`'s `uvicorn` directly.

## Architecture additions (what exists, in brief)

- **Parsers/calculators are registries, not one-file-per-concept sprawl**: `parsers/main_parser.py`'s `PARSER_REGISTRY` (concept → dedicated rendered-report parser, e.g. `revenue_parser.py`, `cost_of_revenue_parser.py`), backed by `analytics.concept_parser_result`/`concept_parser_attempt` (kept separate from `canonical_fact`, which stays `resolve()`'s exclusive output). `mapper/main_calculator.py`'s `METRIC_CALCULATOR_REGISTRY` maps every metric to whichever of `calculate.py`'s generic engine or a specialized module computes it. `calculate.py`'s own internal formula-shape dispatch is further split into `calculate_shapes/` (one file per shape: ratio/sum_diff/sum_diff_ratio/additive/days/roic). New shapes/parsers/calculators are added only once a real, *sized* gap justifies it — never preemptively.
- **`mapper/revenue_resolvers/`**: one file per company-grouping strategy for closing revenue gaps (spurious-zero-tag preference, collaborative-arrangement income, net-lease income, rendered-report parser), dispatched in priority order by a registry — the same "sub-mapper per shape" pattern applied to revenue specifically.
- **`mapper/dedup_majority_resolver.py`** (`resolve-dedup-holes`): where Stage 2e correctly-by-design left a concept with zero authoritative facts over a trivial cross-filing disagreement, a majority vote across raw facts (with a stock-split-aware reconciliation path) fills the `_resolved` concept — never overrides a value `resolve()` already found.
- **`sanity/`** — the Data Sanity Layer: yfinance ratio/line-item cross-checks (`data_sanity_check`, `statement_comparison_finding`), SEC Frames self-consistency (`frames/`), accounting-identity checks (`accounting_identity.py` → `identity_check_score`), metric plausibility gates (`plausibility_check.py`), freshness checks (`freshness_check.py`), and `tag_investigator.py` (per-company `company_tag_preference` overrides — evidence-backed, never a global tag-mapping change from a single company's finding). `incidents/dashboard.py` unifies all of these into one severity-ranked view (`analytics.data_incident`). `mapper/coverage_matrix.py` + `mapper/company_coverage_dashboard.py` answer "does company X have data point Y and why not" from both the metric-wise and company-wise direction.
- **`sanity/period_completeness.py`** (`analytics.company_data_finding`, `analytics.period_gap`) is the main coverage-gap tracker — every missing (company, concept, period) cell gets one classified cause (`no_mapped_tag`, `q4_not_derived`, `conflict_split`, `not_in_sec_feed`, etc.), each mapped to a `finding_type` (`pipeline_bug`/`filer_error`/`data_limit`/`legitimate_absence`). **`not_in_sec_feed` is not always a genuine SEC-side limit** — the single-tag `companyconcept` probe this check used to rely on can return an empty result for a real company with real data (confirmed on Visa, Abbott, Ford, PayPal, and ~14% of a sampled population); fixed 2026-10-09 to only trust a non-empty probe result. Separately, SEC's own bulk Company Facts product can lag 2+ months behind a real, confirmed-filed 10-Q for large companies' most recent quarter — a genuine data-currency gap, not a classifier bug, that the existing rendered-report-parser pattern could in principle close (not yet built for core balance-sheet/income-statement concepts).
- **`scripts/find_period_gap_candidate_tags.py`** / **`scripts/find_concept_gap_clusters.py`** — the two reusable tools for finding a real tag-mapping fix: the first asks "what unmapped tag is present at a concept's specific missing periods," the second asks "what do companies missing a concept *entirely* share." Both only ever produce a *lead* — every candidate still needs a live coexistence check against real companies before shipping.
- **Screener** (`screener/`) reads `analytics.company_screening_snapshot` (a wide, native-column table rebuilt per `dataset_version`, not EAV/JSONB — both alternatives were tried and measured slower) rather than querying `metric_value` directly; boolean AND/OR/NOT trees compile to parameterized `EXISTS` SQL (ADR 0001, which also approved Redis for `apps/backend` caching, overriding doc 02's original "no Redis" for that one case).
- **Company Master price data**: `core.market_price_alpaca` (real, via Alpaca `delayed_sip`) is the only real price source — `core.market_price` still holds only mock rows from the pre-vendor-decision phase and must never be read as real.
