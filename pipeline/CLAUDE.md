**A repeated "connection is lost" failure was actually an N+1-round-trip bug in `normalizer/restatements.py`, not network flakiness -- found live 2026-08-26, a second instance of the exact lesson pipeline/CLAUDE.md already documented on 2026-08-22 (there: a missing index; here: no index issue at all, pure round-trip count).** `supersede_facts_for_company` and `link_amendments_for_company` each issued one SELECT plus one-or-two UPDATEs *per row* in a Python loop (2,000+ round trips for a company with 1,000+ superseded fact pairs, ~11 minutes every run) -- the exact per-row-query-in-a-loop shape this file's own "Notes for skill/agent authors" section already forbids elsewhere in this doc. Fixed by batching each into a handful of set-based queries via `unnest(...)` arrays, regardless of row count -- same semantics, verified against the existing `tests/unit/test_restatements.py` (updated to match the new batched query shapes) before trusting it. After the fix, the entire remaining pipeline (this stage plus 13 more) completed in one clean pass with zero retries. **Lesson: before accepting "the network is flaky" as the explanation for a slow/dropping batch job, check whether the code itself does one write per row in a loop -- that failure mode is indistinguishable from a real network problem until you read the query pattern, not just the error message.**

**A dataset's own bundled metadata/readme can contradict a separately-fetched reference spec from the same publisher — and be the one that's current.** Found live 2026-08-17 (Ownership Stage 4): SEC's Form 13F field-layout spec PDF (`form_13f.pdf`) describes `VALUE` as "Market value (x$1000)" — true historically, but SEC changed this 2023-01-03 to report actual dollars, a change reflected only in the bulk zip's own bundled `FORM13F_readme.htm`, not the separately-hosted spec PDF. Trusting the PDF (multiplying by 1,000 anyway) turned a real ~$242B position into a displayed $242 **trillion** figure — caught by eyeballing the rendered company page, not by any type/range check. Before trusting a reference document's field description for a downloaded dataset, check whatever metadata/readme ships *with that specific download* — it's more likely to reflect the data's actual current state than a spec fetched from a different URL, even from the same official source.

**Casting a column to text in a SELECT list without an explicit alias can silently shadow the numeric column of the same name in a later `ORDER BY`.** Found live 2026-08-17 (Ownership Stage 4): `apps/site`'s `getTopInstitutionalHolders` cast `shares::text` in its outer `SELECT` (needed for the Decimal-as-string wire discipline, see below) and then wrote an unqualified `order by shares desc` — Postgres resolves an unqualified `ORDER BY` name against a `SELECT`-list output alias before a same-named `FROM`-clause column, so the sort ran as a *text* comparison ("9995" sorts above "9990000" lexicographically) instead of numeric. AAPL's real top holder (Vanguard, ~954M shares) rendered below several sub-10,000-share filers on first try. Fixed by qualifying the `ORDER BY` reference to the subquery (`order by dedup.shares desc`) so there's no ambiguity. Whenever a query casts a column to text for output, either alias the cast explicitly or qualify every later reference to the numeric original — never leave both same-named and unqualified in the same query.

**A defensive check that "shouldn't be necessary" caught a real bug a small sample couldn't have — verify new assumptions against the full target set, not just a sample.** Found live 2026-08-17 (Ownership Stage 2): `insider.py`'s docstring originally claimed Form 4 needs no issuer-vs-filer check, unlike Schedule 13D/13G — verified against a small real sample (a handful of AAPL filings) where it held. The check was implemented anyway, defensively. Running the *full* golden-10 (not just AAPL) surfaced 285 real mismatches across 5 companies (JPMorgan itself crossing 10%-ownership thresholds in other companies and filing Form 4 as *their* insider; Alphabet's venture arm filing under the parent's CIK for its own portfolio companies) — the same underlying EDGAR behavior Schedule 13G already has, just also true here. The check already excluded every one correctly; only the docstring was wrong. Lesson: a small sample that doesn't exercise an edge case looks identical to a rule with no edge case — this is the same shape of mistake Company Master 4a already hit once (a ticker-change proxy verified for one case, wrong for 27/38 at full-set scale), now confirmed a second time in a different module.

**A "corrected" number is not automatically a fully-verified one — the correction itself still needs the same full-run check as the original wrong claim.** Found live 2026-08-17 (Ownership Stage 3): doc 19's own first-draft correction (91 filings claimed after fixing a Module-5-vs-Module-4 mixup) was *itself* still an undercount — it only checked the base `submissions.json` file's `filings.recent` window, not continuation pages. Running Stage 3 for real against the full golden-10 surfaced 3,637 Schedule 13D/13G-family filings, not 90 (JPM alone: 2,975, almost all itself as institutional filer, not subject). Lesson: catching one wrong assumption doesn't retire the discipline that caught it — apply the same "check the full target set" rule to the corrected number too, not just the original claim.

**New data source pattern: EDGAR's full-submission `.txt` SGML header, when the primary document has no structured XML.** Found live 2026-08-17 (Ownership Stage 3): unlike Form 4, Schedule 13D/13G has never had a structured XML primary document — checked live against both a 2024 and a 1995 filing, both plain HTML/text. But every full-submission `.txt` (any accession, any year back to at least 1995) carries a machine-readable `SUBJECT COMPANY`/`FILED BY` SGML header with `CENTRAL INDEX KEY` for each — exactly what's needed to resolve an issuer-vs-filer question without parsing free text. Worth remembering as a fallback pattern any time a future form type turns out to lack structured XML: check the full-submission header before assuming a fragile HTML-scraping build is the only option.

**A generic "current listing" query is not the same as "the primary common-stock ticker" — a company can have many simultaneous listings for reasons that have nothing to do with going public more than once.** Found live 2026-08-17 (Alpaca integration, doc 25): the first version of `market_price_alpaca.py` resolved each company's ticker via `core.listing` (all rows with `effective_to is null`), building a `{cik: ticker}` dict. JPM alone has 9 such rows — 5 preferred-share classes plus several structured notes/ETNs it issues under its own CIK (the exact same "one CIK, many securities" pattern already found for Form 15/Chase Capital, doc 23) — and Enbridge has 14 OTC pink-sheet variants of its one real listing. A plain dict comprehension silently kept whichever row Postgres returned last, so the first live run queried Alpaca for a JPM-issued ETN ("VYLD") instead of JPM's own stock, and 3 of 10 companies got no price back at all. First fixed with a `golden_companies.json`-sourced stopgap, same day replaced with a real, general mechanism (below) — this is now the third time this exact shape of bug has appeared in this project (Form 15/Chase Capital, Form 4/13G issuer-vs-filer, now this): before trusting "the current row(s) for this company" as unambiguous, check whether the entity can legitimately have more than one for reasons unrelated to the question being asked (ticker changes, series/classes, subsidiary-issued instruments).

**New module: real security-type classification (`company_master/security_type.py`, doc 25, built 2026-08-17), replacing the golden-file ticker stopgap above.** Sourced from **OpenFIGI**, explicitly **not Alpaca** — direct user instruction, to keep the price vendor's role scoped to price only and not blur it into an identity/classification source. Classifies every current listing (`idType=TICKER` mapping) and stores OpenFIGI's own raw `securityType` string in a new `core.listing.security_type` column — `NULL` means no match, inconclusive, never a negative signal. Checked live across the *full* golden-10 (38 listings) before trusting it, not a sample: found that TSM's own real working ticker classifies as `"ADR"`, not `"Common Stock"` — a naive Common-Stock-only filter would have wrongly excluded the one ticker this pipeline actually needs (`PRIMARY_SECURITY_TYPES = {"Common Stock", "ADR"}` accounts for this). 8 of 10 companies resolve unambiguously; 2 (Alphabet's dual share classes, TSM's ADR vs. its own underlying OTC ordinary shares) have more than one *legitimately valid* primary candidate, not a data error — `resolve_primary_tickers()` breaks that tie with `golden_companies.json`'s curated choice, now a secondary role instead of the primary source of truth. Also found live: unauthenticated OpenFIGI's real per-minute rate limit is tighter than its headline "~5,000/day" figure suggests — a 0.3s request pace produced real HTTP 429s, fixed with a 1.5s pace plus exponential-backoff retry on 429 specifically.

**`core.market_price` currently holds only fabricated data.** Every row is `is_mock=true`/`source='mock'` — no real vendor has been integrated. Any code that reads this table (starting with the still-not-built Mapper follow-on that computes the 6 price-dependent metrics) must filter `is_mock=false` before treating a value as real, exactly the same hard-filter discipline as `core.fact.is_authoritative`. Before a real vendor lands, mock rows must be cleared for whatever scope the real data covers — never let mock and real coexist for the same `(company_id, price_date)`.

**`screener/` is read-only and has no HTTP exposure yet.** It queries `analytics.metric_value`/`core.company` directly (no new schema); manual testing is via `scrooner-screen '<query-json>'`. The 6 price-dependent metrics become screenable automatically the moment the Mapper follow-on above computes real values for them — `screener/resolve.py`'s catalog is already sourced from `analytics.metric_definition where requires_price = false`, no `screener/` code change needed when that changes.

**`ai_query/` runs a deterministic rule-based parser only — no LLM, no real vendor call.** Manual testing via `scrooner-ask "<english text>" --run`. Its `NLInterpreter` Protocol (`ai_query/interpreter.py`) is the swap point for a real LLM (6c) later — a new class implementing the same `interpret(text) -> InterpretationResult` contract, no change to `screener/` or anything downstream. The rule-based grammar (`ai_query/rules.py`) is deliberately bounded (see its module docstring for the documented "between" + other-clause limitation) and its alias tables (`ai_query/aliases.py`) are curated, not fuzzy-matched — extend them the same deliberate way `concept_mapping` gets extended, never by guessing at a phrase's likely meaning.

**The Collector must not:** calculate ROIC/FCF/CAGR, decide which XBRL concept means revenue, clean financial statements, generate screens, contain AI, or expose frontend APIs. It fetches, retries, checkpoints, hashes and stores — nothing else. **The Normalizer must not:** apply investor-facing formulas, decide which XBRL tag "means" revenue, or repair/guess facts the filing didn't report — see doc 09's boundary table. **The Mapper must not:** write to `core`, generate screens, evaluate filter predicates, or bypass `core.fact.is_authoritative` — see doc 11's boundary table. **Company Master must not:** calculate Market Cap/P/E/P/S/P/B/Dividend Yield/FCF Yield (Mapper's job even once 4b supplies the missing price input — see doc 13's boundary table), or assert a `delisted` status this project has no data source to confirm (schema-enforced: `active`/`stale`/`unknown` only). **The Screener must not:** write to `core`/`analytics`, parse natural language (AI Query Engine's job, strictly downstream), invent a metric/operator outside doc 02's locked lists, or guess a null value instead of excluding the company — see doc 14's boundary table. (OR/nested boolean logic is now supported, added 2026-09-10 — see [ADR 0001](../doc/adr/0001-screener-redis-cache-and-boolean-logic.md) and doc 14's addendum — this bullet's "AND-of-predicates only" restriction is superseded, not the rest of it.) **The AI Query Engine must not:** generate a financial fact, metric value, or company list directly (every real answer still comes from the Screener), bypass the Screener's own validation, invent a metric/field the screenable catalog doesn't have, or silently reinterpret an ambiguous request instead of flagging it — see doc 15's boundary table. **`ownership/` must not:** store a Form 4/Schedule 13D/13G row without confirming the golden company as the actual issuer (a missing/unparseable issuer field is inconclusive, never a default match), or guess `percent_of_class`/`shares_owned` from free text instead of leaving it `NULL` — see doc 19. All six frozen modules (Collector through Backend API) are not moving targets — a "quick fix" that blurs any boundary, or that starts writing a later phase's logic into an earlier folder, is building against the architecture. This matters *more*, not less, now that this is a folder instead of a repo — there's no longer a repo wall stopping a stray edit from crossing into `apps/`.

**Shared-table writes need explicit scoping on every dimension another writer keys on, not just the obvious one.** Found live 2026-08-16 (Mapper Day 6): `calculate.py` and `ttm.py` both write `analytics.metric_value`, and `roic`/`roe` share one `metric_definition_id` between them, distinguished only by `period_label`. A delete scoped by `company_id` alone, then by `company_id` + `metric_definition_id` alone, both silently destroyed the other stage's rows on rerun — only a delete additionally excluding `period_label='TTM'` correctly partitioned the two writers. Before adding any new write path to a table another stage also writes into, check what dimensions the other writer keys on, not just the primary foreign key.

**A design idea verified against one real case is not evidence it generalizes — check it against the whole target set before trusting it as a default.** Found live 2026-08-16 (Company Master 4a): a ticker-change-date proxy (derive from the nearest name-change date) was verified correct for the one case it was designed around (Block/Square, independently confirmed as a real, publicly-announced coincidence). Applied as a blanket default, it produced wrong dates for 27 of 38 golden-set listing rows — AAPL and NKE, whose tickers never changed, both got a plausible-looking but false date from an unrelated real rename. Fixed by requiring explicit per-CIK confirmation before applying any such proxy (a small, reviewed allowlist), mirroring Mapper's `approved`/`provisional`/`rejected` `concept_mapping` discipline: automate detection/ranking, keep acceptance human, especially wherever a wrong answer would look plausible instead of obviously broken.

**A database driver's typed return values can silently break an equality check against an application-level value of the same conceptual identity.** Found live 2026-08-17 (Backend API Stage 7c): psycopg returns a `uuid.UUID` object for a Postgres `uuid` column; comparing it directly (`!=`) against the plain string `user_id` Supabase Auth hands back is *always* unequal in Python, even for the exact same UUID — so an ownership check failed for every caller, including the legitimate owner (failed closed, not a security hole, but a real functional bug). **Connection reliability, Supabase side:** batch DB jobs over the free-tier pooler connection have hit real, intermittent `SSL SYSCALL... Operation timed out` errors and, separately, silent multi-minute hangs with no error at all (Normalizer Day 7 — see `doc/learnings/normalizer-retrospective.md`). If a job stalls with no output: don't assume it's a repeat of a previously-fixed cause. Check `select pid, state, wait_event_type, wait_event, query_start, query from pg_stat_activity where datname = current_database()` for a genuine blocking lock first; if none, it's very likely a stalled client-side connection — stop the task and retry once cleanly rather than waiting indefinitely. **A repeated connection-drop failure can be a real, fixable query-performance bug, not just network flakiness — found live 2026-08-22 via the Supabase MCP server's log access.** The 100-company pilot's `normalizer/restatements.py` stage kept failing with `OperationalError: the connection is lost` across multiple retries. Checking Supabase's own Postgres logs (not available before this session connected the Supabase MCP server) showed the real sequence: three individual queries taking 23s/19s/10s each (a `core.fact` self-join matching an amending filing's facts to the filing it amends, filtered by `filing_id`), immediately followed by `"received fast shutdown request"` → a burst of 9 `"terminating connection due to administrator command"` lines → the database restarting ~45s later. Root cause: `core.fact` had no index with `filing_id` as a usable leading column (only a 5-column composite key with `filing_id` last) — Supabase's own performance advisor (`get_advisors`) had already flagged this exact gap (`fact_filing_id_fkey`, "without a covering index"). Fixed with one additive index (`db/migrations/0019_fact_filing_id_index.sql`) — verified via `EXPLAIN` before/after: the plan cost dropped from `51998` (Nested Loop) to `656` (Hash Join), ~80x cheaper. Lesson: a client-side "connection lost" error doesn't mean the network is flaky — check the database's own logs for what it was doing in the seconds before the drop; a sustained multi-second query can look identical to a random disconnect from the client side, but one is a fixable code issue and the other isn't.

**Real gotcha found building `revenue_parser.py`: a rendered SEC `R*.htm` table's data rows can carry extra interleaved footnote-reference cells (a marker like `[1]`, or just an empty placeholder) that the date-header row does NOT have, so a data row's raw cell index drifts out of sync with the header row's date-column index.** `segment_revenue.py`'s own proven parser assumes 1:1 positional alignment between a row's value cells and the header's date cells — true for every company it was checked against, false for MSP Recovery's primary income statement (a value at raw index 2 actually belonged to date-column 0, not 2). Fixed by pairing the first valid value found in a row with `date_cells[0]` (the table's own most-recent period) instead of tracking raw index correspondence — verified via regression tests written against literal real HTML fixtures, not live fetches. **Any future rendered-report parser must verify column alignment against real, diverse companies before trusting a positional index — don't assume `segment_revenue.py`'s original alignment logic generalizes to a different report type.**

**A period-matching join that doesn't distinguish `instant` from `duration` period_type can silently fail 99.5-99.9% of the time for one whole class of concept, across the entire population, not just one company — found live 2026-09-13 verifying a real user report about Robinhood (HOOD).** `yfinance_financials/compare.py`'s `_load_our_periods()`/`_closest_period()` matched yfinance's quarterly figures against `core.period` rows by end-date proximity alone, with no period_type filter — but a real fiscal quarter routinely has BOTH a `duration` period (income statement/cash flow) and an `instant` period (balance-sheet snapshot) sharing the identical end_date, the same "two period rows, one real quarter" shape this project has hit before (Nike's FY/Q4, MSGS's overlapping duration spans). **Screener snapshot rebuilt from EAV to a wide, native-column table (2026-09-20, migration 0068) — a real design flaw, found by direct founder question ("is the database design correct?"), fixed through TWO iterations, the first of which measured WORSE than the original and was reverted before shipping.** `analytics.company_screening_snapshot` (built 2026-09-10, see that entry above) was itself already a real fix for a live-query performance problem, but was still EAV-shaped (`company_id, metric_definition_id, value`, 384,640 rows for a 5,282-company universe) — correct for sparse/rarely-co-queried attributes, wrong for a screener, which always wants several attributes of the SAME company at once. **First fix attempt, measured and REJECTED**: pivoted to one row per company with all 82 metrics packed into a single `metrics jsonb` column. **Two generalizable lessons**: (1) "a wide table needs no schema migration" and "a wide table is fast" are two SEPARATE claims — JSONB satisfies the first but can badly fail the second once a value's size crosses Postgres's TOAST threshold (~2KB), because every key access pays the FULL blob's decompression cost regardless of how many keys are actually needed; native columns satisfy both simultaneously here because `ADD COLUMN IF NOT EXISTS` on a nullable column is itself metadata-only, so "no migration needed" was never actually JSONB-exclusive to begin with. (2) A newly-created or newly-rebuilt table has no planner statistics until `ANALYZE` runs — the JSONB attempt's very first `EXPLAIN` badly misestimated row counts (`rows=39` planned vs. `rows=5217` actual) purely from being freshly created; always `ANALYZE` before trusting a performance measurement on a table that was just built or fully rewritten, or a bad plan choice can masquerade as (or hide) a real design problem.

**Three real, non-obvious operational gotchas hit building the `CONCURRENTLY` half, each fixed before the final successful run:** (1) the Supabase MCP `execute_sql` tool's own client-side timeout tore down the connection mid-build, and `CREATE INDEX CONCURRENTLY`'s failure mode for a torn-down session is a permanently invalid, half-built index left in the catalog (`indisvalid=false`) — `IF NOT EXISTS` checks only whether the NAME exists, not whether it's valid, so a naive retry silently no-ops against a broken index forever. Fixed by moving to a detached `psql` process (`nohup ... &; disown`) immune to any single tool call's timeout, plus an explicit `DROP INDEX CONCURRENTLY IF EXISTS` before every retry. (2) That still weren't enough — the retry hit a SERVER-side `statement_timeout` of 2 minutes, enforced by this project's Supavisor pooler connection regardless of client patience. `PGOPTIONS="-c statement_timeout=0"` (the standard way to set a startup GUC) was silently ignored by the pooler — confirmed live (`show statement_timeout` still read `2min` with `PGOPTIONS` set). (3) The fix that actually worked: `SET statement_timeout = 0;` as an explicit statement, in the same session, BEFORE the `CREATE INDEX CONCURRENTLY` — but only when fed to `psql -f <script>`, never `psql -c "SET ...; CREATE INDEX CONCURRENTLY ...;"`, because `-c` sends multiple `;`-separated statements as one Simple Query message that Postgres wraps in an implicit transaction (which `CONCURRENTLY` forbids), while `-f`/stdin dispatches each statement as its own separate protocol message/implicit transaction — confirmed by testing the `SET` propagation in isolation before trusting it against the real 27 GB table. All 5 indexes verified `indisvalid=true, indisready=true` afterward; a fresh advisor pull confirms both the `unindexed_foreign_keys` and `no_primary_key` categories are now fully empty. **Generalizable: this project's pooler enforces a hard server-side statement_timeout that a client-side option cannot override — any future long-running DDL/maintenance statement against this database needs an explicit `SET statement_timeout = 0` issued via a script file (`-f`/stdin), never `-c` or a client-side timeout knob, and should assume a `CONCURRENTLY` operation interrupted mid-build leaves an invalid object that must be dropped before retrying.**
