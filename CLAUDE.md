# CLAUDE.md — Scrooner Project Context

> This file is the entry point for any AI agent (Claude Code, a Claude Agent SDK build, or similar) working in the Scrooner codebase. It synthesizes the canonical product/decision docs in this folder. **If this summary and a source doc ever disagree, the source doc wins** — read the linked doc before making a decision that depends on it.

**`doc/` reorganized 2026-08-18** into topic subfolders (`foundational/`, `requirements/`, `execution-plans/`, `scoping/`, `planning/`, `reference/`, `status/`, plus unchanged `learnings/`, `adr/`, `html/`) — see [`doc/README.md`](doc/README.md) for the full layout. Doc numbers (e.g. "doc 19") are unchanged identities; only their folder changed. Every link in this file and across the repo was updated in the same pass.

> **Working on data correctness/verification specifically? Start at [`doc/data-moat/README.md`](doc/data-moat/README.md), not here.** Added 2026-09-08 as a dedicated, go-forward entry point for the moat itself (doc 01: data → trust → distribution → UX, in that order) — systems, learnings, and locked decisions scoped tightly to "is our data right and traceable," separate from this file's whole-product narrative. Nothing existing was moved there; it curates and points into what's already in `doc/learnings/`, `doc/status/`, and `pipeline/CLAUDE.md`.

> **Frontend consolidated to a single Next.js app, 2026-09-05 — see [doc 43](doc/planning/43_Single_Nextjs_Shared_Domain_and_Shadcn_Migration_Plan.md).** `apps/site` (Astro) is retired; `apps/app` (Next.js App Router) is now the only frontend, serving both public (`scrooner.com`) and authenticated (`scrooner.com/app`) routes from one runtime. **Caveat on this file's own historical entries below:** many pre-2026-09-05 paragraphs describing past frontend work were mechanically relabeled from `apps/site`/Astro to `apps/app`/Next.js when this decision landed, including inside quoted technical detail — e.g. an entry may say "Next.js, `output: 'server'`" even though `output: 'server'` is an Astro-specific config key that was never a Next.js concept. Treat any such Astro-specific technical detail inside a historical entry as accurate for **what was true at the time** (the page really was built in Astro then), not as a claim about Next.js. `pipeline/CLAUDE.md`'s own historical entries were NOT relabeled and still say `apps/site` — read those literally as the pre-migration path; the current path is under `apps/app`.

## What Scrooner is

A research and fundamental stock-screening product for US-listed companies. A serious retail investor describes a financial screen in **plain English**; Scrooner returns **deterministic, traceable** results computed from normalized SEC filing data — not an AI-generated opinion.

**Shortest product promise:** the easiest way to screen US companies using complex fundamental logic in plain English.

**North star:** be the site a US investor opens first to understand a company — and trusts enough to come back to every time.

Reference points for feel and philosophy: **Zerodha** and **Screener.in** — focused utility, restrained UI, fast, high trust, minimal decorative complexity.

## Who it's for

- **Primary:** serious self-directed fundamental investors researching US-listed companies.
- **Geography:** US + India initially, usable globally. English + USD only for V1.
- **Not the target:** day traders, options traders, passive-only investors, crypto users, institutions.

## The moat (in order)

1. **Data moat** — SEC EDGAR parsed once, normalized consistently, mapped to canonical concepts. Free and redistributable, so this can be free-forever without a data-cost trap.
2. **Trust moat** — every number traces to source filing, formula version, and data date. AI is an interface assistant, never the source of financial truth.
3. **Distribution moat** — thousands of indexable company/screen/glossary pages compound via SEO.
4. **UX wedge** — wins on *feel* (clean, calm, fast, mobile) not on metric count.

## Business model

Free core + paid premium (~$100/year hypothesis). Later: broker affiliate, ads, B2B data API. First commercial milestone: ~1,000 paying customers (~$100k ARR).

## Operating principles (KISS BORING)

| Principle | Rule |
|---|---|
| Correctness before breadth | A small trusted metric set beats a large questionable database |
| Determinism before AI magic | AI interprets intent; code + versioned data decide results |
| Traceability by default | Every number shows source, period, formula/version, data date |
| One source of truth | Each decision/metric/interface has one canonical home |
| Vertical slices | Finish usable data-to-interface paths, don't half-build every layer |
| Evidence before expansion | Add features/dependencies/markets only after observed demand |
| Static/public; dynamic/private | Next.js for crawlable content, Next.js for authenticated interaction |
| Manual verification is a feature | Inspect filings and edge cases before trusting automation |
| Low operational burden | Prefer managed, conventional components a solo founder can run |
| Kill scope aggressively | Anything not needed to validate the core job → Later or Never |

**When in doubt:** choose whichever option improves data correctness, auditability, or user simplicity with the least operational burden. A new dependency must solve a demonstrated problem, not a hypothetical one.

## Architecture at a glance

Three concerns, sharing governed data, each with a narrow responsibility:

1. **Data pipeline** (`pipeline/` in this repo) — Collector → Normalizer → Mapper/Metrics, in Python, writes to shared Postgres.
2. **Public SEO website** — `scrooner.com`, Next.js, static-first, indexable (company pages, curated screens, guides, glossary, marketing).
3. **Authenticated app** — `scrooner.com/app`, Next.js App Router, interactive screener/prompt UI, auth, saved screens, billing.

```
SEC EDGAR → Collector (raw, lossless, immutable) → Normalizer (canonical facts)
          → Mapper/Metrics (canonical concepts, versioned formulas)
          → Company Master (identity, market data)
          → Screener (deterministic predicates) ← AI query layer (NL → validated schema)
          → served via Next.js (scrooner.com) + Next.js (scrooner.com/app)
```

**Component boundaries are strict** — see doc 04's "Data boundaries" table before writing pipeline code. E.g. the Collector may fetch/retry/checkpoint/hash/store but must never normalize, repair, infer periods, map concepts, or calculate metrics.

Any service's own connection-pool `max` needs to leave real headroom below 15, not just fit its own peak concurrency in isolation — check current usage (`select count(*) from pg_stat_activity`) before raising a pool size, don't just pick a number that works in isolated testing.

**A Postgres database can enter a genuine, project-wide read-only state independent of any one session or transaction** — found live 2026-08-21: `default_transaction_read_only` came back `on`, sourced from `configuration file` (not a per-session `SET`), rejecting writes even for the `postgres` superuser role, while `pg_is_in_recovery()` was `false` (so not a replica-routing issue) and database size was nowhere near the plan's quota. This is a platform/control-plane state, not something fixable from application code — if a batch job fails with `ReadOnlySqlTransaction`, check `show default_transaction_read_only` directly before assuming a code bug or retrying blindly; it can also clear on its own within the same session (it did, here, without any action taken).

Full writeup: `doc/learnings/2026-09-03-resolve-delete-scope-and-hung-workers.md`. A third issue was found but NOT root-caused: `coverage_snapshot.py`'s own insert path left several rows holding stale values despite `compute_snapshot()` itself computing correctly (traced explicitly) — ruled out timing, SQL, triggers, and a uniform `executemany` bug, but the exact mechanism (a Supavisor pooler interaction is the leading, unconfirmed hypothesis) was never pinned down. Every affected row was individually cross-checked against live data and corrected by hand; see `doc/learnings/2026-09-03-coverage-snapshot-insert-anomaly.md` for the full elimination trail — flagged as open, not closed, for whoever next touches a similar delete-then-`executemany` pattern. **Final verified score, 2026-09-03: `avg_metric_coverage_score` 54.76%, `avg_concept_coverage_score` 73.15%**, zero mismatches confirmed against live data before reporting.

**Real gap found wiring `scrooner-map snapshot-coverage` into a daily cron (2026-09-03): no scheduled GitHub Actions workflow reprocesses the Normalizer/Mapper stages at all.** `scrooner-incremental` (the only daily job, `pipeline-refresh.yml`) is Collector-only — it discovers new filing metadata into `raw`, but nothing downstream automatically reruns `resolve-facts`/`calculate`/etc. into `core`/`analytics`. Every full-population Mapper run this session was triggered manually. Added the snapshot step to the existing daily workflow (safe, additive — it just reads and records the current state), but deliberately did NOT also automate the reprocessing chain itself: a full run took 3-4+ hours this session, and doing that daily against the full population would be wasteful and likely exceed normal CI cost/timeout norms. An incremental-scope version (react only to what `scrooner-incremental` found new that day) is the likely right shape, but needs an explicit decision before building — see `doc/planning/41_Scrooner_Coverage_Improvement_Plan.md`'s "Cadence" section.

**Prioritization filter** — before building anything, ask:
- Does this improve core screening correctness, clarity, or repeat usage? (If no → don't build now.)
- Is it required for the next validation gate? (If no → Later.)
- Can a solo bootstrapper operate it reliably? (If no → simplify or reject.)
- Is demand supported by user behavior, not just a hypothesis? (If no → keep as hypothesis.)
- Can it be tested and traced? (If no → redesign first.)

## Claude Code tooling in this repo

- **A commit on `main` must be pushed in the same turn it's made — never left local-only "for later."** This is a hard, standing rule as of 2026-09-12, added after the identical failure recurred three times: a real fix (the pipeline-freshness alert-fatigue fix, then the sanity-layer's missing GitHub secrets, then others) got committed locally but sat unpushed for a day or more, so the scheduled GitHub Actions cron kept running the *old*, still-broken workflow file even though the fix "existed" — each recurrence looked like a fresh mystery until someone actually ran `git log origin/main..HEAD` and found the gap. The fix is procedural, not tooling: before ending any turn that includes a commit, push it, or say explicitly why not (e.g. the user asked to hold off). Don't try to solve this with a git hook that auto-pushes — that was attempted 2026-09-12 and rightly blocked by the permission classifier, since an automation that pushes to remote without per-action confirmation is exactly the class of risky action this project's own safety discipline (root CLAUDE.md's "Executing actions with care") exists to catch. Before trusting that any previously-reported fix is actually live, check `git log origin/main..HEAD` first — a fix "committed" is not the same claim as a fix "deployed."
- `.claude/settings.json` has a `Stop` hook that fires once per session and prompts a review of whether anything durable came up worth adding here — that's the source of any "Stop hook feedback" message. It dedupes via a `/tmp` marker keyed on session id, so it won't loop.
- `.claude/skills/`, `.claude/commands/`, `.claude/agents/` — mostly still empty by design; don't pre-populate them, add an entry only after the same multi-step workflow has come up 2-3 times in real sessions. Two exceptions so far, both added 2026-08-14:
  - **`verify-collector-day`** — runs a Collector day's job against the live SEC API + Supabase and checks it against doc 08's stated "Done when" text, with actual evidence (row counts, query output), not an assertion. Earned its place: the same run-then-verify loop had already repeated three times in one session (initial schema, the `(cik, ticker)` fix, the `sec_filing_documents` fix) before it was built.
  - **`run-collector-day`** — the fuller loop this skill's own first real use exposed: launch a remote/cloud agent for a Collector day, then *never trust its self-report* — Day 3's agent stopped twice with vague, non-terminal language ("waiting for...", "set a background watcher...") despite `status: completed`, and the work was genuinely incomplete both times (checked directly against the live DB, not inferred). Encodes: launch with full context, verify independently on every completion notification, resume the same agent with specific evidence-backed corrections if incomplete, write a `doc/learnings/` entry, only close out on real evidence, never auto-chain into the next day.
- [`doc/learnings/`](doc/learnings/) — day-by-day engineering journal (added 2026-08-14): what broke, how it was actually found (almost always by checking live data/state, not by reasoning from memory), what changed, and the generalizable lesson. Not a decision doc — read it to avoid rediscovering a problem this project already hit once. `run-collector-day` writes to it automatically now.
- [`doc/reference/claude-code-guide.md`](doc/reference/claude-code-guide.md) — non-canonical (no status line by design) how-to reference for building a skill/subagent/slash-command when one is actually justified: file locations, frontmatter fields, gotchas. Its own "Suggested starting set for Scrooner" (a `scrooner-conventions` skill, `filing-reconciler`/`collector-tester` subagents, `/reconcile-golden`) is still mostly *candidates for later*, not a to-do list: `filing-reconciler` needs the Normalizer to exist (it doesn't yet), `collector-tester` needs Day 4's actual retry/idempotency suite to exist as a repeatable thing (also not yet). Revisit each individually once its own precondition is real, not all at once just because one skill got built.

## Notes for skill / agent authors

- This project has a strong bias toward **narrow, deterministic, auditable** behavior — any agent or skill built for Scrooner should default to the same: prefer explicit, traceable logic over generative shortcuts, especially anywhere near financial calculations.
- Anything touching the **Collector** must stay lossless/immutable — a skill that "cleans up" or "fixes" raw data at collection time is building against the architecture.
- Anything touching the **AI query/prompt layer** must only ever emit a structured, schema-validated query — never a stock list, a fabricated metric, or free-text financial claims.
- Check doc 02 (Decision Register) before proposing new dependencies, architecture changes, or scope additions — most tempting additions (real-time data, dashboards, chatbot Q&A, broader exchanges) have already been explicitly rejected or deferred for a stated reason.
- Whenever Mapper/Metrics work starts: it must treat `core.fact.is_authoritative = false` as a hard filter, and "no authoritative fact for this period" as a valid, expected null result — never fall back to an arbitrary non-authoritative row to avoid a gap. As of 2026-08-15, ~6.6% of duplicate `(company, concept, unit, period)` groups in the golden-8 are genuine unresolved conflicts (see `doc/learnings/normalizer-day-05-dedupe.md`) — common enough that silently picking one would be a real, frequent correctness bug, not a rare corner case.
- Any code path handling a reported financial value must stay `Decimal` end to end — parse JSON with `parse_float=Decimal`, never cast to `float` for calculation convenience, and serialize as a string (not a JS number) at any API/frontend boundary. See doc 04's correctness controls.
- Any new per-company/per-concept batch job (Mapper included) loads its lookups into memory up front and batches its writes — never a query per candidate row inside a loop. See doc 04's correctness controls; found the hard way (Normalizer Day 7, `doc/learnings/normalizer-retrospective.md`) when a stage that deviated from this shape hit real connection timeouts on a large company that every other stage, following this shape from the start, never hit.
- **Before writing any new fetch against a SEC filing type, or widening an existing fetch's date range: check [`doc/foundational/38_Scrooner_History_Depth_Gate.md`](doc/foundational/38_Scrooner_History_Depth_Gate.md) first.** It's a 5-case decision tree keyed on the source's own real refiling cadence (mandatory-every-period vs. per-transaction vs. only-if-changed vs. already-self-comparing), not a single blanket rule — a source that only refiles when something changes (e.g. Schedule 13G) needs a *longer* window than one with a mandatory cadence, which is the opposite of the intuitive guess. Hard ceiling either way: never treat data before 2015-01-01 as current for any display-facing feature. Written after `ownership/beneficial_ownership.py` was found live (2026-08-30) to have no history bound at all, requiring a 90% (193,751-row) cleanup once fixed — this gate exists so that cost is paid once, not per fetch module.
- **Any full-population bulk `executemany` write must be batched (~5,000 rows/chunk), never one call over the whole matched set.** Found live 2026-08-31: `ownership/institutional.py`/`mutual_fund.py` each did a single unbounded `executemany` — fine at golden-10 scale, but at real full-population scale (2.35M / 1.9M matched rows, once the CUSIP crosswalk stopped being golden-10-only) it drops the Supabase pooled connection mid-write (`SSL connection has been closed unexpectedly`). Chunking keeps it a single logical delete-then-reinsert pass, just with bounded round-trips.
- **Any delete-then-reinsert write scoped by `company_id` (or similar) needs a supporting index on that column *before* it runs at full-population scale, not after.** Found live 2026-08-31, same day as above: even after batching the insert, `core.institutional_ownership`'s `delete ... where company_id = any($1) and source_zip = $2` timed out on its own, because no index existed on `(company_id, source_zip)` and the table had grown past 2M rows — a full sequential scan every write. Fixed with `idx_institutional_ownership_company_source`/`idx_fund_ownership_company` (migration `0029`). Check for this index gap proactively on any table a batch job deletes-then-reinserts into once it scales past golden-10.
- **A background `bash -c "... | xargs -P N ..." &` wrapper is NOT stopped by killing its current child workers.** The wrapper's own `xargs` loop just spawns new workers from wherever it left off in the batch list. Killing only the visible `scrooner-*` worker processes (not the wrapper's own PID) let two full copies of the same full-population job run in parallel, undetected, for 2+ hours (2026-08-31) — no data corruption since writes are idempotent, but real wasted SEC-fetch budget. Always locate and kill the wrapper `bash -c` process itself (`ps aux | grep "xargs -P"`), not just its children.
- **`uv run <service>` does not auto-load `.env`.** `apps/backend`'s `uv run uvicorn main:app` crashes with `KeyError: 'SUPABASE_URL'` unless the shell has explicitly sourced `.env` first (`set -a; source .env; set +a`) — unlike `pipeline`'s own CLI commands, which load config themselves. `apps/app`'s Next.js `dev` script also needs `next dev --webpack` explicitly on this darwin/arm64 dev setup (Turbopack, the default, has no native bindings here and crashes on launch) — `build` already uses `--webpack`, `dev` doesn't; pass the flag by hand when starting it locally.
- **Employee headcount, About text, and company website are real but only extractable from each 10-K's own prose, not any structured field.** Checked live 2026-08-30/31: `dei:EntityNumberOfEmployees` covers only ~3.5% of companies (not even Apple/Microsoft/Costco tag it), and `submissions.json`'s `website`/`investorWebsite` fields exist in SEC's own schema but are empty for every company checked. All three are real, disclosed in Item 1's "Human Capital"/business-description text and the mandatory "Available Information" section — built in `pipeline/src/scrooner_pipeline/company_master/business_text.py` (regex extraction, HTML-entity decoding, hidden-inline-XBRL stripping) + `employee_headcount.py` (fetch orchestration), stored in `core.employee_headcount_disclosure`/`core.company.about_text`/`core.company.website`, wired into `apps/app`'s company page. Headcount is confirmed **annual-only** (a 10-Q never repeats the Human Capital section) — "quarterly headcount" is not obtainable from any SEC filing, not an engineering gap. See `doc/scoping/39_Scrooner_Employee_Headcount_Full_Coverage_Plan.md`.
- **Revenue by segment is extractable, contra earlier docs calling it "structurally blocked."** The standard Company Facts API does strip dimensional/segment XBRL entirely (doc 22's finding still holds), but each filing's own auto-rendered `R*.htm` "Details" report (found via `FilingSummary.xml`) has the real segment breakdown in a parseable HTML table, complete with the real XBRL concept ref per row (`onclick="Show.showAR(this, 'defref_...')"`). Built `pipeline/src/scrooner_pipeline/segments/segment_revenue.py` (2026-08-31), verified for 7 of the golden-10 (Apple, Microsoft, Alphabet, Nike, Block, Reddit, JPMorgan-partial); real report-title false positives are common (a bank's "Loans - By Portfolio Segment" or a "... Reconciliation (Details)" report both match a naive "segment" keyword search) — title selection needs a scoring heuristic (prefer "revenue"+"segment", exclude known off-topic triggers), not first-match. Segment dimension rows use several different XBRL axes depending on filer (`StatementBusinessSegmentsAxis`, `StatementGeographicalAxis`, `SubsegmentsAxis`, `ProductOrServiceAxis` all seen live) — checking only one axis silently under-covers real companies.
- **`analytics.metric_value` has no unique constraint on `(company_id, metric_definition_id, period_label, period_end)`.** `calculate.py` can silently fan out into 2+ competing rows for the same slot when Normalizer correctly leaves more than one `is_authoritative=true` fact unresolved for a concept/period (the same real ambiguity Normalizer Day 5 already documented as deliberate, not a bug) — found live 2026-08-31, 29,764 duplicate groups, 1,659 with genuinely different values. Cleaned up (kept lowest `id` per group, 30,183 rows removed) but the root cause in `calculate.py`'s resolution logic is still open — flagged, not fixed, same as `insider_summary.py`'s N+1 pattern. See `doc/learnings/2026-08-31-metric-value-duplicate-rows.md`.
- **A same-sum-mode keyword-matched XBRL candidate tag is frequently a different concept entirely that happens to share vocabulary — verify semantic equivalence against real company data, never trust "same statement area + similar name + high company count" alone.** Found live 2026-09-02 building a systematic tag-coverage library (`pipeline/scripts/build_tag_coverage_library.py`, `doc/reference/40_Scrooner_XBRL_Tag_Coverage_Library.md`): the automated top-ranked candidate for `research_and_development` was a deferred-tax-asset tag, `goodwill`'s candidate explicitly *excludes* goodwill, `comprehensive_income`'s candidate was an accumulated balance not a period flow. Roughly half of the top-ranked candidates checked by eye were wrong. Every candidate this library (or any future keyword-driven tag search) surfaces is a lead to investigate, never an approval — spot-check 2-3 real companies before adding anything past `provisional` confidence, same discipline as every other `concept_mapping` addition this project has made.
- **A batch job's "keeps going past a single company's failure" resilience can silently strand that company at zero forever, invisible in the aggregate summary.** Found live 2026-09-03: `normalizer/periods.py`'s `_bracket_fye()` extrapolated a company's fiscal-year-end pattern by stepping `date(year ± 1, month, day)` one year at a time — crashes with `ValueError: day is out of range for month` for any company whose observed FYE anchor is Feb 29, the instant extrapolation steps into a non-leap year (3 years out of 4). MannKind Corp (a real, ordinary 10-K/10-Q domestic filer, not an edge case by any other measure) hit this and was left with **zero `core.period`/`core.fact`/`analytics.canonical_fact` rows** despite the Collector having successfully fetched its real, 553-tag companyfacts payload — the crash was logged as one `errored=1` in a per-company debug line, never surfaced in the run's own aggregate stats. Broader check found 29 active companies total with real `core.filing` rows but zero `core.period` rows; 24 were structural (real royalty/asset-backed trusts with no Company Facts API payload at all), 5 were this exact bug. Fixed with a `_step_year()` helper that rolls Feb 29 to Feb 28 in a non-leap target year. Recovery run for the 5 affected companies (full Normalizer + Mapper chain): 29,468 new `core.fact` rows, `skipped_period_not_found` dropped from 48,580 to 0 confirming every one of those skips was this bug's downstream symptom. See `doc/learnings/2026-09-03-leap-year-fye-anchor-crash.md`. **Lesson, generalizable beyond this bug: periodically check "does every company with a real upstream payload have a downstream row" directly — a clean-looking aggregate summary and a per-company silent failure look identical from the outside.**
- **A module defaulting a "snapshot date" to Python's local `date.today()` can silently disagree with the database server's own `current_date` — root-causing a previously "unexplained" write anomaly.** Found live 2026-09-04: `coverage_snapshot.py`'s `write_snapshot()` defaulted to local-clock `date.today()` (this dev machine runs IST, UTC+5:30) while the Postgres server runs UTC. During the ~5.5-hour daily window where IST has already rolled to the next calendar date but UTC hasn't, a same-day verification query using SQL's `current_date` silently read yesterday's real, correctly-written row instead of today's — exactly reproducing the prior day's "insert anomaly" symptom for the aggregate `score` rows (previously attributed, unresolved, to a possible Supavisor pooler quirk). Fixed by switching the default to `datetime.now(timezone.utc).date()`, keeping every environment (this machine, the UTC-based GitHub Actions runner) consistent. Does **not** fully explain the original investigation's narrower finding (3 individual concept rows + 1 metric row stale within the same insert batch) — that stays open. See the 2026-09-04 addendum in `doc/learnings/2026-09-03-coverage-snapshot-insert-anomaly.md`. Any other module defaulting a "today" value the same bare way is worth the same check.
- **Grouping a data-gap population by which tag they already share with each other is a real, cheap discovery method — distinct from keyword-based tag search.** Sizing a planned Parser 3 build (rendered-table extraction) before committing to it, breaking down the 693 companies missing `revenue` surfaced 44 with no `sic_description` at all, every one a Business Development Company — a real sector whose income statement genuinely has no revenue line (they report "Total investment income," `us-gaap:GrossInvestmentIncomeOperating`, a standard tag that shares zero vocabulary with "revenue"). Shipped as a new, deliberately separate `bdc_total_investment_income` canonical concept (118 real companies, broader than the 44-company sample) — never merged into `revenue`, same sector-isolation reasoning as banks/insurers/REITs. Built a reusable tool for this, `pipeline/scripts/find_concept_gap_clusters.py` (user-suggested: cluster the gap population by shared tags rather than investigating one company at a time), which needed two real refinements before it produced signal instead of noise: (1) restrict candidates to `unit='usd'` + `period_type='duration'` facts — an unfiltered version was dominated by balance-sheet/equity tags (`RetainedEarningsAccumulatedDeficit`, `AdditionalPaidInCapital`) that SPACs/shells share for unrelated reasons; (2) exclude SIC categories already confirmed structural/legitimate-absence (SPACs, pharma, biotech, mining) — even after the unit/period filter, this large homogeneous population's shared "pre-revenue capital-raising" tags (IPO proceeds, stock issuance costs) still drowned out the real signal. With both filters applied, the tool immediately surfaced a **second, not-yet-built cluster** the same way: mortgage REITs (AGNC Investment Corp, Ellington Financial, TPG RE Finance Trust, etc.) sharing `ManagementFeeExpense` but no investment-income tag of their own. See `doc/learnings/2026-09-04-bdc-sector-concept-and-gap-clustering-tool.md`.
- **A `sum`-mode canonical concept needing a widened tag set must never add the new tags directly to its own `concept_mapping`** — `resolve.py`'s `sum` mode sums every matched tag unconditionally, with no "prefer group A, else group B" logic, so adding a company's alternate/split tag alongside its already-mapped combined tag double-counts for any company reporting both. Found and fixed live 2026-09-02 for `total_debt` (`LongTermDebtCurrent`+`LongTermDebtNoncurrent` split tags vs. the existing combined `LongTermDebt` tag, ~2,168 companies report both). Fixed with a new, generalized `mapper/concept_fallback.py` module: a second `sum`-mode concept (`total_debt_split`) captures the split tags cleanly (they can't double-count each other), then a third concept (`total_debt_resolved`, zero `concept_mapping` rows of its own, never touched by `resolve()`) merges "primary total_debt where present, else total_debt_split" at Python read-time — the same "prefer resolved value A, else B" idiom already live in `expanded_metrics.py`'s/`price_metrics.py`'s shares-outstanding fallback. Reusable directly for any future `sum`-mode concept needing the same pattern (`FALLBACK_PAIRS` list).
- **A defensive check that closes one known false-positive mode is not proof a signal is now fully trustworthy in every dimension — check it against data already on hand that the check itself doesn't look at.** Found live 2026-09-02: `company_master/status.py`'s Form 15 "delisted" inference already had a real, evidence-based safeguard (only trust a Form 15 whose own cover page says "common stock," added after JPM's Chase-Capital-trust false positive) — but 222 real active companies (AMD, Intel, HP, Caterpillar, US Bancorp, Applied Materials among them) still passed that exact check and got marked `delisted` anyway, because 192 of them kept filing real 10-Ks/10-Qs for years or decades after their "common stock" Form 15 (AMD's dates to 1996; it filed a 10-Q in 2026-08). Almost certainly a historical Section 12(g)→12(b) exchange up-listing, not a real delisting. Fixed by cross-checking the confirmed signal against filing recency — a signal `status.py` was already computing for every company anyway, just not using to sanity-check this one. Blast radius went beyond the one bug: any full-population batch job (like this session's tag-coverage rollout) whose CIK list is generated by filtering `status='active'` silently drops every falsely-`delisted` company, even though its underlying `core`/`raw` data is fine — check `core.company.status`'s distribution before trusting a "full population" batch list reflects the real active set. See `doc/learnings/2026-09-02-delisted-status-false-positive.md`.
- **Any coverage/count query against `analytics.metric_value` must filter `value is not null` — a bare `count(distinct company_id)` counts documented failures as successes.** `metric_value` stores an explicit row with `is_null_reason` set even when a metric couldn't be computed for a company (the same traceability discipline as `excluded_missing_data` elsewhere), so a naive per-metric-definition row count treats "we tried and correctly got null" identically to "we computed a real value." Found live 2026-09-02, in the very first run of the brand-new coverage-score tracker (`mapper/coverage_snapshot.py`, doc 41) meant to catch exactly this kind of gap — several metrics showed a false 100% (including `ev_ebitda`/`ev_sales`/`peg_ratio`/`buyback_yield`/`total_shareholder_yield`, which were actually a genuine 0%, since all 5 depend on `market_cap` and had last been computed while `market_cap` itself was universally null). `canonical_fact` (the concept-level table one layer upstream) does NOT have this problem — it only ever stores real values, never an explicit-null row — so this filter is specifically a `metric_value` concern, not a general one. See `doc/learnings/2026-09-02-coverage-score-system.md`.
- **`mapper/resolve.py`'s per-company delete used to be scoped only by `company_id`, silently wiping any zero-`concept_mapping` concept (e.g. `total_debt_resolved`) on every `resolve-facts` run.** Fixed 2026-09-03 by scoping the delete to only `canonical_concept_id`s that have ever had a `concept_mapping` row (`_load_managed_concept_ids()`) — a concept resolve() has no mappings for is now structurally untouchable by it, rather than depending on operators always running `resolve-concept-fallbacks` immediately after `resolve-facts` (which `concept_fallback.py`'s own docstring already asked for, but nothing enforced, and got skipped twice in one session before a coverage-score regression caught it). **Any future zero-mapping "resolved by a separate module" concept is now safe by construction** — no new discipline needed. See `doc/learnings/2026-09-03-resolve-delete-scope-and-hung-workers.md`.
- **`common/errors.py`'s `log_error()` — the shared per-company dead-letter handler at 20 call sites across the Normalizer and Mapper — used to be unprotected against its own failure.** When the *original* error was a dead database connection, `log_error()`'s own `rollback()`/insert/`commit()` also raised, and nothing caught that second exception — silently violating its own documented contract ("one company's exception must never abort the batch") and crashing the entire remaining batch of up to 15 companies instead of skipping just the one that failed. Fixed 2026-09-03 by wrapping `log_error()`'s own body in try/except. **A module's docstring promising a contract is not the same as code that enforces it** — verify the failure path itself is tested, not just the happy path.
- **A background worker can hang for hours, not just minutes, with zero client-side error output — and a shell wrapper's own "done" message does not mean the underlying work finished.** Found live 2026-09-03: 3 of 6 `xargs -P 6` workers sat alive-but-stuck for 4+ hours (`pipeline/CLAUDE.md`'s existing "silent multi-minute hangs" note undersold how long this can run); `xargs` still printed a clean completion banner after its own pipeline exhausted the input list, but only 889 of 5,216 companies had actually been processed, discovered only by checking `min(company_id)`/`max(company_id)` actually touched against the real database, not by trusting the log's own success banner. When resuming or verifying any batch job's real completion, check the database directly for the actual population reached, not the wrapper script's own exit message. A Monitor-based watchdog (poll `ps` every 60s, kill any single-company worker older than ~12-15 minutes) is now the standard mitigation for this session's remaining reruns.
- **`mapper/expanded_metrics.py` was silently wiping `market_cap`/`trailing_pe`/`dividend_yield`/`ebitda`/`debtor_days`/`inventory_days`/`payables_days` on every `calculate-expanded-metrics` run, never restoring them.** Found live 2026-09-03 re-checking the full coverage list: 3 of the 6 locked V1 price metrics showed a genuine 0% despite having been verified real hours earlier. Root cause: its per-company delete-then-reinsert scoped the delete by `list(metric_ids.values())`, where `metric_ids` held BOTH its own 9 real outputs AND 8 metrics it only reads as dependencies (owned by `calculate.py`/`price_metrics.py`) — deleting all 17, reinserting only its own 9. Fixed by scoping the delete to an explicit, named `OUTPUT_METRIC_NAMES` set instead of the whole dict (1 new regression test). **Audited all 8 other `calculate`-family modules for the same shape — none had it**; each either uses a single non-list `metric_definition_id`, builds its delete list from an explicit named subset, or (like `reconciliation.py`) never mixes metric-level reads into the same dict as its outputs in the first place. Generalizable check for any future module with this shape: a function that both reads dependency values through an ID-lookup dict AND deletes-then-reinserts must build its delete target list from an explicit "this is what I write" set, never from `dict.values()` of whatever was loaded for convenience. Full writeup and restoration: `doc/learnings/2026-09-03-expanded-metrics-delete-scope-bug.md`. **Restoration completed same day, 0 errors, verified against live data: `market_cap` 0%→60.03%, `trailing_pe` 0%→48.72%, `dividend_yield` 0%→16.09%.** Same day, directly asked to find "core metrics that should be near-100%": sampled companies missing `revenue` (86.3%) and `shares_outstanding` (91.0%) by name/industry rather than assuming the shortfall was inherent. `revenue` had a real, closeable gap — J.M. Also raised `lib/company/db.ts`'s pool `idle_timeout` 20→90 so a cache-miss regeneration during low traffic doesn't pay a needless reconnect between two regenerations minutes apart. 87/87 frontend tests, `tsc`, `eslint` all clean. **Generalizable: a bare `revalidate` export is a no-op for any Next.js page reading Postgres directly (the `apps/app/lib/*/db.ts` pattern) — it only fires for `fetch()`-based data, and silently doing nothing is easy to mistake for "already handled."**
  **Same day, addendum, directly prompted ("why we need to run query everytime, when opening company?"): `unstable_cache` replaced with Redis.** Re-examining that question surfaced the real gap in the first fix: `unstable_cache`'s default cache handler (no custom `cacheHandlers`/`incrementalCacheHandlerPath` configured) is per SERVER PROCESS, not shared — invisible on the single dev server this was tested against, but means every instance of a horizontally-scaled deployment would independently pay the full query cost on its own first hit per ticker. Replaced with `apps/app/lib/company/cache.ts`, a Redis-backed cache with the exact same fail-open contract as `apps/backend/cache.py` (`company-page:*` keys, separate from the backend's own `screen:*`/`auth-user:*` — same Redis instance in production, disjoint key space), justified as a second use of the Redis dependency ADR 0001 already accepted, not a new infrastructure decision. New `redis` npm dependency in `apps/app` (mirrors the Python `redis` package `apps/backend` already uses); `REDIS_URL` added to `apps/app/.env.local`/`.env.example`, optional (absent/unreachable Redis fails open to Postgres, same as the backend). **Verified live, real production build across THREE separate `next start` processes** (not just repeat requests to one): a cold ticker still costs the real ~10s; a repeat request on the same process costs ~0.04s; critically, a **brand-new process** (killed and restarted on a different port) serving a ticker another process had already cached returned in **~0.27s** (a Redis hit, not a requery) — proving the cross-instance sharing `unstable_cache` couldn't provide — while a still-uncached ticker on that same fresh process correctly still cost the real ~9.7s, confirming the cache stayed honestly per-ticker throughout. 87/87 frontend tests, `tsc`, `eslint` clean after the swap.
  **Same day, second addendum, directly prompted ("why is it that slow, can you check db design, any flaw there") — three real missing-index flaws found and fixed, migration `pipeline/db/migrations/0066_company_page_hot_path_indexes.sql`.** A cache HIT is now fast, but that doesn't explain why a cache MISS was slow in the first place -- checked by running `EXPLAIN (ANALYZE, BUFFERS)` against companies deliberately NOT cache-warm (a random obscure ticker, then AAPL after other testing had evicted it from shared_buffers) rather than trusting the earlier 207ms number, which turned out to be a buffer-cache-warm artifact from repeated manual testing, not representative. Found: (1) `core.listing` had no index usable for a ticker lookup at all -- only `UNIQUE(company_id, ticker)`, useless when ticker is the known value -- so every ticker lookup (the company page, search/autocomplete) did a full `Seq Scan` of the whole table; fixed with `idx_listing_lower_ticker on core.listing (lower(ticker))`. (2) `core.company` had no index on `y_industry`, the peer-comparison join key -- every page load did a full `Seq Scan` of the active company population for peers; fixed with a partial index matching the query's own filter, `idx_company_y_industry_active on core.company (y_industry) where status = 'active'`. (3) **The serious one**, only visible testing a large company, not a small one: `core.institutional_ownership`'s per-company filer-dedup subquery had no covering index -- the existing index didn't cover the dedup's own sort columns (`filer_name`/`is_amendment`/`filing_date`), so Postgres heap-fetched all 18,962 of AAPL's rows individually, measured at **8,205ms for that one node alone** (~0.43ms/row, real random I/O against a 1.8GB table, not a planner mistake) -- invisible in every earlier test since a small ticker has orders of magnitude fewer rows there. Fixed with a covering index matching the subquery's exact sort order plus an `include` for the selected columns, turning it into a single Index Only Scan. **Verified live, before/after**: VITL (small) 861ms→82ms execution; AAPL (large) 8,767ms→140-187ms (the institutional_ownership node alone 8,205ms→18ms). All three indexes are `create index if not exists`, applied directly to the live database, confirmed idempotent on a second run. No application code changed -- purely schema-level, orthogonal to the Redis caching addendum above.
  **Same day, third addendum, directly prompted ("match the speed with screener speed... apply same fix on screens and screener page please"): the same audit applied to `apps/backend`'s saved-screens endpoints, found and fixed the one real gap.** `app.saved_screen`/`app.user_screen_run`/`app.screen_result`/`app.screen_result_item` were already correctly indexed and `db_pool.py`'s pool was already `min_size=1`/`autocommit=True` (no cold-connect penalty) -- that work already happened 2026-09-10/12. `/v1/screen` and `/v1/screen-runs` already have thorough Redis caching, but `routers/saved_screens.py`'s `list_screens` (`GET /v1/screens`) and `get_screen` (`GET /v1/screens/{slug}`) had **none** -- every call paid a real Postgres round trip even though query execution itself is sub-millisecond (confirmed via `EXPLAIN ANALYZE`), because the round trip, not execution, is the real cost. Added a 30s-TTL cache for the saved_screen row itself (`screens-list:{user_id}`/`screen-detail:{user_id}:{slug}`, same fail-open contract as every other entry in `cache.py`) -- deliberately NOT caching the run's own paginated result data, which already has its own separate, correctness-sensitive cache (`get_cached_run_page`, keyed by run_id). Every write (`create_screen`/`rename_screen`/`delete_screen`/`refresh_screen`) explicitly invalidates the relevant keys -- TTL is a memory-hygiene backstop, not the correctness mechanism. One real wrinkle: `rename_screen`/`delete_screen` only ever took a numeric `screen_id`, not the row's `slug`, needed to invalidate the slug-keyed cache -- fixed by changing `RETURNING id` to `RETURNING slug` rather than adding a second query. 7 new tests (`tests/test_saved_screens_cache.py`, monkeypatched -- this project's test `REDIS_URL` is deliberately unreachable, matching `test_screen_run_cache.py`'s own established discipline), backend suite 41→48. **Verified live against the real database and a real local Redis, using real saved-screen data**: `GET /v1/screens` 297.7ms→0.29ms (1,027x), `GET /v1/screens/{slug}` (detail + run page) 1,760.6ms→2.14ms (823x). `apps/app`'s own screens pages (`/app/screens`, `/app/screens/[slug]`) deliberately kept `force-dynamic`/`cache: "no-store"` unchanged -- correct, since this is per-user data that (unlike the public company page) can never be shared across users; the new cache lives entirely on the `apps/backend` side, same as `/v1/screen`'s own.
